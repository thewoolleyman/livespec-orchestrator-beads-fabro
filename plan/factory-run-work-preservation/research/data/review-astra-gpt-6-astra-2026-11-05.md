Ranked findings, most severe first:

1. **High — The detached-HEAD safeguard does not survive the engine checkpoint, and recovery can select a snapshot that discards all earlier work.**

   **Claim.** Reading `fabro/run/<run-id>` is necessary but insufficient. The engine itself can replace that branch from detached HEAD before the proposed preservation step reads it. Keeping the older ref prevents physical destruction of its objects, but the proposal then prohibits recovery from that older ref. This turns preserved work into work the recovery algorithm refuses to use.

   **Evidence.** `Proposal:28` requires preservation after the engine checkpoint, selects the newest ref, and rejects only a commit reachable from the item's base commit. `Proposal:167` says the run's other work-in-progress refs MUST NOT be used. In the actual checkpoint implementation, `commit()` first calls `ensure_repository()` (`F/lib/components/fabro-petri/src/checkpoint.rs:475-494`). If HEAD is not already on the run branch, that method executes `git checkout -q -B <run-branch>` with no start point, resetting the branch to the current HEAD (`:774-789`). It then creates an allow-empty checkpoint (`:521-537`). The checkpoint runs before the after-visit hook (finding 3).

   Concrete failure sequence: `implement`, `fix` and `review_fix` produce work preserved at F; a late refresh/publication path leaves HEAD detached on default-branch D; its checkpoint resets the run branch and creates C on D; preservation correctly keeps F and creates a sibling at C; a cancel or `rm` follows; recovery chooses C and refuses F. C is a *child* of D, so even when D is the item's base, C is not reachable **from** that base and passes the proposed exclusion. Several visits' work is omitted from recovery despite being fetchable at F. This is a source-derived counterexample starting from the detached state described in `Note:108-123`, not a fresh reproduction of that incident. The incident's exact historical sequence is **UNVERIFIED** here. Also, today's `refresh_repair` node only reads a brief and routes (`R/.claude-plugin/.fabro/workflows/implement-work-item/workflow.fabro:721-725`); Scenario 314's claim that this node itself rebases (`Proposal:61-65`) misidentifies the current owner of that operation.

   **Recommendation.** Separate “latest snapshot observed” from “snapshot approved as the recovery seed.” Preserve divergent snapshots, but do not automatically promote a default-only rollback over an existing work-bearing snapshot. Require evidence of the intended rewrite, or hold automatic recovery with both candidates named. Test the actual checkpoint's `checkout -B` behavior, including an empty checkpoint on the default tree. The guard belongs in recovery validation as well as capture; checking only the branch name or equality with the base SHA cannot prove retention of work.

2. **High — Fail-open preservation admits unbounded loss, contradicting the advertised one-visit limit.**

   **Claim.** A server crash during one visit is the accepted loss. Continuing through arbitrarily many unsuccessful preservation pushes accepts a different, larger loss, which the current text does not acknowledge.

   **Evidence.** `Proposal:28` says a failed push must neither stop the run nor change the visit outcome. `Proposal:110` destroys even if nothing was preserved and adds no new live-sandbox read. Yet `Note:100-104` promises at most the current visit, and `Children:27` describes the same bound. The engine's independent push is disabled (`R/.claude-plugin/.fabro/workflows/implement-work-item/workflow.toml:432-434`). This is not just a hypothetical network problem: the existing needs-human script explicitly handles forge refusal of workflow-file changes and authentication/push failures (`R/.claude-plugin/.fabro/workflows/implement-work-item/workflow.fabro:2071`). Copying its mechanism does not establish that arbitrary work can be pushed successfully.

   Concrete sequence: implement checkpoint I cannot be pushed; fix checkpoint F cannot be pushed; review_fix checkpoint G cannot be pushed; wall-budget removal calls the proposed wrapper, records “no ref,” and removes the sandbox. I, F and G are all lost. The same happens with an outside cancel, crash or operator removal after those failures. Even a temporary failed push followed by a destructive branch rewrite can lose the earlier lineage permanently: retrying only the *current* tip no longer includes it.

   **Recommendation.** Resolve the contract before implementation. The smallest fail-open design must explicitly promise preservation through the last *successful* capture, report the unpreserved interval, and classify preservation outages separately in the seven-day proof. If the maintainer's one-visit bound is strict even during a forge outage, advancing into another work-producing visit must wait or terminate safely when capture fails; both existing MUST-continue and unconditional destruction rules then need changing. Do not certify the strict bound from a successful-push-only canary. Also specify retry eligibility by “tip not yet successfully preserved,” not only “checkpoint moved it.”

3. **High — Neither mechanism as presented covers the contract; two after-visit hooks are the smaller source-supported solution.**

   **Claim.** One `stage_complete` hook misses failures. Command nodes only after agent nodes miss command-stage mutations and introduce routing changes. The source resolves the proposed open question more precisely than “the implementer measures it.”

   **Evidence and timing.** Fabro checkpoints non-cancelled attempt results in `prepare_result`, before recording the result; cancelled attempts skip the checkpoint (`F/lib/components/fabro-petri/src/hooks.rs:1541-1570`). The outer hook delegates `after_record` to Petri (`:1573-1575`). Petri maps that callback to `AfterVisit` (`P/crates/core/execution/src/hooks.rs:443-457`), and maps failures **and cancellations** to `stage_failed`, other non-skipped outcomes to `stage_complete` (`P/crates/attractor/steps/src/hooks/mod.rs:741-770`). The driver awaits `after_record` before route resolution and transition (`P/crates/core/driver/src/run.rs:1644-1695`). Thus the Git commit exists before these hooks execute, while the separate platform checkpoint record is written later in Fabro's transition (`F/lib/components/fabro-petri/src/hooks.rs:1595-1604`). “Checkpoint” must distinguish those two events.

   A failed `publish_draft` routes to `refresh_repair`, whose failure routes to `needs_human` (`R/.claude-plugin/.fabro/workflows/implement-work-item/workflow.fabro:2245,2255-2256`); these failed visits are not `stage_complete` events. Cancellation before a subsequent successful visit leaves their checkpoints uncaptured by a success-only hook. For the single-node graph, the implement agent can be followed by `implement_commit_settle`; preservation only immediately after the agent can precede completion of its detached commit (`e7f5ec757^:.claude-plugin/.fabro/workflows/implement-work-item/workflow.fabro:183-190,2233-2238`). `Note:165-166` also understates routing work: moving an agent's outcome-conditioned edges onto a new successful command does not preserve the agent's outcome or preferred label automatically.

   **Recommendation.** Use two nonblocking hook declarations, `stage_complete` and `stage_failed`, invoking one trusted, bounded, idempotent helper for all relevant workflow nodes, including command nodes. This needs no Fabro change in the inspected lineage, creates no extra checkpoint-producing graph nodes, and leaves routing intact. Do not substitute `checkpoint_saved`: the pinned Petri hook service explicitly calls it unsupported (`P/crates/attractor/steps/src/hooks/mod.rs:451-465`). A command-node solution remains possible if credential integration requires it, but it must cover every mutation boundary and preserve original routing data; “after each agent” is insufficient.

   There is also a concrete observability requirement: merely echoing a push error to stderr is insufficient for the hook receipt. The command-hook executor retains stdout for decision parsing and discards stderr in this path (`P/crates/attractor/steps/src/hooks/executors.rs:274-299`). Use the supported structured reason that reaches the hook report, with nonblocking behavior explicitly set; report construction retains that reason (`P/crates/attractor/steps/src/hooks/mod.rs:534-563`). Verify that the event record actually contains the ref and failed step. Cancellation/crash during the callback still needs the loss accounting in finding 2.

4. **High — The credential amendment grants permission but does not supply a credential path compatible with withdrawal.**

   **Claim.** “Same mechanism as needs_human” is not a sufficient integration design. Present helpers depend on the run-wide minting inputs that withdrawal is intended to remove. A script outside the working tree is not, merely by location, an inaccessible or immutable credential boundary.

   **Evidence.** `Note:71-74` and `Children:27-29` rely on that mechanism. The current refreshing wrapper projects App inputs into the sandbox environment (`C/_dispatcher_gh_refresh.py:334-341`); `push_origin` mints a token, exports it as `LIVESPEC_PUSH_TOKEN`, and executes the supplied command (`C/_dispatcher_git_push.py:74-81`). The generic git helper invokes `gh auth git-credential` (`C/_dispatcher_git_credential_helper.py:69-74`). The engine's private publisher has its own token resolver (`F/lib/apps/fabro-cli/src/commands/run/publish.rs:287-296`), but the ordinary run-hook command path supplies hook context variables and spawns through the sandbox environment; it does not call that resolver (`P/crates/attractor/steps/src/hooks/executors.rs:184-213,244-252`). The engine's source credential is an HTTP-header environment value (`F/lib/components/fabro-petri/src/source.rs:68-82`), not an already exposed restricted preservation service.

   The governing confinement clause prohibits agent-held tokens or minting keys and requires trusted tooling plus credential isolation (`R/SPECIFICATION/contracts.md:3457`). Read-only `bd show` and `bd comments` checks confirmed that **Withdraw every publication-capable credential from agent stages** (bd-ib-w64kr3) expressly removes run-wide token/App projection, including integration re-projection; **Scope publication credentials to command publication steps** (bd-ib-sgnfom) retains the needs-human exception. Their requirements match that cited clause. Neither inspected item description names an authenticated run-hook preservation entry point. The proposal's replacement wording still calls the exception a “command step,” while its preservation paragraph permits a run hook (`Proposal:28,32-33`).

   **Recommendation.** Make the preservation helper an explicit consumer of the same trusted credential boundary those items build, and amend their scope consistently. Authorize both named preservation *operations*, including their hook invocation, from trusted workflow context; never authorize by an agent-settable environment flag. Specify who can invoke the helper, which immutable run/repository/ref identity it uses, and how agents cannot read its secrets or replace its program. Disable repository hooks **and** neutralize repository-controlled Git command/helper/remote configuration while a credential is present. Prove capture after withdrawal, refusal from an agent, and inability to redirect the push to another run. Compatibility of that future boundary with either mechanism is **UNVERIFIED**; today's ambient-credential success would not prove it. This is a required dependency, not a reason to revive an outbox service or change Fabro.

5. **High — Committer time is not an ordering protocol, and the reference script is not a safe implementation of the proposed ref algorithm.**

   **Claim.** The proposal cannot deterministically identify the latest preserved visit across rewrites using commit time. The “never force” rule is sensible, but its claimed interim reference violates it.

   **Evidence.** `Proposal:28` defines newest by latest committer time; `Proposal:167` makes that choice exclusive. The checkpoint command uses ordinary `git commit --allow-empty` without a monotonic capture ordinal (`F/lib/components/fabro-petri/src/checkpoint.rs:522-535`). Two divergent checkpoints can share the same timestamp, and the design supplies no tie rule. A clock moving backward also makes a later capture rank earlier. These are counterexamples permitted by the design, not observed clock incidents. Ancestry cannot order divergent siblings.

   The cited interim script, `/tmp/claude-1000/-data-projects-livespec-orchestrator-beads-fabro/c23be22c-a604-40c4-bd9c-3107b5db4a76/scratchpad/preserve_runs.sh`, reads the run branch at lines 45-48 and checks ancestry only against the unsuffixed ref at lines 54-59. Its actual push uses `"+$sha:$ref"` at line 62: it **is forced**. It neither searches all siblings nor applies the same check to an existing sibling. Its fallback to HEAD when the run branch is absent also differs from “never workspace HEAD” (lines 44-48). `Note:123` therefore overstates what this reference establishes.

   **Recommendation.** Record capture order in durable, run-scoped metadata, not commit timestamps, with an explicit tie/retry rule. If retaining fast-forward-plus-siblings, resolve the case where several refs are ancestors, fetch missing ancestry rather than treating a failed query as “not descendant,” and define SHA-prefix collision/reuse behavior. The simpler alternative is one immutable, ordered ref per captured tip: one normal push, no mutable ancestry search, and the same closure cleanup. Keep the reference script as incident evidence, not code to copy unmodified. Remote ref presence proves publication of a named SHA; it does not prove the recovery choice identified in finding 1.

7. **Medium — The destruction wrapper's scope misses an existing abandonment route and leaves unattributed runs and duplicate receipts underspecified.**

   **Claim.** A single wrapper is useful, but the proposed check's enumerated operation types do not cover every existing way this Dispatcher ends a run. Its receipt requirements also assume an item and an observable last visit that may not exist.

   **Evidence.** `Proposal:110` enumerates cancel/delete/run-sandbox deletion. Orphan termination first answers an abandonment question and returns immediately on success, before either cancel or rm (`C/_dispatcher_reconcile_runs_terminate.py:120-148`). A matcher confined to cancel/delete calls can miss that path. The existing `fabro_port_seam` is a transport-confinement check, not a preservation-policy check, and deliberately exempts the facade family (`R/dev-tooling/checks/fabro_port_seam.py:19-45,128-131`). `Children:100` also explicitly identifies probe removals without their own work item, whereas Scenario 315's orphan example requires “its item” to carry a comment (`Proposal:131-135`). Finally, `Proposal:110` deduplicates a comment “written after the run's last node visit,” yet external removal can make the latest run record unavailable; `Proposal:28` still requires comparison with the tip the run last reported.

   **Recommendation.** Give the wrapper a small explicit context: repository/run/factory, optional item, destruction operation, observed preservation refs, and known/unknown final tip. Include abandonment answers in policy coverage and test direct facade calls as well as transport bypasses. When no item is attributable, use a journal receipt; never invent an item or infer “no work” from lack of attribution. Deduplicate by the observed ref/SHA set and outcome, so a later ref advance warrants a new receipt and an unreadable final tip is explicitly unknown. Preserve existing terminal-publish obligations as named exceptions: they still require live reads (`R/SPECIFICATION/contracts.md:6302,6304`), so “no new read” must not be implemented as “no reads at all.” Keep this as one small receipt-and-destroy policy, not another export service.

9. **Medium — Retention needs an eligibility boundary and eventual semantics; the current assertions conflict.**

   **Claim.** The closure rule is the right simple retention policy, but “when read, no refs exist” cannot hold simultaneously with failed deletion retries and an exemption for previously closed items. “Before this rule took effect” is not an implementable fleet boundary until recorded somewhere.

   **Evidence.** **Delete preservation refs when an item closes** (bd-ib-efiasj) requires no matching refs whenever a closed item is read (`Children:140-141`), then permits failed deletion and requires old closed items to retain refs (`Children:143-144`). The normative paragraph repeats the exemption without specifying the effective timestamp or eligibility record (`Proposal:220`). It also permits cleanup on the Dispatcher's own close/accept path, while preservation fires on later workflow node completions (`Proposal:28`). Deleting once at closure can therefore race a final publisher and leave a recreated ref; repeated cleanup needs an actual enumeration path, not an assumption that the item happens to be read again. The current ended-run collector explicitly restricts collection to ended runs belonging to closed items (`C/_dispatcher_ended_run_collection.py:36-55,71-72`), a useful existing place to coordinate cleanup.

   **Recommendation.** Record one durable eligibility boundary for the new rule, preserve the explicitly grandfathered population, and say “attempt deletion, eventually absent after a successful pass once the run cannot publish again.” Test failed deletion/retry and a late preservation push after closure. Qualify the first two child assertions by eligibility and successful cleanup; add an explicit test that grandfathered refs survive. Continue using item closure rather than an age policy, and do not silently include the historical backlog. This is a small extension of cleanup, not a new retention service.

The smallest coherent implementation keeps the four responsibilities—capture, receipt before destruction, recovery selection, and closure cleanup—but shares their ref discovery/identity code. Prefer the two awaited hooks and one trusted publisher; avoid new graph nodes after every agent, a live-sandbox exporter on every teardown, an outbox service, and timestamp-based ordering. Immutable ordered capture refs are a simpler alternative to the mutable-ref/sibling search if ref count is acceptable under the already-required closure cleanup. The ancestry/rollback guard, credential isolation, and recovery test are necessary correctness work, not optional complexity. This recommendation implements the chosen direction; it does not silently grant a stronger outage-loss guarantee than the maintainer selected (`Note:8-15,51-98`; `Proposal:28,110,167,220`).

Overall verdict: **revise before implementation**. Preserve-on-progress is viable without a Fabro change, and the pinned source supports a compact two-hook mechanism. The present draft can still recover the wrong tree, exceed its claimed loss bound, and be implemented against incompatible acceptance criteria. Fix those contracts and prove the restricted credential path and single-node recovery before calling the design ready.
