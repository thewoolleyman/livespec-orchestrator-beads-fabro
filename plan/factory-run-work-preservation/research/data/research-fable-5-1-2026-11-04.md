# Research: preserving a factory run's work (Fable 5.1, 2026-11-04)

Read-only research for plan `factory-run-work-preservation`. Local citations are `path:line`. The deployed engine is the Fabro carrier worktree `~/.worktrees/fabro/carrier-petri-v0.382` (adeefec4c), which embeds Petri; `/data/projects/fabro` master (3b37818) predates the Petri integration and is cited for docs only. Web claims cite URLs; "UNVERIFIED" marks what I could not confirm from a primary source in the time box.

## 1. What Fabro and Petri provide

**Per-attempt checkpoint commit, sandbox-local.** After every node attempt the Fabro host hook `prepare_result` commits the tree on `fabro/run/<id>`, with `--no-verify` when `skip_git_hooks` is set (carrier `lib/components/fabro-petri/src/hooks.rs:13-19`, `:647-735`; `fabro-workflow/src/sandbox_git.rs:117`). "A stage that failed on its own terms is committed like a successful one; only a cancelled attempt is not" (`hooks.rs:16-17`). A failed commit is fatal and cancels the run (`hooks.rs:578`).

**Run-branch push.** Upstream: "When pushing is configured, Fabro pushes `fabro/run/{run_id}` after each checkpoint and again before successful completion" (`docs/public/execution/checkpoints.mdx` §Run workspaces). The push follows the commit, from the workspace that owns the run branch, warns on failure and retries at the next checkpoint (`hooks.rs:706-716`). The credential is the **server's** GitHub App token, resolved by `GitHubPublisher::push` and handed to `git` inside the sandbox as an HTTP-header env for one repo (`lib/apps/fabro-cli/src/commands/run/publish.rs:287-345`). Upstream defaults to pushing for GitHub targets; this factory sets `run_branch.push=false` and `meta_branch.push=false` (`workflow.toml:432-438`). Upstream has dropped meta branches ("Fabro no longer creates or pushes `fabro/meta/{run_id}`", checkpoints.mdx §Metadata branch), so `meta_branch.push` is dead config.

**`finalize_run`.** Every Fabro run requires finalization (`hooks.rs:1636-1641`). It records the cumulative base→head `run.diff` platform record with the patch as a blob, then for `RunStatus::Success` only pushes and opens the PR (`hooks.rs:1643-1700`). Petri awaits it "after terminal workflow execution, while its environments remain available… Failed and cancelled execution also invoke the finalizer" (`petri/crates/core/execution/HOOKS.md:264-268`; `driver/src/lifecycle.rs:549-552`). Two limits: (a) `run.diff` lives in the run store, which `rm -f` deletes; (b) "restart exits do not finalize" means a Petri **loop_restart successor** (`lifecycle.rs:373-377`), not a server restart. A server restart or crash kills the worker, so no driver exists to await anything; the resumed driver re-runs `run_finished`/`scope_released` but "holds no environment… a hook placed in the sandbox reports that it cannot run" (HOOKS.md, "Run notes are recorded at least once").

**Run hooks.** `[[run.hooks]]` events include `stage_complete`, `stage_failed`, `run_complete`, `run_failed`, `sandbox_cleanup`, `checkpoint_saved`; command hooks run in the sandbox by default or on the host with `sandbox=false`; HTTP hooks always fire from the host (`docs/public/agents/hooks.mdx:82-103, 247-255`). Under Petri, `run_complete`/`run_failed` fire by final status, "neither for a cancelled run"; `sandbox_cleanup` fires at scope release "with the sandbox still there" (`petri/crates/attractor/FORMAT.md:531-535, 654-656`); `checkpoint_saved` "warns at load and never runs" (FORMAT.md:656-657). Hooks are observational and fail-open (HOOKS.md:262): a hook cannot refuse a teardown.

**Sandbox retention.** "The workspace survives success, failure and cancellation under `--retain always` (the Fabro default)" (`petri/crates/fabro/HANDOFF.md:125-126`). Environments carry `lifecycle.preserve`, `stop_on_terminal`, `auto_stop` (`docs/public/execution/environments.mdx:125-148`). On the k8s driver the workspace is a node-local `hostPath` directory; `stop` deletes the pod and keeps the directory, `delete` empties it through a cleanup pod; snapshots are refused (`sandbox-driver-kubernetes/README.md` "Workspace", "Lifecycle fence", "Refused"; `src/sandbox.rs:349-363`). That is why one tree could be copied off a node by hand.

**Deletion.** `fabro runs rm` is one server call (`fabro-cli/src/commands/runs/rm.rs`); `delete_run_internal` cancels a live worker, waits a grace, then deletes sandbox resource and records (`fabro-server/src/server.rs:2757-2900`). Nothing exports first.

**Read-out after the fact.** `GET /api/v1/runs/{id}/files` materializes from the live sandbox and, when it is gone, degrades to the stored final patch (`fabro-server/src/run_files.rs:251, 518-541, 819-870`); `fabro dump` exports events, checkpoints and diffs from the store (`docs/public/reference/run-directory.mdx:33-46`). Both die with `rm -f`.

**Upstream's recommendation** is: push the run branch after every checkpoint, keep the run store, fork/rewind from the published branch ("requires run-branch pushes to be enabled", checkpoints.mdx). It keeps "no second checkout, bare snapshot repository, or Git checkpoint bundle on the server for a remote sandbox". Upstream's answer to this plan is `run_branch.push = true`.

| Mechanism | Covers | Cost | Gap left |
|---|---|---|---|
| `run_branch.push=true` | every checkpointed attempt, whatever ends the run later | ~1 push per attempt (10-25/run), one `fabro/run/<id>` ref per run | cancelled attempt's uncommitted tail; the server token enters a `git` env inside the sandbox, which the ratified clause forbids ("never through an environment variable", `SPECIFICATION/contracts.md:3457`); no upstream GC of `fabro/run/*` |
| `finalize_run` | failed and cancelled runs on a live driver | none | store-only; deleted by `rm -f`; nothing on worker death |
| `sandbox_cleanup` hook | scope release on a live driver | one hook run | fail-open; not on `rm -f` of a dead worker; needs a credential to push |
| retain/`preserve` | everything while the sandbox exists | disk, k8s nodes fill | not durable; k8s copy-out broken; `rm -f` still deletes |
| `/files` + Git Data API (Scenario 183) | any run whose records and sandbox survive | 1 forge write per file + 3 | store deleted by `rm -f`; degraded answer is the final patch only |

## 2. Other factories and coding-agent platforms

Common shape: the agent works on its own branch in an ephemeral VM, **pushes commits as it goes**, and the platform treats "already pushed" as the durability line; anything uncommitted dies with the VM. Sandbox snapshots are for environment reuse, not work recovery.

- **GitHub Copilot coding agent.** "Stopping a session ends the GitHub Actions run and preserves any commits already pushed"; "The session, its files, and its in-progress work live in GitHub-hosted infrastructure" ([docs](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)). Copilot works on a branch and draft PR it owns. Timeout length and the fate of unpushed work: UNVERIFIED (only a third-party exam page cites 70 min).
- **OpenAI Codex cloud.** "Codex creates a container and checks out your repo at the selected branch or commit SHA… Codex caches container state for up to 12 hours"; on finish "it shows its answer and a diff of any files it changed", then you open a PR ([docs](https://learn.chatgpt.com/docs/environments/cloud-environment.md)). The diff is held platform-side; cancel/crash handling of a partial diff: UNVERIFIED.
- **Devin.** Machine snapshots are "save states" taken only when idle or after a session ends and terminate the session ([search result summary of docs.devin.ai/onboard-devin/snapshots](https://docs.devin.ai/onboard-devin/snapshots); page returned 404 to direct fetch, UNVERIFIED). A third-party guide says uncommitted work disappears at session end ([fast.io](https://fast.io/resources/devin-ai-file-management/)).
- **Cursor cloud agents.** Agents "run in isolated VMs… work on a separate branch, then push changes to your repo for handoff"; snapshots "save your base environment configuration", not work ([docs](https://cursor.com/docs/cloud-agent)). Stop/fail behaviour: not documented.
- **Google Jules.** "Jules runs in a virtual machine where it clones your code, installs dependencies, and modifies files" ([docs](https://jules.google/docs)); branch and PR as the output per third-party write-ups; stop behaviour UNVERIFIED.
- **OpenHands.** The one platform with an explicit preservation layer: standard sandboxes sit on a PVC that survives pause/resume, and "OpenHands can automatically archive workspace contents before pausing/stopping" to S3 with a manifest, archive first then release storage; fuse workspaces "purged… > 30 days" ([archive-sandbox](https://docs.openhands.dev/cookbook/archive-sandbox.md)). An automation PR proposes a 2-hour sandbox retention after runs ([PR, unmerged, UNVERIFIED](https://gh.r-mj.com/OpenHands/automation/pull/33)).
- **StrongDM attractor (Fabro's lineage).** Ports checkpoint the pipeline state (`.attractor/checkpoint.json` on exit) and one Go port "runs attractor pipelines in isolated git worktrees" ([streamweave-attractor](https://docs.rs/crate/streamweave-attractor/0.2.0); [Willison](https://simonwillison.net/2026/feb/7/software-factory/)). No push-on-progress found; the upstream spec was not fetched (UNVERIFIED).
- Factory.ai, Sweep, Amp, Sourcegraph: not reached in the time box.

Pattern tally: continuous push to an agent-owned branch (Copilot, Cursor, Jules); platform-held diff plus cached container (Codex); workspace archive to object storage before teardown with a TTL (OpenHands); environment snapshots everywhere, never as work recovery. No platform I found uses a durable-execution engine for the git tree itself; the tree's durability is always a push or an archive.

## 3. Durable-execution and CI practice that applies

- **Progress before acknowledge.** Temporal: "Each State Transition is recorded in a persistence store… If a failure occurs, the Workflow Execution picks up where the last recorded event occurred" ([docs](https://docs.temporal.io/workflow-execution)). Petri already does this for *control* state (event log, resume, `scope_acquired` restore, `LostSandbox::Replace`); the missing half is a durable store for the *tree*.
- **Transactional outbox.** Write the message in the same transaction as the state, let a separate relay publish it; "Messages are guaranteed to be sent if and only if the database transaction commits", delivered at-least-once ([microservices.io](https://microservices.io/patterns/data/transactional-outbox.html)). Translation: the sandbox's commit is the transaction; a relay outside the sandbox does the forge write.
- **Finalizers.** A Kubernetes finalizer means "the deletion will not be complete until the finalizer is removed", and the owning controller runs idempotent cleanup first ([k8s blog](https://www.kubernetes.io/blog/2021/05/14/using-finalizers-to-control-deletion/)). The factory's equivalent is a `Removing` state that cannot be entered until an export record exists.
- **preStop is not a durability tool.** The hook "must complete its execution before the TERM signal can be sent", but "the container will eventually terminate within the Pod's termination grace period", and a hook "fails if the container is already in a terminated or completed state"; delivery is at-least-once ([k8s docs](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/)). Same lesson as `sandbox_cleanup`: last-moment hooks bound the loss, they do not prevent it.
- **CI artifact retention.** GitHub Actions `retention-days` is per-upload and capped by repo/org policy ([docs](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/storing-and-sharing-data-from-a-workflow)); the 90-day default is UNVERIFIED from the pages fetched. The transferable rule: every artifact carries its TTL at creation, so nothing needs a later GC decision.
- **Git mechanics.** Git Data API blobs accept utf-8 or base64 content; the read endpoint "supports blobs up to 100 megabytes" ([docs](https://docs.github.com/en/rest/git/blobs)). A commit stays reachable while any ref (branch or otherwise) points at it; non-branch namespaces (`refs/livespec/...`) stay out of the PR UI and are what the factory already uses.

## 4. Candidate designs

Endings to cover: E1 wall budget, E2 stall watchdog, E3 stale reap, E4 orphan reconcile, E5 engine terminal failure, E6 external/operator cancel, E7 server restart or crash, E8 operator `fabro rm`, E9 docker/k8s sandbox reclaim.

**A. One Dispatcher chokepoint.** `FabroPort.rm`, `FabroHttpPort.cancel`, abandon and `docker rm` all route through one `preserve_then(...)` that reads `/runs/{id}/files` and writes a `refs/livespec/preserved-publish/<item>/<sha>` commit through the Git Data API before any destructive call; a static check forbids direct calls. Covers E1-E5, E9; misses E6-E8. Writer: Dispatcher host. Credential: Dispatcher's GitHub App via REST. Cost: one export per ending (one blob write per changed file + 3 calls), one ref per ending. Retention: implied by item state (drop when item accepted or after 30 days); today's 197 refs show the rule is missing. In-flight fixes: adcaa6, vraou4, ds4yrm each collapse into "call the chokepoint"; vraou4 (external cancel) is still only partially met because the Dispatcher learns of the cancel after the fact and `/files` may already be degraded.

**B. Engine push on progress (`run_branch.push=true`).** Zero code; the engine pushes `fabro/run/<id>` after every checkpoint. Covers every ending for work committed by the last finished attempt, E6-E8 included. Misses the cancelled attempt's uncommitted tail (`hooks.rs:16-17`) and the tree a wall-budget cancel interrupts mid-agent. Writer: `git` inside the sandbox, token from the server. Credential path **conflicts with the ratified clause** (`contracts.md:3457`: no credential in the sandbox env; header env is an env var and same-uid `/proc` reads are possible). Cost: 10-25 pushes/run, one ref per run, no GC upstream. In-flight fixes: adcaa6 and vraou4 become unnecessary for committed work; ds4yrm still needs a tail export.

**C. Workflow-graph push at command stages.** Each command stage that already holds the credential (janitor-green hand-off, `publish_draft`, `pr_refresh`, `needs_human`) pushes `refs/livespec/wip/<item>/<run>` with `push_origin`. Confinement-compliant by construction; covers E1-E9 for work up to the last command stage; misses everything an agent stage did since (the incident's fix laps sat exactly there). Cost: 3-6 pushes/run, one force-updated ref per run (rebases make it non-fast-forward). Fixes: adcaa6 is this design for one stage; the other two unchanged.

**D. Fabro-server hook (`stage_complete`, `sandbox=false`).** A host-side command hook on the factory server reads the checkpoint from the sandbox and pushes it with the server's App token to `refs/livespec/wip/...`. Same coverage as B minus the cancel path (no hook fires on cancel) and minus E7. Keeps the credential on the server host, but on k8s the server has no direct git access to the pod's hostPath, so it would ride the broken `/files`-style read. Cost as B. Fixes as B.

**E. Export-before-delete inside the engine, plus k8s workspace retention.** Patch the fork so `delete_run_internal` and cancel run a required export (push run branch or write `run.diff` to the artifact store **outside** the run's records) before `Removing`; make the k8s `stop` (keeps hostPath) the default on `rm` until an export record exists, `delete` only after. Covers E1-E6, E8, E9; misses E7 only when the crash kills the worker mid-attempt. Writer: fabro-server. Credential: server App token. Cost: fork hand-build and maintenance (`.ai/fabro-fork-hand-build.md`), one export per run. Fixes: all three become server guarantees.

**F. Outbox mirror (my pick, with A as the tail gate).** Enable the engine's per-checkpoint push, but point it at a credential-free bare mirror on the factory host (plain git over the sandbox network, write-only, reachable only from sandboxes), not at GitHub. A host-side relay (systemd timer or Dispatcher poll) pushes mirror refs to origin as `refs/livespec/wip/<item>/<run>` with the Dispatcher's App token and marks each as relayed. This is the transactional outbox: the sandbox's commit plus local push is the transaction, the relay the publisher, at-least-once and idempotent because git pushes are. Covers E1-E9 for committed work, including server restart and operator `rm` (the mirror is a separate process and disk). Misses the uncommitted tail at cancel, which A covers for the Dispatcher-issued endings, and E6-E8 tails remain the residual loss (bounded to one attempt). Writer: engine for the local hop, host relay for the forge hop. Credential path: none in the sandbox; App token only in the relay. Cost: one local push per attempt (cheap), relay pushes batched to one per run per few minutes, one `wip` ref per run plus one `preserved-publish` ref per Dispatcher ending. Retention: `wip/<item>/*` and `preserved-publish/<item>/*` deleted when the item is accepted or closed; everything else after 30 days; the 420 `needs-human/*` refs join the same GC. Effect on the in-flight fixes: ds4yrm (wall budget) becomes "export the tail through A, then rm"; vraou4 (external cancel) needs no cancel-time code, only the relay; adcaa6 (cancel-for-restart) reduces to a relay flush before the restart. Fabro's push machinery already exists; the fork change is small (push URL and credential selection per environment), and the engine's own `run_branch.push` upstream default is honoured rather than fought.

**Why F+A over B.** B is one config line but spends the confinement clause the maintainer ratified three weeks ago, and it leaves `fabro/run/*` growing with no owner. F keeps the sandbox credential-free, survives the server, and makes the Dispatcher chokepoint a bounded-tail fix instead of the whole safety net. If the maintainer would rather amend the clause to allow a between-attempt `git` push with a transient header env, B plus A is the 48-hour version of the same shape and I would take it as the interim.
