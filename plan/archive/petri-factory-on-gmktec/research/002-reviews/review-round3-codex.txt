    # Independent review, round 3 — Docker on gmktec-xubuntu

    Reviewed 2026-10-15 against revision 3. **BLOCKERS remain. Do not converge this revision on gmktec as
written.**

    This is a design review, not implementation acceptance. The only write was this explicitly requested,
gitignored report. No host, service, package, firewall, ledger or tracked repository content was changed. No
installation, simulation, container launch, active application probe or fault injection was performed. Remote
commands used only the brief's allowed reads. References to `design.md` mean this directory's revision 3;
`ansible/` and `ci-runner/` paths are relative to `/data/projects/livespec-dev-tooling/`. Earlier reviewers'

    ## Ranked findings

    ### BLOCKER 1 — Confirmation still has two durable authorities, and rollback revokes only one of the two
start permissions

    Evidence: `design.md:54–55,94–99,116–122,129–154,250–254`.

    Atomic replacement protects `state.json`, but the systemd condition does not read that file. Confirmation
separately writes the global `confirmed` file, removes `allow-start`, enables units, and finally publishes state
`confirmed`. Consider a crash immediately after the global file is written, or an enablement failure after it is
written. State is still nonterminal, yet Docker has durable permission to start. The specified rollback removes
only `allow-start`: the OR condition remains satisfied by `confirmed`. The assertion that no new start is
possible is false in this case. A reboot in this gap also defeats the claim that an unfinished run cannot start
Docker if the boot actor fails. The later-run classifier trusts the global file rather than requiring completed
actor finalization.

    Passing probes before this gap does not itself make accepting the run wrong. The missing piece is a defined
commit point and recovery semantics: either durable confirmation is irrevocable and every subsequent failure
resumes only confirmation finalization, or a rollback must durably revoke every start permission before killing
anything. Specify consistency checks for the run identity, configuration digest, decision and marker; define
missing/corrupt state behavior. Test kills between every operation inside confirmation, including marker
publication and enablement failure, not merely between named phases. One writer does not make two files plus
systemd operations atomic.

    ### BLOCKER 2 — “One actor” is an assertion, not an enforced host-wide ownership rule

    Evidence: `design.md:78–90,124–127,150–154,248–257`.

    A template instantiated with a run ID permits multiple distinct services. The resume row explicitly says to
start a **new** actor run whenever installed packages lack confirmation; it does not exclude a still-running
actor, an incomplete rollback or the boot actor. After a controller dies, a normal rerun can therefore start B
while A is observing or rolling back. Their shared `allow-start`, global `confirmed`, Docker units and firewall
are not per-run resources. B can recreate permission or start Docker while A cleans it up. Atomic per-run state
files cannot serialize this.

    Make one host-wide owner mechanically exclusive across normal start, rerun and boot recovery. A rerun must
attach to or recover the existing run, not allocate a second transition until recovery is terminal and verified.
Define precedence between `rollback-partial` and the broader installed/unconfirmed row. Include concurrent
controller starts, controller retry during rollback, and boot/retry overlap in acceptance.

    There are related restart holes. The design persists completed rollback phases but does not define how their
predicates are revalidated after reboot: firewall state and cgroups do not survive a boot like disk state does.
Nor does it specify persistent absolute deadlines/boot identity, so an implementation could reset N on each
restart. Specify that recovery cannot restart the safety window indefinitely, and that recovered phase
completion is accepted only if its postcondition still holds. If the boot actor resumes a forward-start phase,
its `Before=` relationship to the Docker units also needs an explicit service type/job graph: a oneshot that
synchronously waits for a unit ordered after its own completion deadlocks. Prefer an explicit boot recovery
policy rather than an ambiguous copy of every forward phase.

    ### BLOCKER 3 — The replacement for the dead-man timer cannot currently detect its own loss of progress

    Evidence: `design.md:79–80,103–105,148–162,299–309`; local `/usr/share/man/man5/systemd.service.5.gz`
(`Restart=`, `WatchdogSec=`, `TimeoutStartSec=`) and `/usr/share/man/man5/systemd.unit.5.gz`
(`StartLimitIntervalSec=`, `StartLimitBurst=`). Cross-checked the [upstream service manual source](https://
raw.githubusercontent.com/systemd/systemd/main/man/systemd.service.xml).

    `Restart=on-failure` handles certain exits, not a live but stuck actor. With `TimeoutStartSec=infinity` and
no independent progress supervision, a deadlock, SIGSTOP or blocking operation outside a correctly bounded
subprocess leaves `allow-start` present indefinitely. In-process deadline checks are ineffective when their
process cannot reach them. Repeated failing restarts can also exhaust systemd's start limit and leave the actor
failed while Docker remains permitted. For non-oneshot services, default handling of SIGTERM/SIGHUP/SIGPIPE
counts as clean termination and does not trigger on-failure restart; the service type and signal policy are
unspecified.

    Keep one decision-maker, but provide independent liveness supervision capable of replacing a stalled owner
with recovery, without creating two concurrent decision-makers. Specify restart limits/backoff, signal behavior,
stop/shutdown behavior, and bounded calls in **all** phases including persistence and probes. Acceptance needs a
hung actor, repeated crash/start-limit exhaustion, signals other than SIGKILL, and failure before the actor's
first durable state publication. An actor that never successfully starts should leave permissions absent; prove
that invariant as well.

    The explicit rollback budgets and early FORWARD restoration improve the earlier global-timeout problem. They
do not establish that those budgets will be enforced when the sole enforcer stops making progress. The old
`systemd-run` arming failure no longer applies, because revision 3 uses installed services; the equivalent
start/arming failure still needs the above invariant.

    ### BLOCKER 4 — Timer stopping plus a lock-free observation is still not a package-transaction fence

    Evidence: `design.md:220–242`; fresh gmktec `systemctl is-active k3s-agent tailscaled local-homelab-llama-
server unattended-upgrades apt-daily.timer apt-daily-upgrade.timer` returned six `active` lines. Fresh hp reads
of `/var/lib/dpkg/info/docker.io.postinst` and `/var/lib/dpkg/info/containerd.postinst` still show unit enable/
start actions, and Docker's script includes AppArmor loading.

    Downloading an exact audited set is a substantial improvement: `dpkg -i` makes no new apt resolver choice.
But stopping two timers and observing no package process/free lock does not reserve that state through
simulation, download, audit and install. An independently launched apt/packagekit operation can begin afterward.
There is no specified lock ownership and revalidation boundary that makes the observed state the state mutated.
An existing pending configuration/trigger queue is also not explicitly refused. `dpkg --configure -a` on
recovery broadens execution to **every** pending package, not just this role's audited set. Three start
conditions do not inhibit unrelated package scripts or trigger handlers.

    Specify an implementable package-lock protocol using the actual locking semantics, with validation under
ownership and refusal/revalidation after contention. Audit the complete effects of the actual dpkg operation,
including relevant triggers and dpkg hooks/configuration, not just apt hook files (the direct dpkg path does not
execute apt's hooks). Recover only the recorded package transaction or explicitly refuse unrelated pending work.
The promised digests/allowlist must exist and be reviewed before application.

    An Ansible `always` block is not crash recovery: if the controller is killed or loses the host, the timers
can stay stopped for the rest of the boot. Persist their prior state and give restoration a host-local recovery
owner and a deadline independent of the controller. Do not unconditionally start timers that were previously
inactive.

    ### SHOULD-FIX 5 — The proposed condition-verification command does not verify those conditions

    Evidence: `design.md:49–74`; local `/usr/share/man/man5/org.freedesktop.systemd1.5.gz` declares the unit's
`Conditions` array. A local read `systemctl show -p Conditions -p ConditionPathExists dbus.service` returned
only `Conditions=[unprintable]`, with no `ConditionPathExists` property. This is a control-host observation, not
a gmktec experiment. See also the [upstream D-Bus manual source](https://raw.githubusercontent.com/systemd/
systemd/main/man/org.freedesktop.systemd1.xml).

    `ConditionPathExists` is unit-file syntax; requesting a same-named show property is not proof systemd loaded
it. Before package installation the main unit files are absent as well, so specify how an effective loaded unit
is verified at that stage rather than assuming drop-in directories alone constitute the packaged units. Inspect
the real loaded `Conditions`, load state and drop-in paths at the appropriate point, and prove in the disposable
VM that postinst and socket/boot starts are inhibited throughout installation. Exit status or empty output must
not count as success.

    The OR syntax is appropriate for these two intended permissions. Conditions are start-time checks, not a
continuously enforced lease: removing a file does not stop an already active service or cancel an already
accepted start. Track outstanding start jobs and quiesce them during rollback, then verify absence of processes
and jobs before firewall/interface cleanup. A bounded wait for the `systemctl` client is not by itself
cancellation of the manager's job. hp's freshly read Docker unit has `TimeoutSec=0`, `Restart=always`,
`Requires=docker.socket`, and `KillMode=process`, making that distinction relevant.

    ### SHOULD-FIX 6 — The probe recipe assumes privileges the specified credential does not have

    Evidence: `design.md:170–184,192–201`; `ci-runner/k3s/phase2/node-status-credential/node-status-patch-
rbac.yaml:109–118` grants only `get` and `patch` on `nodes/status`, restricted to one node. It grants neither
endpoints nor ordinary nodes/pods reads.

    Read Ready and allocatable via the authorized named node **status subresource**; an ordinary `kubectl get
node` is not the same permission. The proposed DNS-endpoint lookup with this credential cannot work under the
committed grant. The fallback cross-node pod TCP test can be valid, but it needs an explicit known endpoint,
port, identity and ownership/discovery source rather than silently assuming another forbidden API read. An
endpoint list containing a remote DNS pod would also not prove which backend answered a ClusterIP request when
local and remote backends coexist. Ensure all possible selected backends are remote or instrument the actual
path.

    The effective-resync timing requirement is better than an arbitrary delay, but agent flags alone do not
establish hardcoded/version-dependent controller defaults or actual completed resyncs. Record the effective
source for each interval, including kube-router and kube-proxy, and address flannel reconciliation as
applicable. A 420-second sampled window is evidence, not a guarantee of uninterrupted service.

    Controller-side SSH/LLM probes can occur at the **beginning** of that window and their file remains
sufficient at its end. Loss of tailnet reachability after that early success can still yield confirmation if
local probes pass. Require a fresh end-of-window challenge/response tied to run ID and phase, with a bounded age
and no acceptance of an earlier signal after reboot/resume. Host service-active does not replace that
independent path.

    ### SHOULD-FIX 7 — Detecting an out-of-scope consumer is not preventing its unrecoverable mutations

    Evidence: `design.md:106–112,132–141,205–216,250–257,274–295`; fresh hp `/usr/lib/systemd/system/
docker.socket` read shows `/run/docker.sock`, mode `0660`, group `docker`; fresh gmktec `ip route` shows the two
LAN defaults, LAN 192.168.1.0/24 and pod routes 10.42.0.0/24, 10.42.1.0/24, 10.42.2.0/24, with no main-table
172.17 route.

    Empty foreign stores and postponing Fabro are useful controls. But the design does not establish exclusive
access to the newly active Docker/containerd APIs during the window. A same-bridge container evades the
additional-network predicate and can override its cgroup parent; a user-created bridge can modify routes/sysctls
before a 15-second sample detects it, and the specified rollback deletes only docker0. “Canary is the only
container” must be a verified admission condition, not an inference from the factory being stopped. Specify the
allowed clients/workload inventory and how admission stays exclusive through recovery. If unexpected resources
are detected, never claim docker0-only cleanup completely recovered them.

    Also define the predicate precisely: Docker's built-in `host` and `none` networks are not forbidden extra
bridges, and the canary's expected veth is necessarily another Docker-created interface. A literal reading of
“any other Docker network ... or Docker-created interface” rejects normal initialization. Keep exact owned
network/interface identities, namespace-aware cleanup, and a preflight collision check against all relevant
route tables/families. The permitted main-table route read above is not an exhaustive routing audit. No broad
route restoration should be introduced.

    ### SHOULD-FIX 8 — Resume provenance is described but not published at a defined crash-safe boundary

    Evidence: `design.md:85,239–257`.

    Nothing says when or how `installed` is written relative to the first `dpkg -i`. A crash after package
mutation but before the record leaves this role's own packages classified as foreign. A crash after creating the
guard directory/configuration but before packages exist matches neither the pristine row nor the installed row.
`rollback-partial` acknowledgment also does not specify whether repair must complete before a new run starts.
The broad installed/unconfirmed row is insufficient to distinguish these cases from an actor still running
(blocker 2).

    Persist prepared transaction provenance before mutation, then reconcile actual package/configuration state
against it. Specify the pre-install, partially installed, configured/inert, running, rollback-incomplete and
committed states, including durable snapshots and missing records. An acknowledgment is permission to
investigate/repair, not evidence that failed cleanup has become safe. Extend fault injection into installation
and all record-publication boundaries.

    ### SHOULD-FIX 9 — Companion implementation and host-record corrections remain prerequisites, not completed
dispositions

    ### NOTE 10 — The revised firewall cleanup covers the demonstrated raw/NAT and IPv6 omissions within an
exclusive clean-install scope

    Evidence: `design.md:203–216`; fresh hp `sudo -n nft list ruleset` showed raw PREROUTING destination drops
referencing docker0 and the direct 172.17.0.0/16 POSTROUTING masquerade. Fresh `sudo -n ip6tables -S` showed

The nft output warns that these tables are managed by iptables-nft.

    The current token-based predicates select those direct rules and both-family chain references. Flush-all-
before-delete handles inter-chain references; bounded xtables waits, re-reads and residue reporting are
appropriate. Do not revert to older isolation-chain assumptions or whole-table restoration. This resolves the
demonstrated rule-selection defect, not the ownership/admission defects in finding 7 or a tested rollback
implementation.

    After quiescing all writers, verify the **whole** final rollback predicate again, including both FORWARD
policies, processes/jobs and interfaces. An early recorded policy restoration can become stale while the daemon
is still alive. If kill/stop fails, later cleanup is best-effort and must remain partial; retries cannot
establish exclusive ownership while a writer survives.

    ### NOTE 11 — Shared-state and access claims are better scoped, but partial recovery is not a no-lockout
guarantee

    Evidence: `design.md:15–20,142–144,185–190,263–281,299–319`; host AGENTS.md “Access”; `llm-server.md`
“systemd unit” and “Verification evidence.” Fresh gmktec service reads returned active for the three required

recording a shared-state change proves access restoration.

    The proposed real-systemd/dpkg/iptables-nft VM acceptance is valuable and must produce evidence before
convergence. Its stubbed k3s/LLM checks do not test actual kube-router/kube-proxy/flannel coexistence. Retain

representative environment if available. No such acceptance result was supplied or generated in this review.
