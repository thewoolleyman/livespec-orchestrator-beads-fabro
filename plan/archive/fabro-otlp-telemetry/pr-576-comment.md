Treating Fabro’s canonical `RunEvent` stream as the curated OTLP logs surface is cleaner than exporting the intentionally unstable developer `tracing` output, and keeping the initial increment logs-only gives the work a clear boundary while deferring metrics and trace design.

- Map each event’s timestamp, name, severity, redacted properties, bounded envelope attributes, and process resource attributes into the corresponding OTLP fields.

- Keep the application path non-blocking by enqueueing and batching exports away from workflow execution.

- Reuse the existing `RunEvent` redaction logic and add parity tests proving that OTLP receives the same redacted property values as the existing event representations.

- Cap large event bodies, flush buffered records in the correct shutdown order, and ensure collector outages or exporter errors can never fail a run.

To answer the earlier blocking-versus-async question: with OpenTelemetry Rust 0.32, the stable default `BatchLogProcessor` keeps the application path non-blocking while driving the supported blocking HTTP exporter on its dedicated background thread. The async reqwest exporter requires the experimental async-runtime log processor and an additional feature that the sketch does not currently enable. For this first slice, I would use the stable batch processor with `reqwest-blocking-client`; that preserves non-blocking behavior for Fabro without taking a dependency on the experimental processor.

One related dependency detail: in `opentelemetry-otlp` 0.32, the `http-proto` and `http-json` features both enable the SDK’s trace and metrics features. So the first slice can be logs-only behaviorally, but `default-features = false` does not currently produce a strictly logs-only compiled dependency graph while either HTTP encoding is enabled.
