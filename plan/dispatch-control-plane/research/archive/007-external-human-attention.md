# 007 — Human attention and driving an autonomous software factory

[Back to index](https://github.com/thewoolleyman/livespec-orchestrator-beads-fabro/blob/master/plan/dispatch-control-plane/research/README.md)

**Archived — supporting research, 25 October 2026.** Retained as evidence for the current reports. Observations and source checks describe that date, not a fresh assessment of the running system.

Research date: **2026-10-25**. Publication dates below describe the cited work; “observed 2026-10-25” describes an undated, changeable documentation page. Evidence labels distinguish experiments, observational research, practitioner reports, and product documentation. Recommendations are research inferences, not changes to this repository or its operating policy.

## 1. One-paragraph answer

Operate the factory through explicit delegation, a durable queue of exceptions, and a measured human attention budget. Humans should set goals, resolve consequential tradeoffs, and grant bounded authority; agents should prepare evidence and carry authorized work to a verifiable outcome. Contemporary evidence supports this direction: Anthropic reports substantial waiting for human input and output volumes that exceed practical reading capacity ([2026-10-16, observational company study](https://www.anthropic.com/research/employment-at-anthropic)), while its Claude Code team describes reducing review effort through verification, approval requirements based on change risk, and recovery mechanisms ([2026-10-15, practitioner report](https://claude.dev/blog/solving-code-review-at-anthropic/)). Transfer SRE’s distinction between urgent pages and queued work, including grouping and accountable ownership ([2016, Google SRE](https://sre.google/sre-book/monitoring-distributed-systems/)). Give an LLM coordinator bounded responsibility for synthesis, investigation, and recommendations; keep admission rules, resource accounting, permissions, and durable dispositions enforceable outside its conversation. Separate persistent session records from replaceable model contexts and execution hosts, as demonstrated in Anthropic’s managed-agent architecture ([2026-04-08, engineering report](https://www.anthropic.com/engineering/managed-agents)). These sources support selective, well-instrumented oversight; they do not establish a universal number of agents per maintainer or prove that reduced approval counts preserve quality in this factory.

## 2. Findings

### F01. Autonomy should be allocated by function and action scope

**Sources, dates, evidence:** Parasuraman, Sheridan, and Wickens, [A model for types and levels of human interaction with automation](https://dl.acm.org/doi/10.1109/3468.844354), **2000-05-01**, foundational research framework; Google, [Developer’s guide to multi-agent patterns in ADK](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/), **2025-12-16**, vendor design guidance; OpenAI, [Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals), **observed 2026-10-25**, official SDK documentation.

The foundational framework separates information acquisition, analysis, decision selection, and action implementation. A system can automate each to a different extent. Consequently, a coordinator’s ability to diagnose a hold does not imply authority to release it, and authority to schedule work does not imply authority to change a budget. This application is an inference from the framework, rather than a tested factory design. [Parasuraman et al., 2000-05-01](https://dl.acm.org/doi/10.1109/3468.844354).

For this note, **human-in-the-loop** means a required human decision before an action proceeds; **human-on-the-loop** means supervision of already authorized execution with a means to intervene. Google illustrates approval checkpoints for consequential actions. OpenAI documents automatic guardrails separately from approval interruptions, with resumable state that an application can serialize while waiting. Both describe mechanisms; neither establishes which of this fleet’s actions require a maintainer. [Google, 2025-12-16](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/); [OpenAI, observed 2026-10-25](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals).

**Management by exception**, as used here, means delegating a bounded objective and escalating material deviations, exhausted recovery paths, or decisions beyond the delegate’s authority. The exception must identify an accountable resolver; it need not go directly to the maintainer. This is a proposed operating definition combining scoped automation with human review boundaries. [Google SRE, 2016](https://sre.google/sre-book/automation-at-google/); [OpenAI, observed 2026-10-25](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals).

### F02. There is direct, recent evidence of the human attention bottleneck

**Source, date, evidence:** Anthropic, [How employment is changing at Anthropic](https://www.anthropic.com/research/employment-at-anthropic), **2026-10-16**, company telemetry, employee surveys, interviews, and observational comparisons. This is first-party research by a vendor with unusually intensive internal adoption.

Anthropic reports that employee-directed interactive agent runtime reached about six times assumed employee work hours by August 2026. It also estimates that interactive sessions spend around 80% of their wall-clock time waiting for human input. The measures use different denominators: runtime includes inference and active tools, excludes waits longer than 30 minutes, and pools subagents; human hours assume a 40-hour week. The six-to-one ratio is not a sixfold productivity estimate, and session idle time does not establish that every wait required an urgent human response. [Anthropic, 2026-10-16](https://www.anthropic.com/research/employment-at-anthropic).

The estimated time to read even non-technical employees’ agent output exceeds half a work week, using 0.75 words per token and 250 words per minute. That is an estimated reading burden, not observed reading time. Reported responses include request-triage agents, dashboards, standing instructions, and more work on agent-management infrastructure. Tool adoption was not randomized, so the study’s output associations warrant caution. [Anthropic, 2026-10-16](https://www.anthropic.com/research/employment-at-anthropic).

### F03. Experienced users replace some approvals with active intervention

**Source, date, evidence:** Anthropic, [Measuring AI agent autonomy in practice](https://www.anthropic.com/research/measuring-agent-autonomy), **2026-02-18**, observational analysis of millions of interactions, combining Claude Code telemetry and sampled API tool calls.

Full auto-approval rises from roughly 20% of sessions among newer Claude Code users to over 40% among users with extensive experience. Human interruptions also rise, from around 5% of turns at low tenure to around 9% among more experienced users. This supports measuring steering and intervention alongside approvals. It does not show that auto-approval causes better outcomes: experience, task choice, configuration, and user selection may all matter. [Anthropic, 2026-02-18](https://www.anthropic.com/research/measuring-agent-autonomy).

The study also finds more agent-initiated clarification on complex tasks, while explicitly cautioning that the stops may occur at the wrong moments or ask unnecessary questions. A model’s willingness to ask is therefore a useful signal to evaluate, rather than a sufficient escalation policy. API observations cannot reconstruct complete customer workflows, another important limit on generalization. [Anthropic, 2026-02-18](https://www.anthropic.com/research/measuring-agent-autonomy).

### F04. Oversight includes preparation and planning, as well as review

**Source, date, evidence:** [Human oversight of agentic systems in practice: Examining the oversight work, challenges, and heuristics of developers using software agents](https://arxiv.org/html/2606.05391), **2026-06-03**, exploratory qualitative study, interviews with **17 experienced developers**. Twelve participants worked at one company; participants generally delegated relatively small tasks and had substantial tooling resources.

The study identifies four forms of oversight: configuring constraints before execution, co-planning, monitoring during execution, and reviewing afterward. Participants used small, independently testable tasks and up-front decisions to make subsequent review manageable. They also described information overload and shortcuts: treating plans as faithful descriptions of actual execution, treating passing tests as correctness guarantees, spot-checking, and trusting agents in unfamiliar areas. These are observed heuristics, not validated guarantees. [Study, 2026-06-03](https://arxiv.org/html/2606.05391).

For this factory, the implication is that attention spent on clear plan scope and acceptance evidence may prevent repeated downstream escalations. Counting only final approval time would miss that work. The interviews do not quantify the savings or establish that their practices scale to long-running, multi-tenant fleets. [Study, 2026-06-03](https://arxiv.org/html/2606.05391).

### F05. More human interaction does not automatically mean better judgment

**Sources, dates, evidence:** Buçinca, Malaya, and Gajos, [To Trust or to Think](https://www.eecs.harvard.edu/~kgajos/papers/2021/bucinca2021trust.shtml), **2021-04**, controlled experiment with **199 participants**; Vaccaro et al., [When combinations of humans and AI are useful](https://www.nature.com/articles/s41562-024-02024-1), **2024-10-28**, preregistered systematic review and meta-analysis of **106 experiments and 370 effect sizes**.

Buçinca and colleagues found that interventions requiring more deliberate engagement reduced overreliance compared with simple explainable-AI interfaces, but participants liked the most effective interventions least. This supports preserving meaningful deliberation at selected consequential decisions. It does not support adding friction to every permission prompt. The experiment concerns decision support, not autonomous coding fleets. [Buçinca et al., 2021-04](https://www.eecs.harvard.edu/~kgajos/papers/2021/bucinca2021trust.shtml).

The meta-analysis found average human–AI performance below the better of the human-only and AI-only conditions, with losses more common in decision tasks and stronger gains in content creation. Human–AI combinations could still improve on humans alone. Included experiments were published in 2020–2023, so this is evidence against assuming that a human checkpoint necessarily adds value, rather than a current estimate of coding-agent performance. [Vaccaro et al., 2024-10-28](https://www.nature.com/articles/s41562-024-02024-1).

### F06. Supervisory capacity depends on reorientation and safe unattended time

**Sources, dates, evidence:** Endsley and Kiris, [The Out-of-the-Loop Performance Problem and Level of Control in Automation](https://journals.sagepub.com/doi/10.1518/001872095779064555), **1995-06**, experimental navigation-task research; Crandall et al., [Validating Human–Robot Interaction Schemes in Multitasking Environments](https://scholarsarchive.byu.edu/facpub/363/), **2005-07-01**, human–robot interaction research and measurement methodology.

Endsley and Kiris connect reduced situation awareness under automation with slower decisions following automation failure. The practical concern is takeover readiness: a person asked to intervene after hours of autonomous activity needs to understand the current state and consequences. A stream of progress messages alone does not demonstrate that readiness. The original experiment studied navigation, so the transfer to software operations is conceptual. [Endsley and Kiris, 1995-06](https://journals.sagepub.com/doi/10.1518/001872095779064555).

Crandall and colleagues analyze how long a robot can be left unattended and how much interaction it needs afterward, using those quantities to reason about manageable team size under stated independence assumptions. For agents, analogous measurements would include time to the next necessary decision and time to reconstruct context. This offers a better starting point than a universal agents-per-human ratio; correlated incidents and heterogeneous software tasks make direct numerical transfer inappropriate. [Crandall et al., 2005-07-01](https://scholarsarchive.byu.edu/facpub/363/).

### F07. SRE distinguishes urgent interruption from work that can queue

**Sources, dates, evidence:** Google, [Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/), **2016**, practitioner synthesis; Google, [Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/), **2018**, engineering guidance with worked alerting models. An **SLO** is a service-level objective; an **error budget** is the tolerated amount of failure against that objective.

Google distinguishes pages, email alerts, and tickets, emphasizes the cost of interruption, and warns that excessive noise makes people skim or ignore important alerts. Its monitoring guidance favors clear symptoms and simple, comprehensible rules over requiring someone to continuously watch a dashboard. A factory’s routine capacity wait, an approval due tomorrow, and a runaway action needing immediate containment have different interruption requirements. The factory examples are applications of the SRE principles. [Google SRE, 2016](https://sre.google/sre-book/monitoring-distributed-systems/).

The workbook evaluates alerting through precision, recall, detection time, and reset time, and recommends different responses to rapid and slow error-budget consumption. Transfer the significance-and-time-to-harm reasoning. The workbook’s request-service thresholds are not validated attention or token-budget thresholds for a software factory. [Google SRE Workbook, 2018](https://sre.google/workbook/alerting-on-slos/).

**Runbooks versus judgment:** Google’s automation chapter emphasizes consistency for well-scoped, known procedures and describes the limits of human-dependent routine operation. Its troubleshooting chapter pairs alerts with evidence and playbooks, while explicitly retaining engineering judgment for severity and response. The transfer is to automate an authorized runbook when its preconditions, actions, and verification are reliable; use investigation when observations no longer fit it, and route consequential choices to someone with authority. Runbooks themselves need maintenance as systems change. [The Evolution of Automation at Google, 2016](https://sre.google/sre-book/automation-at-google/); [Effective Troubleshooting, 2016](https://sre.google/sre-book/effective-troubleshooting/), both practitioner guidance.

### F08. Finding an exception and notifying a person are separate operations

**Sources, dates, evidence:** Prometheus, [Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/), **observed 2026-10-25**, maintained product documentation; Horvitz et al., [Attention-Sensitive Alerting](https://www.microsoft.com/en-us/research/publication/attention-sensitive-alerting/), **1999-07**, foundational decision-theoretic research.

Alertmanager explicitly separates incoming alerts from deduplication, grouping, receiver routing, inhibition, and time-bounded silences. It illustrates grouping many failing service instances into one notification while retaining visibility of affected instances. This is a concrete pattern for grouping many blocked runs behind one established provider incident. Inhibition suppresses a notification; it does not establish that the underlying condition has cleared. [Prometheus, observed 2026-10-25](https://prometheus.io/docs/alerting/latest/alertmanager/).

Horvitz and colleagues model the cost of delaying information against the context-sensitive cost of interruption. Their application was messaging, not agent fleets, but it explains why importance alone is insufficient: the relevant question is what is lost by waiting until the next review opportunity. A factory can implement that principle initially with explicit urgency and deadline rules, without pretending to have calibrated numerical utility estimates. [Horvitz et al., 1999-07](https://www.microsoft.com/en-us/research/publication/attention-sensitive-alerting/).

### F09. Protecting attention requires workload policy and clear ownership

**Sources, dates, evidence:** Google, [Dealing with Interrupts](https://sre.google/sre-book/dealing-with-interrupts/), **2016**, practitioner guidance; Anthropic, [Lessons from Anthropic on building effective human-agent teams](https://claude.com/resources/articles/building-effective-human-agent-teams), **2026-06-24**, internal practitioner examples published by a vendor.

Google treats pages, tickets, and ongoing operational duties as workload, and discusses assigning responsibility so an entire team is not continuously interruptible. Backlog, frequency, severity, response expectations, and available responders all matter. Its recommendations protect time for sustained work; a faster notification transport alone cannot create more reviewer capacity. [Google SRE, 2016](https://sre.google/sre-book/dealing-with-interrupts/).

Anthropic describes explicit human and agent roles, humans retaining goal-setting, and autonomy expanding by task type after experience. It reports batching questions, providing enough repeated context for quick reorientation, limiting how many items humans see at once, assigning communication-triage agents, and limiting daily agent work to maintain sustainable review demand. These are unusually relevant practices, but the article supplies no controlled estimate of their effectiveness or optimal limits. [Anthropic, 2026-06-24](https://claude.com/resources/articles/building-effective-human-agent-teams).

### F11. Users report both excessive alerts and invisible waiting

**Sources, dates, evidence:** Individual first-person issue reports in the Claude Code repository; anecdotal, version- and workflow-dependent evidence.

In [the inactivity-based notification request](https://github.com/anthropics/claude-code/issues/7460), opened **2025-09-11**, a user describes redundant notifications while already interacting with the application and proposes delaying delivery until inactivity. In [the waiting-for-input notification request](https://github.com/anthropics/claude-code/issues/36885), opened **2026-03-21**, another user describes manually checking multiple sessions to find those waiting on questions or permission. They specifically distinguish waiting for approval from an event on every tool invocation. These reports identify opposing failure modes; they do not establish either behavior in current releases or its prevalence. [Issue #7460, 2025-09-11](https://github.com/anthropics/claude-code/issues/7460); [issue #36885, 2026-03-21](https://github.com/anthropics/claude-code/issues/36885).

Devin’s current background-only, opt-in, consolidated notifications are a documented design response consistent with these concerns, rather than measured proof that they solve them. The transferable requirement is event-specific, presence-aware delivery with a persistent place to find pending work. A user noticing an alert and a user resolving its decision are distinct events. [Devin documentation, observed 2026-10-25](https://docs.devin.ai/desktop/agent-command-center).

### F12. Recent review practice combines risk routing, evidence, and recovery

**Source, date, evidence:** Claude Code team, [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/), **2026-10-15**, detailed vendor practitioner report with internal before/after outcome metrics. This is not an independent evaluation or randomized comparison of the full process.

The team reports that merged PR volume more than doubled from June to September while the share reverted fell by over 40%. Its process combines pre-PR verification, automated bug and security review, required CI, approval requirements based on the change’s risk, a merge queue, gradual release, and rapid rollback. Certain paths always require people; automated approvals cannot substitute for a required human, and approval applies to a particular commit. The report tracks human approvals, comments, waiting time, and reverts/incidents, acknowledging that less review can merely move human effort into repairs. [Claude Code team, 2026-10-15](https://claude.dev/blog/solving-code-review-at-anthropic/).

The same account describes an agent author and reviewer cycling through more than fifty review rounds overnight, and says automatic tightening of approval policy when incident indicators deteriorate was still missing. This provides both a success report and a concrete failure mode: review and repair require convergence bounds and outcome feedback. Its lighter approval paths depend on trusted authors and substantial surrounding infrastructure. [Claude Code team, 2026-10-15](https://claude.dev/blog/solving-code-review-at-anthropic/).

### F13. Deterministic workflow steps can remove routine mid-run approvals

**Source, date, evidence:** Stripe, [Minions: Stripe’s one-shot, end-to-end coding agents](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents), **2026-02-09**, production engineering report; volume and success descriptions are company-reported.

Stripe reports over a thousand merged PRs per week written entirely by Minions and reviewed by humans. A typical run proceeds from a Slack request to a PR ready for review without intermediate interaction. Its harness interleaves model-driven work with deterministic git, lint, and testing steps. Isolated devboxes have restricted access, reducing the need for permission checks inside those environments. [Stripe, 2026-02-09](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents).

The report caps CI feedback at two rounds, citing diminishing returns in time, compute, and tokens. This is evidence for bounding a routine recovery loop and delivering a reviewable artifact. It supplies no independent review-time distribution, failure denominator, or comparison showing that two rounds is optimal elsewhere. Its throughput also depends on Stripe’s mature developer infrastructure and distributed reviewers. [Stripe, 2026-02-09](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents).

### F14. Working manager-agent patterns keep an explicit task and progress model

**Sources, dates, evidence:** Microsoft Research, [Magentic-One](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/), **2024-11-04**, research system and benchmark report; Anthropic, [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system), **2025-06-13**, deployed research-agent engineering report with internal evaluations.

Magentic-One separates a task ledger containing facts, assumptions, and a plan from a progress ledger tracking assignments and progress. Repeated lack of progress triggers replanning. This is a concrete manager pattern for bounded task execution; the existence of a “ledger” does not itself establish durable database storage, multi-host fencing, or authority over a factory’s budgets. Microsoft also explicitly notes that the system remains fallible. [Microsoft Research, 2024-11-04](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/).

Anthropic’s lead research agent decomposes a query, assigns bounded subtasks, and synthesizes compact results. It persists plans in memory and lets workers publish artifacts referenced by the lead. The report describes duplicate effort from vague delegation and synchronous bottlenecks. It reports roughly 15 times chat token use for multi-agent work, and explicitly warns that coding’s shared context and dependencies often fit less well than parallel research. Those cost ratios and task-fit observations describe this deployment, not a universal multiplier. [Anthropic, 2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system).

### F15. A coordinator can become the serialization bottleneck

**Source, date, evidence:** Cursor, [Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents), **2026-01-14**, vendor experiment report describing multi-week, many-agent coding runs. It is not an independently verified production-quality benchmark.

Cursor describes equal-status agents coordinating through a locked shared file: agents held locks too long, failed to release them, or bypassed the protocol, and twenty agents could deliver the effective throughput of two or three. Optimistic concurrency improved robustness but did not solve the broader coordination problem. The report’s more successful arrangement separated recursive planning from focused workers and a cycle-ending judge. [Cursor, 2026-01-14](https://cursor.com/blog/scaling-agents).

A dedicated integrator role introduced more bottlenecks than it solved and was removed. Fresh starts helped reduce drift, while the authors still reported excessively long runs and coordination inefficiencies. This is a warning against routing every worker result, conflict, and scheduling decision through one LLM session. It does not establish that planners should own resource accounting or that large generated codebases meet acceptance criteria. [Cursor, 2026-01-14](https://cursor.com/blog/scaling-agents).

### F16. Durable state should outlive both the model context and execution host

**Sources, dates, evidence:** Anthropic, [How we built Claude Managed Agents](https://www.anthropic.com/engineering/managed-agents), **2026-04-08**, infrastructure engineering report; Anthropic, [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), **2025-11-26**, coding-agent harness experiments.

Managed Agents separates the session’s append-only event log, the replaceable harness, and the execution sandbox. A replacement harness can recover session events; the model can query history beyond its current context window. This addresses an earlier coupled design where container failure could lose the session. Importantly, the durable session is distinct from the compressed context the model currently sees. The report also notes that a context-reset workaround useful for an older model became unnecessary with a newer one. [Anthropic, 2026-04-08](https://www.anthropic.com/engineering/managed-agents).

The earlier coding harness uses an initializer, incremental work, a feature list, progress records, and git history to support successive fresh sessions. It describes premature completion and context exhaustion even with compaction. Transfer the persistent evidence and incremental recovery pattern. A worker-local progress file is useful within one environment; fleet holds, budgets, and human rulings require a shared authority beyond that environment. The shared-authority requirement is our inference, not a claim that these articles specify this factory’s control store. [Anthropic, 2025-11-26](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Anthropic, 2026-04-08](https://www.anthropic.com/engineering/managed-agents).

### F17. More agents and more context are conditional tools, with documented failures

**Sources, dates, evidence:** [Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/html/2503.13657v3), **2025-10-26 revision**, empirical trace analysis and failure taxonomy; Anthropic, [When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop), **2026-10-22**, vendor guidance with customer anecdotes.

The revised MAST study contains 1,642 annotated traces across seven frameworks. Its fourteen failure modes span system design, inter-agent misalignment, and verification. The taxonomy was developed from closer expert analysis of over 150 traces; large-scale labeling used an LLM annotator calibrated against human annotations. Thus, 1,642 traces should not be described as 1,642 independently human-analyzed cases. The systems and models studied are older than this note, but coordination and termination defects remain useful failure categories. [MAST study, 2025-10-26](https://arxiv.org/html/2503.13657v3).

Anthropic’s October guidance describes context loss at handoffs, overlapping specialists, conflicting accumulated prompts, fragmented evaluations, and latency. It recommends splitting where independent contexts or permissions help, and otherwise testing a simpler loop with progressively loaded skills and tools. Even that loop retains hard budgets and write gates in the harness. This qualifies the earlier multi-agent enthusiasm: choose boundaries by context and measured outcomes, and reevaluate them when models change. Customer anecdotes do not prove a general advantage for either architecture. [Anthropic, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop).

### F18. Measure accepted work and human effort; output volume is insufficient

**Sources, dates, evidence:** METR, [Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/), **2025-07-10**, randomized controlled trial; METR, [We are Changing our Developer Productivity Experiment Design](https://metr.org/blog/2026-02-24-uplift-update/), **2026-02-24**, follow-up measurement and methodological critique.

The original trial randomly assigned AI availability for 246 real tasks undertaken by sixteen experienced developers in repositories they knew well. Using early-2025 tools increased task time by 19% in that setting. This is a stronger causal design than vendor throughput claims, but a limited population and now-historical tools. It does not estimate the performance of an unattended 2026 factory. [METR, 2025-07-10](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/).

The 2026 follow-up says newer data are unreliable for estimating current acceleration because developers increasingly declined no-AI work, compensation changed, and concurrent agent use complicated time accounting. Raw estimates leaned toward speedups with broad uncertainty. The implication is methodological: measure complete accepted outcomes, human handling and repair time, and agent concurrency in this system; avoid treating either old slowdown figures or current vendor output counts as a forecast. [METR, 2026-02-24](https://metr.org/blog/2026-02-24-uplift-update/).

## 3. What maps onto our problems

The problem labels are: **(a)** throughput, token spend, expiring account capacity, and future local compute; **(b)** fleet control state that survives host changes; **(c)** the division of judgment between an LLM coordinator and deterministic scheduling; **(d)** routing human attention without overload. **Adopt** means the principle fits directly. **Adapt** means the mechanism needs local policy or measurement. **Reject** identifies an extrapolation the evidence does not support. These are recommendations, not operational authorizations.

| Finding | Problems | Disposition and reason |
| --- | --- | --- |
| F01: authority by function | (c), (d) | **Adopt.** Record separate rights to observe, recommend, and act, scoped by operation and subject. A useful diagnosis should not silently grant policy-changing authority. |
| F02: observed attention bottleneck | (a), (d) | **Adapt.** Treat human handling as a constrained resource. Measure local active work and actual necessary waiting; do not copy Anthropic’s six-to-one ratio as a staffing or productivity target. |
| F03: approvals and interventions | (c), (d) | **Adapt.** Permit authorized work to proceed with effective intervention paths. Measure unnecessary asks and missed interventions, alongside approvals. Retain required human valves. |
| F04: oversight before execution | (a), (c), (d) | **Adopt.** Keep human rulings at the plan or policy level when one ruling can govern many items. Invest in clear acceptance evidence and bounded tasks before dispatch. |
| F05: interaction quality | (c), (d) | **Adapt.** Make consequential decisions deliberative and evidence-backed; simplify routine permissions. **Reject** approval count or explanation length as a proxy for sound judgment. |
| F06: takeover readiness | (a), (d) | **Adapt.** Measure safe unattended time and human reorientation time. Include recent changes, evidence, and consequences in an escalation. **Reject** a fixed agents-per-maintainer ratio. |
| F07: pages and tickets | (a), (d) | **Adopt** separate urgent, queued, and informational handling. **Adapt** urgency thresholds to factory commitments and time to harm; an expected quota wait should not page by default. |
| F08: notification routing | (b), (d) | **Adopt.** Keep deterministic facts available while grouping notifications, routing ownership, and supporting expiring silences. **Reject** treating silence, delivery, or acknowledgment as resolution. |
| F09: workload ownership | (a), (c), (d) | **Adapt.** Give each request an owner, protect decision windows, batch related questions, and keep review demand within available capacity. A coordinator may assemble a digest within its delegated scope. |
| F10: product surfaces | (b), (d) | **Adapt.** Render an actionable queue with distinct input-needed, approval-needed, review-ready, resource-wait, and incident facts. Preserve current domain meanings rather than importing a vendor’s status vocabulary wholesale. |
| F11: user complaints | (d) | **Adapt.** Notify on meaningful state changes, account for whether the person is already present, and retain pending decisions visibly. Verify delivery behavior locally; the reports are diagnostic examples, not prevalence estimates. |
| F12: risk-based review | (a), (c), (d) | **Adapt.** Route review by change consequence and evidence; bind approvals to the reviewed subject. Measure total human effort and escaped failures. **Reject** weakening existing approval rules on the strength of another team’s results. |
| F13: deterministic steps | (a), (c), (d) | **Adopt** mechanically enforced routine steps within authorized runs. **Adapt** retry bounds to measured recovery yield; the two-round Stripe rule is an example, not a universal setting. |

### A proposed operating model to evaluate

The following is a synthesis of the findings above. It has not been implemented or measured here.

**Keep facts, authority, and communication distinct.** Continue composing deterministic `needs-attention` facts, then apply a separately inspectable routing policy. A shared record should retain pending decisions, owners, dispositions, notification history, and relevant policy versions. An LLM can explain a fact or recommend a grouping while the original fact and evidence remain accessible. A missing or stale observation should remain visibly uncertain. This combines the alert-routing separation in F08 with the durable-session separation in F16. [Prometheus, observed 2026-10-25](https://prometheus.io/docs/alerting/latest/alertmanager/); [Anthropic, 2026-04-08](https://www.anthropic.com/engineering/managed-agents).

**Route by required action and time to consequence.** Use three delivery modes with explicit meanings: interrupt now when waiting materially worsens a consequential outcome; queue a decision for an identified review window when waiting is acceptable; retain an informational fact when no human action is presently required. For example, one established provider outage can produce one owned incident linking affected runs. A known capacity wait can remain visible without repeated questions. A genuinely new conflict between maintainer goals belongs in the decision queue with a recommendation and deadline. These are proposed applications of SRE and attention-sensitive alerting, not claims about current factory behavior. [Google SRE, 2016](https://sre.google/sre-book/monitoring-distributed-systems/); [Horvitz et al., 1999-07](https://www.microsoft.com/en-us/research/publication/attention-sensitive-alerting/).

**Make each escalation sufficient to decide.** A proposed decision packet should state the named tenant and workstream, the verified condition and observation time, affected work, why existing authority cannot resolve it, the concrete decision, available options, the agent’s recommendation, consequences of waiting, and evidence links. A disposition should identify who decided, its scope, the subject or policy revision it covers, and any expiry or release condition. Group repeated instances under one ruling where its scope genuinely covers them. Scope any hold to its actual impact so unaffected authorized work can continue. Keep acknowledgment separate from a decision and from verified resolution. This applies the takeover-readiness and bounded-authority findings. [Endsley and Kiris, 1995-06](https://journals.sagepub.com/doi/10.1518/001872095779064555); [OpenAI, observed 2026-10-25](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals).

**Budget the demand placed on the maintainer.** A simple planning check is:

`λ × p × t + e × u < H`

Here, `λ` is candidate outcomes per hour; `p` is the fraction requiring human review; `t` is mean human minutes per such review, including reorientation; `e` is additional interventions per hour not already counted in reviews; `u` is mean human minutes per additional intervention; and `H` is available human handling minutes per hour. This is an illustrative average-capacity condition derived for this note, not a validated control algorithm. Bursty arrivals, long decisions, and correlated incidents require spare capacity. Measure backlog age and handling-time distributions as well as averages. The rationale comes from interrupt workload and measured attention bottlenecks. [Google SRE, 2016](https://sre.google/sre-book/dealing-with-interrupts/); [Anthropic, 2026-10-16](https://www.anthropic.com/research/employment-at-anthropic).

For **(a)**, admitting more work can improve useful throughput while review capacity is available; afterward it can mainly grow unfinished work. Evaluate work admission against downstream review and recovery demand as well as provider and machine capacity. Expiring token allowances, purchased tokens, and local models with no expiring token allowance have different resource economics, but all can generate human handling demand. Preserve that distinction in policy and measurements; an unused subscription allowance is not itself evidence that more review-producing work is valuable. This is our application of F02, F09, and F18, rather than a scheduler policy established by the sources. [Anthropic, 2026-06-24](https://claude.com/resources/articles/building-effective-human-agent-teams); [METR, 2026-02-24](https://metr.org/blog/2026-02-24-uplift-update/).

For **(b)** and **(c)**, use a host-independent authority for holds, budgets, priorities, grants, and rulings, with explicit update preconditions and a recoverable decision history. Session summaries and caches can point to those records. Give the LLM coordinator bounded jobs such as investigating a new failure class, proposing a cross-tenant priority tradeoff, or preparing a review digest. Where the maintainer has delegated judgment, the coordinator can decide within that grant and record its disposition, with deterministic enforcement of the grant’s limits. Keep readiness enforcement, claims, accounting, known waits, and execution of ratified rules in deterministic code. Coordinator restarts should recover the task and authoritative facts, and selective retrieval should reconstruct only the context needed for the next decision. Durable recovery is supported by the cited architecture; atomic budget reservation and concurrent-writer semantics still require a local design. [Anthropic, 2026-04-08](https://www.anthropic.com/engineering/managed-agents); [Microsoft Research, 2024-11-04](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/).

For **(d)**, measure human handling minutes per accepted outcome, age of unresolved decisions, avoidable duplicate questions, notifications requiring no action, consequential misses, and post-approval repair effort. Break those measures down by tenant and request class. Evaluate batching and reduced review against escaped defects and recovery costs, with explicit bounds on review/fix loops. That makes attention reduction accountable to outcomes. [Claude Code team, 2026-10-15](https://claude.dev/blog/solving-code-review-at-anthropic/); [Google SRE Workbook, 2018](https://sre.google/workbook/alerting-on-slos/).

## 4. Open questions and what I could not find

- **The local demand distribution is unknown.** This research did not inspect live ledger records, dispatch runs, or maintainer response telemetry. We do not yet know which attention classes dominate, how often a request is self-resolvable, or the human time distribution by task type. F02’s telemetry is a reason to measure those quantities, not a substitute for local measurements.
- **No universal human attention allowance emerged.** Within the primary research and practitioner sources reviewed here, I found no validated number of coding agents per maintainer, interruption budget, or review-backlog threshold that transfers to this fleet. The robotics work has explicit assumptions; SRE thresholds address different services; current agent studies cover narrower populations.
- **No controlled comparison settles the coordinator boundary.** The manager reports demonstrate useful patterns and failure cases. They do not compare an LLM fleet governor with a deterministic scheduler under matched workloads, budgets, and human staffing. A bounded LLM investigator over deterministic control is a design recommendation to evaluate, not an experimentally established winner.
- **Approval-fatigue evidence is uneven.** There are direct coding-user complaints and relevant controlled decision-support studies. In the sources reviewed, I did not find a controlled coding-fleet experiment measuring how notification batching changes both missed consequential decisions and total human effort. Product documentation establishes available mechanisms; it does not establish user benefit.
- **Risk routing needs local evaluation.** Anthropic’s review report is recent and concrete, but combines many interventions, uses its own code and trusted authors, and reports outcome proxies. Classifier accuracy, correlated reviewer errors, reversibility, and delayed incidents remain relevant. Required human approvals in this repository remain governing policy.
- **Persistent storage principles do not select the control store.** The sources support recoverable state outside a session or sandbox. They do not establish whether this fleet should use Beads/Dolt records, a separate control service, or another transaction boundary, nor how cross-tenant authorization and atomic reservations should work.
- **Future local models remain an extrapolation.** Much of the agent evidence concerns well-resourced organizations using frontier models. It does not show that the same coordinator decomposition, escalation calibration, or verification coverage works with a smaller local model. Resource availability, model capability, and attention demand need separate measurements.
- **Control-room guidance has limits here.** The foundational supervisory-control papers provide transferable concepts, but I did not establish a validated alarm-rate target for software factories. The HSE [alarm-management page](https://www.hse.gov.uk/humanfactors/topics/alarm-management.htm) could not be retrieved during this research (**attempted 2026-10-25**); no numerical industrial-alarm standard is asserted from it.
- **Product coverage is a dated sample.** The comparison covers the cited official GitHub, Devin, OpenAI, Cursor, and Claude Code pages, plus the two dated user reports. I did not run live UI trials or a systematic user survey. Older labels such as “inbox” should be verified against the deployed version before becoming console requirements.

Repository grounding was read-only: the brief supplied the system context, and `.claude-plugin/scripts/livespec_orchestrator_beads_fabro/commands/needs_attention.py` was inspected to confirm that the existing abstraction composes multiple deterministic fact sources. No fleet-wide behavior or baseline performance is claimed from that code inspection. The sole authored artifact is this research note.
