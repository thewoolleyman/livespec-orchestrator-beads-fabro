# How others solve agent-fleet capacity and control state

The strongest prior art supports a deterministic admission service over shared, durable state, with separate inference routing and metering beneath it: gateways already pool endpoints and credentials, enforce scoped budgets, and perform fallback; job and workflow systems already provide queues, priorities, leases, retries, and recovery. This is a synthesis of [LiteLLM's distributed-state documentation](https://docs.litellm.ai/docs/proxy/redis_requirements) (accessed 2026-10-25), [Kueue's admission design](https://kueue.sigs.k8s.io/docs/concepts/admission_fair_sharing/) (updated 2026-09-22), and [Temporal's downstream-rate-limit pattern](https://temporal.io/blog/rate-limit-downstream-apis) (2026-07-16). For this factory, adapt those mechanisms to typed capacity pools: hosted accounts have scoped, replenishing or resetting entitlements; local models have finite concurrent serving capacity; money has separate spending and pacing constraints. Keep LLMs responsible for task decomposition, diagnosis, and proposed policy changes, while code owns claims, holds, counters, and routine resumption. [Stripe's production account](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2) (2026-02-19) supports this division. None of the sources examined establishes a complete, independently validated scheduler combining subscription-account windows, hosted APIs, local models, and autonomous coding runs; assembling that control policy remains our work.

## Findings

Research date: **2026-10-25**. Publication or modification dates appear beside sources where available. **Undated** means the page supplied no usable publication date; its access date is given instead. Documentation establishes a supported or described design, not independently measured production behavior. Practitioner reports and project benchmarks are identified as self-reported. Recommendations below are this note's analysis; no factory implementation audit or live capacity experiment was performed.

### F1. Pool quota domains, not simply API keys; subscription accounts need their own adapters

**Sources and evidence:** [Anthropic API rate limits](https://platform.claude.com/docs/en/api/rate-limits), undated, accessed 2026-10-25 — provider specification; [OpenRouter limits](https://openrouter.ai/docs/api/reference/limits), undated, accessed 2026-10-25 — provider specification; [CLIProxyAPI configuration](https://help.router-for.me/configuration/options), undated, accessed 2026-10-25 — open-source configuration documentation; [CLIProxyAPI Quota Inspector](https://github.com/AllenReder/CLIproxyAPI-Quota-Inspector), undated README, accessed 2026-10-25 — working-tool interface described by its author, not independently tested here.

Anthropic distinguishes organization-level spending and rate limits, with optional workspace limits. Its API uses a continuously replenishing token bucket; requests, input tokens, and output tokens can constrain throughput separately. OpenRouter explicitly says additional accounts or keys do not increase its globally governed rate limits. Consequently, credential count is not a reliable capacity measurement. These are API contracts and should not be substituted for subscription-product contracts. [Anthropic](https://platform.claude.com/docs/en/api/rate-limits), [OpenRouter](https://openrouter.ai/docs/api/reference/limits) (both accessed 2026-10-25).

CLIProxyAPI is closer to subscription pooling than the general API gateways: its current configuration describes round-robin, weighted round-robin, and fill-first credential selection, optional session affinity, retry rounds, and credential/model cooldowns. Cooldown persistence is optional and documented as `.cds` files beside authentication files. The inspector describes reading Codex five-hour/seven-day windows and Gemini CLI/Antigravity quotas from a running proxy. This is evidence that provider-specific quota observation and account selection exist; it does not establish a durable, fleet-wide admission authority. [Configuration](https://help.router-for.me/configuration/options), [inspector](https://github.com/AllenReder/CLIproxyAPI-Quota-Inspector) (accessed 2026-10-25).

A [2026-05-18 issue](https://github.com/router-for-me/CLIProxyAPI/issues/3467) reports that one client could exhaust the shared upstream credential pool because the proxy lacked per-client admission limits. It contains code references, but remains a historical reporter claim, not a verification of today's entire product. Its useful lesson is to test consumer fairness independently from upstream failover.

**Implication:** represent the actual shared quota domain, credential binding, observed remaining entitlement, reset/replenishment semantics, and observation time separately. Account rotation can select provisioned capacity; it does not manufacture capacity or replace budgeting.

### F2. LiteLLM provides concrete shared-budget and reservation mechanisms, including a local-model escape route

**Sources and evidence:** [Budgets and rate limits](https://docs.litellm.ai/docs/proxy/users), [Redis requirements](https://docs.litellm.ai/docs/proxy/redis_requirements), and [provider-budget routing](https://docs.litellm.ai/docs/proxy/provider_budget_routing), all undated, accessed 2026-10-25 — implementation-oriented project documentation.

LiteLLM documents budgets for teams, users, keys, and agents; provider/model budgets select eligible deployments under configured spending windows. Shared Redis coordinates rate counters, cooldowns, and budget state across workers. Without shared coordination, independent workers can each admit against their own apparent allowance. Provider-budget routing is a useful endpoint-selection mechanism, but a daily dollar allowance is not a subscription's rolling entitlement. [Redis requirements](https://docs.litellm.ai/docs/proxy/redis_requirements), [provider budgets](https://docs.litellm.ai/docs/proxy/provider_budget_routing) (accessed 2026-10-25).

The budget documentation describes pre-call maximum-cost reservation followed by reconciliation to actual cost. It also permits explicitly zero-priced models after a caller's monetary budget is exhausted, giving an example with Ollama. This is unusually direct prior art for paid-to-local fallback. Such models still need a separate serving-capacity limit. The same documentation describes database validation and rejection when authoritative spend cannot be verified under its fail-closed option. Reservation coverage and failure behavior therefore matter more than a feature named “budget.” [Budget documentation](https://docs.litellm.ai/docs/proxy/users#budget-reservation) (accessed 2026-10-25).

The boundary is significant: [issue #35524](https://github.com/BerriAI/litellm/issues/35524), opened 2026-08-01 and with a reporter's static verification dated 2026-10-06, identifies priced requests whose admission cost cannot be estimated. The issue page is closed as not planned while its body still describes a residual concern. Treat that as a version-specific investigation lead, not proof that all current budget paths fail. Our corresponding requirement is explicit handling of unknown cost rather than silently treating it as zero.

### F3. Gateways already express routing policy; quality compatibility and price ceilings remain distinct from availability

**Sources and evidence:** [Portkey AI Gateway overview](https://docs.portkey.ai/docs/product/ai-gateway), modified 2026-08-06 — vendor capability documentation; [OpenRouter provider routing](https://openrouter.ai/docs/guides/routing/provider-selection), undated, accessed 2026-10-25 — provider behavior specification; [LiteLLM router](https://docs.litellm.ai/docs/routing), undated, accessed 2026-10-25 — open-source router documentation.

Portkey documents conditional routing, provider/model fallback, API-key load balancing, circuit breakers, budgets, and custom hosts for local/private models. These features establish a common routing interface across deployments; the overview's performance superlatives are marketing and are not used here. It also does not establish that every advertised governance feature ships in the standalone open-source package. [Portkey](https://docs.portkey.ai/docs/product/ai-gateway) (2026-08-06).

OpenRouter supports ordered providers, allowed/excluded providers, fallback control, parameter compatibility, and sorting by price, throughput, or latency. Its documented performance preferences are soft: a preferred latency or throughput threshold does not guarantee that performance. `max_price`, by contrast, can prevent execution when no acceptable price exists. [OpenRouter](https://openrouter.ai/docs/guides/routing/provider-selection) (accessed 2026-10-25).

LiteLLM offers weighted, least-busy, latency, and usage-aware routing. Its own guidance recommends simple shuffling for high-traffic production and warns that usage-aware Redis work adds latency. This is a useful counterexample to assuming that the most elaborate selection algorithm is automatically best. [LiteLLM](https://docs.litellm.ai/docs/routing) (accessed 2026-10-25).

**Implication:** filter by task/model/tool compatibility and hard operator limits first, then rank eligible destinations. None of these sources demonstrates that a different model can safely take over an existing ACP coding session mid-run. Place spill-over at a defined restart, task, or stage boundary unless session transfer is separately proved.

### F4. Production control architectures separate mutable authority, hot counters, analytics, and raw audit payloads

**Sources and evidence:** [Portkey hybrid architecture](https://docs.portkey.ai/docs/aigw/self-hosting/hybrid-deployments/architecture), modified 2026-10-01 — vendor deployment architecture; [LiteLLM production guidance](https://docs.litellm.ai/docs/proxy/prod) and [spend-log retention](https://docs.litellm.ai/docs/proxy/spend_logs_deletion), undated, accessed 2026-10-25 — project operating guidance.

Portkey's documented hybrid deployment gives its backend ownership of relational configuration in MySQL; Redis serves cached configuration and counters; ClickHouse stores lightweight request analytics and administrative audit entries; object storage holds full request/response payloads fetched through pointers. Metrics and raw-log writes are asynchronous. That architecture directly addresses the difference between answering “what is allowed now?” and browsing everything that happened. It is a description of this vendor deployment, not a requirement to adopt its four-store topology. [Architecture](https://docs.portkey.ai/docs/aigw/self-hosting/hybrid-deployments/architecture) (2026-10-01).

The same page documents periodic configuration synchronization and continued service using cached configuration during management-plane disconnection. Thus “central control plane” alone does not establish immediate global hold propagation. The acceptable propagation delay is a separate contract. [Architecture](https://docs.portkey.ai/docs/aigw/self-hosting/hybrid-deployments/architecture) (2026-10-01).

LiteLLM recommends batching spend writes because per-request updates become a database bottleneck. It supplies explicit log-retention and bounded-cleanup controls; without configured retention, cleanup does not automatically exist. These are concrete operational reasons to keep historical detail off routine budget and admission reads. [Production guidance](https://docs.litellm.ai/docs/proxy/prod), [retention](https://docs.litellm.ai/docs/proxy/spend_logs_deletion) (accessed 2026-10-25).

**Implication:** a compact current-state projection plus separately retained history is a sound starting point. A journal is valuable evidence, but repeatedly scanning lifetime history to reconstruct every hold or budget is an avoidable growth dependency.

### F5. Kubernetes LLM gateways distinguish platform quotas from client allowances, but documented enforcement has important limits

**Sources and evidence:** [Envoy AI Gateway/Agent Router architecture](https://aigateway.envoyproxy.io/docs/concepts/architecture/), [QuotaPolicy](https://aigateway.envoyproxy.io/docs/capabilities/traffic/quota-policy/), and [usage-based rate limiting](https://aigateway.envoyproxy.io/docs/capabilities/traffic/usage-based-ratelimiting/), undated, accessed 2026-10-25 — open-source architecture and API documentation. The current documentation uses the name Agent Router while retaining AI Gateway API names.

The architecture separates controller configuration from Envoy and its external processor in the request path. `QuotaPolicy` scopes upstream token consumption to a backend/model across routes; usage-based limits scope consumer allowances to routes. This is the right conceptual separation for “provider pool remaining” versus “tenant allowed share.” [Architecture](https://aigateway.envoyproxy.io/docs/concepts/architecture/), [quota policy](https://aigateway.envoyproxy.io/docs/capabilities/traffic/quota-policy/) (accessed 2026-10-25).

However, the quota documentation says accounting occurs after completion, enforcement needs a dedicated rate-limit service plus Redis, failure defaults to allowing requests, and backend-wide `serviceQuota` is exposed but not enforced. Its `Shared` bucket mode allows a request while at least one applicable bucket has capacity; that differs from requiring every hierarchical ceiling to pass. These documented semantics do not establish a hard fleet spending ceiling under concurrent requests. [QuotaPolicy](https://aigateway.envoyproxy.io/docs/capabilities/traffic/quota-policy/) (accessed 2026-10-25).

The separate usage-based limiter likewise charges completed-response usage, so concurrent requests may already be running before exhaustion becomes visible. [Usage-based rate limiting](https://aigateway.envoyproxy.io/docs/capabilities/traffic/usage-based-ratelimiting/) (accessed 2026-10-25).

**Implication:** borrow the resource model and declarative policy boundary; verify reservation, composition, outage behavior, and actual enforcement for each chosen field. A Kubernetes custom resource's existence is not evidence that its semantics match our requirement.

### F6. Helicone illustrates useful attribution and the difference between distributed storage and strict coordination

**Sources and evidence:** [Helicone custom rate limits](https://docs.helicone.ai/features/advanced-usage/custom-rate-limits), undated, accessed 2026-10-25 — product documentation; [Cloudflare KV consistency](https://developers.cloudflare.com/kv/concepts/how-kv-works/), updated 2026-04-21 — underlying storage specification.

Helicone's page documents request-count or cost-based limits, global/per-user/custom-property segmentation, remaining-limit response headers, and 429 responses. A tenant or run identifier can therefore provide useful accounting attribution. The page describes Cloudflare KV as the storage mechanism and lists token limits and simultaneous multiple policies as “Coming Soon.” This establishes what that particular documented interface promises; it is not an exhaustive claim about every Helicone offering. [Helicone](https://docs.helicone.ai/features/advanced-usage/custom-rate-limits) (accessed 2026-10-25).

Cloudflare specifies eventual consistency for KV, with changes potentially taking 60 seconds or more to appear elsewhere, and says write-heavy counters are a poor fit. It points to Durable Objects for more coordinated write patterns. Therefore, persistence and geographic distribution alone do not prove atomic multi-host budget reservation. This is an inference from the two sources, not a measured Helicone overspend result. [Cloudflare](https://developers.cloudflare.com/kv/concepts/how-kv-works/) (2026-04-21).

**Implication:** adopt consistent attribution and remaining-capacity visibility. Do not use an eventually consistent read as the sole authority for a hard fleet hold or spending reservation.

### F7. Local inference capacity depends on request shape, cache locality, and queue pressure

**Sources and evidence:** [vLLM stable optimization guidance](https://docs.vllm.ai/en/stable/configuration/optimization/), page dated 2026-08-20 — serving-engine documentation; [llm-d intelligent inference scheduling](https://llm-d.ai/blog/intelligent-inference-scheduling-with-llm-d), 2025-09-03 — architecture plus project-authored benchmark; [llm-d launch](https://llm-d.ai/blog/llm-d-announce), 2025-05-20 — project launch and benchmark report.

vLLM describes finite key/value-cache space, preemption and recomputation when that space is exhausted, and controls such as concurrent sequences and batched tokens. Its chunked-prefill scheduler mixes prompt processing with generation, trading throughput against latency. A local server is consequently a queueing resource with workload-dependent capacity, even if its marginal provider-token invoice is zero. [vLLM](https://docs.vllm.ai/en/stable/configuration/optimization/) (2026-08-20).

llm-d represents serving replicas through an inference pool and an endpoint picker that discovers, filters, scores, and selects destinations using load and cache information. Its September benchmark reports roughly 55% request success for prefix-only routing versus 100% for prefix-plus-load routing in the reported high-prefix-sharing workload. With low prefix sharing, the compared strategies performed similarly. Those are project measurements, not independent results or forecasts for our hardware. [Scheduling report](https://llm-d.ai/blog/intelligent-inference-scheduling-with-llm-d) (2025-09-03).

The launch report supplies an additional bounded example: experiments on two eight-H100 nodes, with specified long-input/short-output workloads, reported higher throughput or lower first-token latency from cache-aware scheduling. This supports measuring locality benefits; it does not justify importing the speedup numbers into coding-agent capacity estimates. [Launch report](https://llm-d.ai/blog/llm-d-announce) (2025-05-20).

**Implication:** expose local model identity, validated capabilities, queue age/depth, usable concurrency, and observed serving rate. Keep the per-request serving scheduler beneath the per-run factory scheduler; they operate at different time scales.

### F8. Kueue is direct prior art for tenant shares, pooled capacity, admission, and avoiding head-of-line blocking

**Sources and evidence:** [Kueue ClusterQueue](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/), updated 2026-08-19; [Admission Fair Sharing](https://kueue.sigs.k8s.io/docs/concepts/admission_fair_sharing/), updated 2026-09-22 — open-source admission-controller specifications.

A ClusterQueue governs a resource pool with nominal quotas, resource flavors, and borrowing/lending limits. Cohorts let queues borrow unused capacity. Its default best-effort first-in-first-out policy lets a newer job that fits proceed when an older job cannot fit; strict ordering would let the older job block it. These are concrete mechanisms for pooling capacity without permanently allocating an idle silo to every tenant. [ClusterQueue](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/) (2026-08-19).

Admission Fair Sharing tracks historical consumption by local queue, applies configurable weights and decay, and charges an entry penalty to prevent bursts from exploiting delayed usage updates. The September update anchors usage at quota reservation for applicable queues, including time spent holding quota before final admission. That addresses the same race as many agents concurrently seeing an apparently unused share. [Fair sharing](https://kueue.sigs.k8s.io/docs/concepts/admission_fair_sharing/) (2026-09-22).

**Implication:** borrow weighted fairness, accounting at reservation, and bounded borrowing. Adapt the resource semantics: a GPU slot returns on completion, while spent subscription entitlement returns only according to the provider's window or refill rule. Kueue's compute quota is not itself an account-entitlement meter.

### F9. Prefect and Ray separate concurrency from start rate, and make overload behavior explicit

**Sources and evidence:** [Prefect global limits](https://docs.prefect.io/v3/concepts/global-concurrency-limits) and [usage guide](https://docs.prefect.io/v3/how-to-guides/workflows/global-concurrency-limits), undated, accessed 2026-10-25 — workflow-platform specifications; [Ray Serve production guidance](https://docs.ray.io/en/latest/serve/production-guide/best-practices.html#load-shedding), undated, accessed 2026-10-25 — serving-runtime documentation with a runnable example, not an experiment run here.

Prefect distinguishes holding slots until an operation completes from releasing slots at a configured rate to pace starts. Its server grants timed concurrency leases that clients renew; expiry releases capacity after a client disappears. Missing limits and renewal failures can permit continued execution by default, while strict settings change that behavior. These semantics are explicit and independently configurable. [Concepts](https://docs.prefect.io/v3/concepts/global-concurrency-limits), [guide](https://docs.prefect.io/v3/how-to-guides/workflows/global-concurrency-limits) (accessed 2026-10-25).

Ray Serve separately bounds ongoing requests and queued requests. Its queue bound applies per deployment handle, including proxies, rather than establishing one global fleet queue bound. Full queues reject requests, by default with 503, rather than growing indefinitely. [Ray](https://docs.ray.io/en/latest/serve/production-guide/best-practices.html#load-shedding) (accessed 2026-10-25).

**Implication:** express both occupancy and burn/start rate. Durable waiting work should stay outside active coding agents. A lease is a recovery tool, but its expiry does not establish that a remote Fabro run stopped; safe reassignment also needs a run-state check, an execution fence, or an idempotent submission protocol. That last requirement is our distributed-systems inference, not a guarantee supplied by either product.

### F10. Temporal demonstrates durable, non-LLM coordination, with bounded active history and explicit human decisions

**Sources and evidence:** [Downstream API rate-limit pattern](https://temporal.io/blog/rate-limit-downstream-apis), updated 2026-07-16, and its [implementation guide](https://docs.temporal.io/guides/rate-limit-downstream-apis) — vendor-authored validated pattern; [events and history](https://docs.temporal.io/workflow-execution/event), [Continue-As-New](https://docs.temporal.io/workflow-execution/continue-as-new), and [approval pattern](https://docs.temporal.io/design-patterns/approval), undated, accessed 2026-10-25 — runtime/design documentation.

The downstream pattern uses separate task queues for separately limited APIs, a server-enforced queue-wide activity-start rate, and separate worker concurrency controls. Adding workers therefore need not multiply the queue's allowed start rate. The guide calls out eager execution as a potential bypass and still requires retry handling for shared-key traffic and changing upstream limits. Activity starts per second do not themselves enforce variable token cost or a whole coding run's spend. [Pattern](https://temporal.io/blog/rate-limit-downstream-apis) (2026-07-16), [guide](https://docs.temporal.io/guides/rate-limit-downstream-apis) (accessed 2026-10-25).

Temporal persists execution history for recovery and auditing. Continue-As-New carries selected state into another execution with fresh history. This demonstrates that durable auditability need not entail replaying one ever-growing active history forever. Approval workflows wait for a structured external decision, recording the decision and approver context, with explicit timeout handling. [History](https://docs.temporal.io/workflow-execution/event), [Continue-As-New](https://docs.temporal.io/workflow-execution/continue-as-new), [approval](https://docs.temporal.io/design-patterns/approval) (accessed 2026-10-25).

The separate [priority and fairness documentation](https://docs.temporal.io/develop/task-queue-priority-fairness), accessed 2026-10-25, supports weighted tenant keys and priority classes but qualifies priority ordering as partition-local. It is evidence for programmed arbitration, not a promise of perfectly strict global ordering.

**Implication:** a scheduler can wait, resume, retry, and obtain a human ruling without an LLM staying alive to remember those obligations. Adopting these semantics does not require replacing Fabro with Temporal.

### F11. A database-backed queue is a viable smaller control plane; delivery guarantees still require careful submission semantics

**Sources and evidence:** [Graphile Worker introduction](https://worker.graphile.org/docs) and [job-key semantics](https://worker.graphile.org/docs/job-key), undated, accessed 2026-10-25 — open-source queue design; [Kubernetes API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/#patch-and-apply), undated, accessed 2026-10-25 — public API concurrency specification.

Graphile Worker stores jobs in PostgreSQL, uses transactional guarantees and `SKIP LOCKED` for competing workers, supports unique job keys and retries, and explicitly promises at-least-once execution. Its design rationale is reducing infrastructure overhead by using an existing database. This is a useful alternative to treating a new workflow engine or Kubernetes deployment as mandatory. It is PostgreSQL-specific prior art, not a claim that its implementation can be pointed at Beads/Dolt. [Graphile](https://worker.graphile.org/docs) (accessed 2026-10-25).

Its job-key documentation adds an important limit: in the default replacement mode, submitting a key whose existing job is locked schedules another job. A named deduplication feature therefore does not by itself prevent two copies of already-running remote work. [Job-key semantics](https://worker.graphile.org/docs/job-key) (accessed 2026-10-25).

Kubernetes supplies another concurrency pattern: conditional writes against `resourceVersion` reject stale updates with 409 Conflict. It also supports reading current resources and watching subsequent changes; watch history is finite, so clients must relist when the historical cursor is gone. Current-state access and historical event retention are deliberately different contracts. [API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) (accessed 2026-10-25).

**Implication:** shared SQL with compare-and-swap transitions can implement the essential authority without an LLM or host-local coordination file. A worker crashing after remote submission but before acknowledging it can still cause duplicate submissions on retry. Durable dispatch intent, stable idempotency identity, and reconciliation are required around that boundary; a queue alone cannot prove exactly-once remote execution.

### F12. Coding-fleet practitioners retain LLM planning while moving predictable workflow into code

**Sources and evidence:** [Stripe Minions, part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2), 2026-02-19 — first-party production account; [Cursor scaling autonomous coding](https://cursor.com/blog/scaling-agents), 2026-01-14 — first-party research-fleet experience; [Anthropic multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system), 2025-06-13 — first-party production architecture and internal measurements. All are self-reported, with no independent replication here.

Stripe reports over 1,300 agent-produced, human-reviewed pull requests merged per week. Its blueprints interleave agent loops with deterministic operations such as linting and pushing. The standard flow bounds CI iteration before returning work for human scrutiny. This is strong practitioner evidence for containing open-ended agent behavior inside explicit state-machine transitions; the article does not publish a cross-provider account-pooling algorithm. [Stripe](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2) (2026-02-19).

Cursor describes running hundreds of agents. Flat peer coordination through a shared file and locks produced long-held locks and severe throughput loss; optimistic concurrency improved mechanics but did not solve task ownership. Separating planners from workers improved progress, while a separate integrator role became a bottleneck. This supports a distinction between semantic planning and mechanical claiming; it does not prove that all planner judgment can be replaced by a priority queue. [Cursor](https://cursor.com/blog/scaling-agents) (2026-01-14).

Anthropic uses a lead researcher and parallel subagents, with explicit delegation and effort guidance. It reports that agents consumed approximately four times chat tokens and multi-agent systems approximately fifteen times chat tokens in its data. Those ratios concern its research workloads, not our coding fleet, but they demonstrate why agent-count throughput and economic throughput are different objectives. [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system) (2025-06-13).

### F13. Research schedulers handle uncertain agent graphs without putting an LLM in the resource-allocation loop

**Source and evidence:** [LLMSched v1 full paper](https://arxiv.org/html/2504.03444v1), 2025-04-04, with [submission/version metadata](https://arxiv.org/abs/2504.03444) showing a 2025-04-07 revision and ICDCS 2025 acceptance — academic simulation and physical-testbed evaluation. The detailed numbers below refer to the inspected v1.

LLMSched models variable-duration, dynamically revealed compound-LLM workflows. It uses a Bayesian profiler and an uncertainty-aware scheduling algorithm rather than asking an LLM which waiting job should execute next. Its testbed used Llama2-7B through vLLM on one H800 GPU; tested workloads included code generation, web search, and task planning. Reported scheduling overhead stayed below three milliseconds across the evaluated workload categories. [Paper](https://arxiv.org/html/2504.03444v1) (2025-04-04).

Its headline 14–79% completion-time reduction spans simulation comparisons; the physical-testbed section reports narrower workload-dependent ranges. Neither is a forecast for our fleet. Also, its exploration policy is randomized: this is prior art for a **programmed scheduler without runtime LLM arbitration**, not a literally deterministic algorithm. [Evaluation](https://arxiv.org/html/2504.03444v1#S5) (2025-04-04).

**Implication:** uncertainty about future token use or workflow length is not a reason to require an LLM dispatcher. Start with measured estimates and simple policies; introduce predictive scheduling only when local traces demonstrate a benefit.

## What maps onto our problems

Here **(a)** means throughput and capacity pooling; **(b)** means durable fleet-wide holds, budgets, priorities, and claims; **(c)** means the division between LLM judgment and deterministic scheduling; **(d)** means actionable human attention. **Adopt** means use the principle directly; **adapt** means change its semantics or implementation for this factory; **reject** means do not rely on the specified behavior. These are recommendations, not changes made or maintainer rulings.

| Finding | Problems | Disposition and reason |
|---|---|---|
| F1: quota domains and account rotation | (a), (b), (d) | **Adapt.** Create provider/account adapters with explicit shared quota domains and observation freshness. Preserve session bindings where required. **Reject** counting keys as independent capacity or using host-local cooldown files as fleet authority. Explain exhaustion once at the affected pool, including its next expected recovery. |
| F2: reservations and free fallback | (a), (b) | **Adopt** reserve-before-use and reconcile-after-use. **Adapt** reservations to the dimensions actually visible from subscription accounts and agent stages. Zero-priced fallback remains subject to local occupancy and quality gates. **Reject** an unpriced or unobserved path being treated as unlimited. |
| F3: routing policy | (a), (c) | **Adapt** capability filtering, configured price ceilings, fallback, and measured load. Keep the current repository routing authoritative until changed through its normal process. **Reject** silent quality downgrades or assuming existing ACP sessions can move between providers. |
| F4: state and audit separation | (b), (d) | **Adopt** durable current state, explicit change history, and bounded routine reads. Put large run evidence behind references. **Adapt** caching so a fleet hold has a defined propagation/acknowledgment contract. The factory does not need four new storage products merely because Portkey uses them. |
| F5: Kubernetes gateway quotas | (a), (b) | **Adapt** distinct upstream-pool and consumer-share policies. **Reject** post-completion accounting as a strict concurrent ceiling, fail-open enforcement for hard holds, unenforced API fields, and shared-bucket alternatives where every ceiling must apply. Kubernetes adoption is optional. |
| F6: attribution and consistency | (a), (b), (d) | **Adopt** tenant, plan, run, stage, provider, model, and account-domain attribution. **Reject** eventually consistent usage reads as the sole claim/budget authority. Show freshness and confidence alongside remaining capacity. |
| F7: local serving | (a), (c) | **Adapt** local capacity from measured queueing and serving behavior. Let vLLM/llm-d schedule inference batches; let the factory schedule eligible runs. Avoid a fleet-wide fixed agent count standing in for all model and host limits. |
| F8: fair pooled admission | (a), (b), (c) | **Adopt** weighted tenant shares, charge at reservation, and controlled borrowing of idle share. **Adapt** backfilling with aging so small fitting jobs do not starve large ones. Spent entitlement and reusable occupancy must remain different resource types. |
| F9: limits and back-pressure | (a), (b), (d) | **Adopt** explicit occupancy and pacing controls, renewable claims, and bounded execution queues. **Adapt** recovery to check whether a remote run remains alive. Routine waiting stays in durable state and resumes automatically; it need not wake a human or retain an interactive LLM. |
| F10: durable workflows | (b), (c), (d) | **Adopt** durable waits, scheduled retries, structured rulings, and bounded active history. **Adapt** these ideas to Dispatcher/Fabro before choosing another engine. A retry deadline is a machine obligation; a budget exception or disputed priority is a human decision. |
| F11: database queues and conditional writes | (b), (c) | **Adopt** one shared authority for claims and reservations, conditional transitions, stable dispatch identity, and recovery reconciliation. **Adapt** the storage choice to supported repository seams. **Reject** assuming PostgreSQL queue features or cross-tenant atomic transactions already exist in Beads/Dolt. |
| F12: practitioner division of labor | (a), (c), (d) | **Adopt** code for predictable lifecycle steps and LLMs for decomposition and ambiguous diagnosis. Bound retry/repair loops with an explicit disposition. **Reject** importing a vendor's pull-request count as a capacity target or adding a coordinator/integrator that serializes every routine action. |
| F13: uncertainty-aware scheduling | (a), (c) | **Adapt later.** Record distributions by task/model/stage and update estimates after actual usage. Begin with simple reproducible policies. **Reject** treating a benchmark's percentage improvement as promised factory performance or calling randomized exploration literally deterministic. |

### A concrete synthesis for this factory

The following is a proposed design direction derived from the findings, not a claim that a cited product implements the complete combination.

1. **Use a shared admission authority above the existing tenant-ready lists.** Eligibility still comes from the sanctioned readiness and admission surfaces. The fleet service arbitrates among eligible items, applies holds and policy, and records capacity reservations plus dispatch intent. It should expose decisions such as eligible, waiting for capacity until a stated time, held by an identified ruling, or requiring a decision, with a reason and policy version. This adapts F8–F11 without assigning new business judgment to a daemon.

2. **Keep different resource contracts explicit.** A pool records its provider/model capabilities, actual quota domain, credential references, availability, and observation timestamp. Reusable host/model occupancy is released on completion. Provider token buckets refill continuously. Subscription windows reset or roll according to their own adapters. Money has accounting periods and ceilings. An admission can need several of these resources simultaneously. F1, F2, and F7 support the distinction; their units cannot be added into one invented “capacity” scalar.

3. **Separate hard ceilings from sustainable pacing.** A ceiling answers whether another bounded commitment fits. A pacing policy answers how quickly to consume remaining entitlement before its next recovery while leaving room for interactive sessions and priority work. Remaining usable entitlement divided by time to recovery is a possible initial pacing signal, not a guarantee of future demand or provider capacity. Include consumption outside the factory where observable; otherwise retain explicit uncertainty and headroom. This is an adaptation, not an optimizer validated by the sources.

4. **Make hybrid routing sensitive to both expiry and congestion.** Local-first with hosted spill-over is sensible for qualified tasks when local queues are short and hosted quota is scarce. Hosted-first can be sensible when provisioned entitlement would expire unused or local wait would block valuable work. Never overflow into a second saturated pool. If no compatible destination fits, queue the item and set a recovery trigger. F2, F3, F7, and F9 supply the mechanisms; the preference order needs our measured costs, success rates, and goals.

5. **Reserve bounded work and reconcile remote reality.** Prefer enforceable call/stage limits where available; a forecast for an unbounded agent run is not a hard spend guarantee. Give dispatch intents stable identities, record the selected capacity domain, and reconcile submission outcomes after crashes. Expired leases must not authorize a second live copy merely because the first host stopped heartbeating. Keep settled usage separate from outstanding reservations, including cancellation and failed-run settlement. This follows F2, F9, and F11.

6. **Serve current control state independently of lifetime audit volume.** Keep indexed active holds, policy versions, pool observations, outstanding reservations, and current decision conditions. Append changes with actor, time, reason, and affected scope; retain full evidence separately with references. Define snapshot/rebuild and retention contracts. Shared durable SQL is a reasonable starting candidate; a workflow service or Kubernetes resources are alternatives. Persistence must survive a worker host; availability during failure of the authority itself is a separate deployment requirement. F4, F10, and F11 support this approach.

7. **Project exceptions into the existing needs-attention model.** Aggregate one exhausted provider pool across affected tenants, rather than producing one alert per refused item. Represent expected quota recovery as waiting, with the scheduler responsible for waking it. Escalate unresolved recovery, unverifiable spend, an ambiguous hold, or a requested policy exception with owner, impact, decision needed, and evidence. Human rulings become durable scoped inputs; an LLM can explain or recommend, while code validates and applies the authorized transition. This adapts F10 and F12; the exact aggregation and alert thresholds are our design work.

## Open questions and what could not be established

- **Subscription entitlements remain the least standardized part.** Across the inspected provider specifications, CLIProxyAPI configuration, and quota-inspector README, I did not find a verified common contract for all relevant rolling windows, reset timestamps, permitted concurrency, or conversion from a remaining percentage into tokens available to a particular coding run. Each adapter needs its own evidence and freshness policy. API rate limits cannot fill that gap by analogy.

- **Published steady-state burn optimization was incomplete for our combination.** The examined gateways document budgets, routing, counters, and fallback; Kueue and workflow engines document shares and concurrency. None of the inspected sources supplies a measured controller optimizing multiple hosted subscription windows together with local inference and interactive consumption. We need to choose the objective: completed accepted work, latency for priority work, use of expiring entitlement, money, or a stated combination.

- **The accounting boundary needs investigation.** Can every Claude/Codex/pi inference call in the relevant ACP path be observed and limited, or can only run starts and terminal usage be seen? Which interactive sessions consume the same quota domains? A gateway only controls traffic that actually traverses it. No source read here demonstrates a transparent, compatible gateway insertion into this repository's current ACP path.

- **Session failover is not proved.** Credential selection, request fallback, and workflow replay are documented, but the sources inspected do not prove safe transfer of an arbitrary live coding session's transcript, cached state, provider-specific identifiers, and tool state between accounts or models. Establish supported boundaries before enabling automatic reassignment.

- **Multi-host atomicity needs an explicit supported seam.** The brief establishes that Beads/Dolt is already shared, but this research did not establish supported fleet-wide schemas, atomic cross-tenant budget updates, or a Fabro idempotent-submit contract. Decide where claims and reservations are authoritative and how tenant lifecycle updates converge after partial failure. Neither a shared database address nor a task queue alone settles that transaction boundary.

- **Hard ceilings require a coverage test.** LiteLLM's documentation and reservation issue, Envoy's post-completion accounting and unenforced service-wide field, Prefect's permissive defaults, and KV consistency all show why capability labels are insufficient. An implementation evaluation must cover simultaneous admission, restart with stale counters, lost renewal, cancellation, unknown prices, and submission acknowledgment loss. No product was installed or fault-tested in this research.

- **Local-model economics and quality are unmeasured here.** The vLLM and llm-d sources explain serving bottlenecks, not whether an available local model completes our tasks at acceptable quality. Needed evidence includes accepted outcomes per model, token distributions, queue latency, retry/review cost, and hardware utilization. Zero marginal provider billing does not eliminate those constraints.

- **Audit retention and operator attention need our own requirements.** The sources provide storage separation, bounded workflow histories, and structured decisions. They do not determine this factory's evidence-retention period, acceptable hold-propagation delay, or escalation threshold. Those requirements should be explicit before a cache or retention policy is treated as correct.

- **Evidence limits:** searches covered the named gateways, CLI-account pooling, Kubernetes admission, Temporal, Prefect, Ray, SQL queues, academic scheduling, and first-party coding/research-fleet accounts. Some search requests failed or returned unrelated results; those negatives were not treated as evidence of absence. Claims above rely on pages actually read. Vendor architecture pages and project benchmarks were not independently validated, and feature documentation was not traced to a pinned executable release. This is a sourced design research note, not a procurement benchmark or production acceptance result.
