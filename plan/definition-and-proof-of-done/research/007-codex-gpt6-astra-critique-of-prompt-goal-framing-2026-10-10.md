# Codex (gpt-6-astra) critique of the prompt goal-framing proposal (2026-10-10)

Status of this note: verbatim output of an independent Codex session (GPT-6-Astra, high reasoning) started in a separate herdr pane by the definition-and-proof-of-done session on 2026-10-10 and given tmp/prompt-critique-brief.md and the draft assessment. The proposal improves salience, but it is not yet a behavior-preserving rewrite. Its strongest stall cause is an explicit attended-resume picker rule, not the absence of capitalized GOAL language. Several proposed finish conditions also contradict existing operation boundaries.

This is a source-based critique, not a measured GPT-versus-Claude comparison. I read the seven prose files, six requested bindings, nine stage prompts, and named constraints and AGENTS.md sections. Below, `prose/` means `.claude-plugin/prose/`; `stages/` means `.claude-plugin/.fabro/workflows/implement-work-item/prompts/`. Lines refer to the current files.

## (A) Stall causes by file and line

1. **The picker is commanded, not merely suggested.** `prose/plan.md:164–167` says “an attended resume asks”; `391–400` says “Present the picker and wait,” with the recorded action merely its default. This directly competes with `AGENTS.md:1499–1504` and `1549–1559`, which say to take the recorded action and honor standing authorization. A GPT model can reasonably follow the more specific skill instruction and stop. This is also executable behavior: `.claude-plugin/scripts/livespec_orchestrator_beads_fabro/commands/_plan_next_action.py:223–226` returns `ask=True, next_action=None` for every attended resume. Replacing only Step 3's opening sentence leaves both contradictions intact.

2. **A handoff is presented as an alternative to progress.** `prose/plan.md:169–188` lists “Update reasoning,” “Append a handoff entry,” and “Close the thread” as peer actions. Step 4 (`417–430`) defines a complete handoff without requiring that an authorized next action actually start. A model can satisfy one bullet, emit a polished report, and regard its turn as complete. Make handoff maintenance accompany state changes rather than count as the state change itself.

3. **“STOP” has the wrong scope.** `prose/implement.md:48–53`: “Default: dispatch and stop” / “and STOP” precedes “Monitor the dispatched run instead.” The dominant imperative permits a final answer after submission; the trailing sentence pulls the other way. Say to skip the in-session implementation steps and continue monitoring the selected dispatch. Merely adding a completion paragraph above this is insufficient.

4. **The runnable path can manufacture a refusal.** `prose/implement.md:25,83–97,206–242` still names a JSONL store, hardcodes `work-items.jsonl`, and refuses any status other than `open`. This conflicts with this repository's beads connection and lifecycle instructions. The assessment calls the machinery accurate and leaves this body untouched; a GPT model following the concrete snippet can stop before any goal matters. Treat substrate/status correction as necessary follow-up, not cruft removal disguised as equivalent wording.

5. **Inputs already supplied are solicited again.** `prose/capture-work-item.md:30–34` says “Ask the user” for title, description, and type without first consuming the invocation. `prose/plan.md:138–147` similarly unconditionally asks for topic and done statement. This invites redundant turns even when the caller gave both. Separate missing-input questions from the actual consent to write; retaining consent does not require repeating input collection.

6. **The Codex read is vulnerable to truncation.** `.claude-plugin/.codex-plugin/skills/plan/SKILL.md:123–125` uses one `cat` for the 610-line artifact; the important finish predicates are at `prose/plan.md:503–575`. A successful shell exit does not establish that all output reached the model. This review itself encountered tool-output truncation and had to re-read ranges. Require complete delivered ranges, not just a command that read the file. The binding is 153 lines, not within the assessment's stated 25–76-line range.

## (C) Missing pieces

- **A representable continuation after the last child.** `plan.md:359–365` allows only `impl`, `spec-op`, `human`, and `none`. There is no typed action for host proof, independent replay, completeness review, archive, or a running dispatch. The proposal says to record `impl` / `spec-op` and continue even when neither describes the remaining work. Specify a sanctioned continuation representation before promising automatic end-to-end resume. Do not invent enum values in prose or label agent-performable proof as human work.
- **Freshness and repeat protection.** A pointer can name a closed item or a dispatch already running. On resume and after each result, reconcile the pointer with current ledger/run evidence; advance a completed pointer, reattach to a live run, and use the existing readiness primitive for blockers. A typed instruction is not evidence it is still executable.
- **A real wake-up mechanism.** Recording a deadline does not schedule another Codex turn. Name the run id, observed state, deadline, and verified owner/mechanism that will resume supervision. If no such mechanism exists, keep bounded waits within the active session; an unavoidable exit must report unsupervised incomplete work honestly. Distinguish command/gate completion from item acceptance and plan completion. Do not infer a background process survived from an empty `--json` log.
- **First-screen contract, single shared owner.** Put a short Goal / Continue / Suspend / Fail block immediately below `# plan` in `prose/plan.md`, then the flow, then Reference. End that same shared file with a short exit audit that points back to the block. Each runtime loads this one artifact. Frontmatter descriptions provide discovery summaries, not enforcement. The Codex binding should explicitly finish truncated reads in bounded ranges. Do not add an unsupported frontmatter field and assume the harness enforces it.
- **Authorization must survive conceptually without being invented.** Separate “which already-authorized action next?” from “is this new store write consented?” `AGENTS.md:1556–1557` addresses the first; `constraints.md:470–475` and `contracts.md:1286–1302` govern the second, including invocation-scoped waivers and a specific groom exception. A typed pointer alone cannot manufacture a waiver on resume. Resolve the conflict explicitly rather than silently choosing one source.
- **Behavioral proof for the rewrite.** Use isolated, non-mutating model probes for: attended resume with prior authorization; genuinely absent write consent; stale closed-child pointer; existing live run; all children closed but host proof missing; valid proof but stale review; archive-path refusal; tool failure preventing a handoff; discussion with no drive instruction. Grade the next tool/action and stopping reason, not whether the answer repeats GOAL. Compare with the current prompts. Structural checks alone establish none of these outcomes.
