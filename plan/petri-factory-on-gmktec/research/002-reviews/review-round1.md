# Independent review: Docker on gmktec-xubuntu

Reviewed 2026-10-15. **Do not converge this design as written.** The proposed configuration is plausible, but the recovery mechanism and acceptance test are not yet sufficient for this host.

Scope: independent design review, not implementation acceptance. No host, service, firewall, package, ledger, or tracked repository state was changed. This requested, gitignored report is the only file written. Remote commands were restricted to the brief's allowed reads. No restart, rollback, package simulation, container launch, or pod exec was performed. Paths beginning `ansible/` below are relative to `/data/projects/livespec-dev-tooling/`; `design.md` means `tmp/petri-gmktec-review/design.md` in the review repository.

## Ranked findings

### BLOCKER 1 — The rollback can hang before repairing anything

The first rollback action waits for `systemctl stop docker.socket docker.service containerd.service` to finish, and only then masks Docker and repairs the firewall (`design.md:148–156`). On hp, the exact proposed Docker package ships `TimeoutSec=0`, `Restart=always`, and `KillMode=process`. A hung dockerd shutdown can therefore strand the recovery process at its first step. Wrapping only the client command in a timeout would not itself cancel the systemd job or prove dockerd stopped. Stopping these units also does not prove that all container shims/processes have disappeared, particularly if a preserved configuration enables live restore.

Specify bounded shutdown and escalation, inhibit activation before stopping, and verify that Docker cannot continue rewriting rules before cleanup. Handle absent units, partial installs, command failures and surviving processes explicitly. Do not let one missing chain or failed stop suppress the remaining independent recovery steps. Record rollback-started durably before acting, and distinguish partial failure from completed rollback. The guard must run locally as root with installed, validated executable and readable snapshots; the design currently never schedules installation/validation of that executable before arming.

Evidence: allowed hp reads `cat /usr/lib/systemd/system/docker.service /usr/lib/systemd/system/docker.socket` returned the settings above plus `Requires=docker.socket` and `ExecStart=/usr/bin/dockerd -H fd:// --containerd=/run/containerd/containerd.sock`. `cat /usr/lib/systemd/system/containerd.service` returned `KillMode=process`, `Restart=always`. hp `apt-cache policy docker.io containerd runc` confirmed installed versions match all three proposed pins. Local `/usr/share/man/man5/systemd.service.5.gz`, `TimeoutSec`, documents that it controls both start and stop timeouts.

### BLOCKER 2 — Expiry, confirmation and continued installation can race

The design has no shared state transition between the installer, confirmer and rollback (`design.md:125–156`). Example: rollback observes no `confirmed`; the controller then creates `confirmed` and stops the timer; the already-started rollback still removes Docker. Stopping a timer is not cancellation of its dispatched service. Conversely, expiry during a slow apt operation can roll back a host which the continuing play subsequently starts or modifies again. Controller death after launch does not necessarily terminate its remote package operation.

Define a durable per-run state machine with mutually exclusive confirmation and rollback claims. After expiry wins, no subsequent task may activate Docker or report success. Do not use a lock held through an indefinitely blocking apt operation that also prevents the watchdog from recovering. Before any network-affecting mutation, require successful guard creation and read back its run ID, deadline, unit state, executable and root execution context. A `systemd-run` failure must leave the host unmodified. Check the service as well as the timer on retry; a failed rollback without the final marker must still block re-entry. Use unique unit names or explicitly handle stale transient units.

Writing confirmation first is sensible **only after** atomic arbitration: if that write succeeds and timer-stop fails, a later guard invocation should safely no-op, and cleanup can be retried. If confirmation fails, the timer must remain armed. The documented transient timer also provides no recovery after an unexpected reboot: Docker is enabled by package installation and can restart with the offending configuration while the watchdog is gone. A no-reboot intention is not a boot safety mechanism; persist an unconfirmed-start inhibition/recovery mechanism or do not claim reboot coverage.

Evidence: the only confirmation test is the initial file-existence condition at `design.md:146`, with two separate confirmation operations at `142–144`; the reboot gap is explicit at `167–170`. Local `systemd.timer.5.gz` documents both default `AccuracySec=1min` and retained elapsed timers (`RemainAfterElapse=true`). Thus “within N seconds” (`174–175`) is also too strong without timer accuracy, scheduling and bounded recovery allowances.

### BLOCKER 3 — The described firewall cleanup demonstrably misses Docker rules

Removing jumps and chains named `DOCKER*` is insufficient. hp's live nft representation contains these direct built-in-chain rules:

```text
table ip raw / PREROUTING:
  ip daddr 172.17.0.2 iifname != "docker0" ... drop
  [similar rules for seven other container addresses]
table ip nat / POSTROUTING:
  ip saddr 172.17.0.0/16 oifname != "docker0" ... masquerade
```

Neither is a jump to a Docker chain. The raw rule is encountered before filter/FORWARD. `design.md:150–153` would leave these behind unless “footprint” is implemented more broadly than its stated algorithm. Do not depend on graceful dockerd cleanup in a recovery script intended to handle failure.

Use a version-tested inventory of Docker-owned rules, including direct rules, exact bridge identities and subnets, in both families. Match complete rule specifications, not mutable numeric positions. Remove external references, flush all owned chains before deleting any, and handle inter-chain references and absent rules idempotently. Use the iptables-nft interface consistently with bounded xtables-lock waits and re-read after concurrent reconcilers; do not edit iptables-managed tables with native nft commands or restore their textual nft dump. Preserve pre-existing user rules, particularly `DOCKER-USER`, rather than assuming a prefix implies exclusive ownership. A clean-install-only guard should explicitly reject pre-existing Docker state.

Evidence: allowed hp `sudo -n nft list ruleset` returned the direct rules above and warnings that these tables are managed by iptables-nft. It also showed `DOCKER-CT`, `DOCKER-BRIDGE`, `DOCKER-INTERNAL`, and `DOCKER-FORWARD`, including IPv6 Docker chains despite an IPv4-only bridge. [The exact upstream 29.1.3 iptabler implementation](https://raw.githubusercontent.com/moby/moby/docker-v29.1.3/daemon/libnetwork/drivers/bridge/internal/iptabler/iptabler.go), lines 13–32, identifies the current chains and explains why the older isolation chains are obsolete. Do not build rollback around a Docker 20/28 chain diagram.

### BLOCKER 4 — Counter deltas can both reject a healthy node and approve a broken one

The condition in `design.md:137–140` is not an end-to-end forwarding test. On gmktec, KUBE-FORWARD accepts established connections before the explicit kube-router mark ACCEPT, and that mark ACCEPT precedes FLANNEL-FWD. Traffic accepted earlier never reaches the later counter. Requiring both counters to increase therefore has no sound relationship to healthy traffic. Conversely, packets accepted in one direction can increment counters while DNS, reverse routing, NAT, MTU-sensitive traffic or a different cross-node path fails. Reconcilers can replace rules and reset counters during the window.

Replace the confirmation predicate with controlled, pre-baselined transactions from a pod network namespace on this node: cluster DNS, a known cross-node pod/ClusterIP endpoint, and permitted external HTTPS, including successful replies. Exercise fresh connections, not only established keepalives. Verify the applicable NodePort path if it is a required workload dependency. A pod exec is a useful transport for these probes, not proof by itself. Use a suitable diagnostic workload or pre-existing approved tooling; absence of curl in a production container must not masquerade as a networking failure. Include a bounded observation period spanning relevant controller reconciliation, plus Docker bridge egress verification before factory admission. None of those active tests was authorized for this review.

Evidence: gmktec `sudo -n iptables -S` showed the ordering and ACCEPT rules described. A subsequent `sudo -n iptables -L -v -n` showed zero packets on both nominated FORWARD rules while the required services were active. That single sample does not prove an outage or measure a delta; it illustrates why baseline traffic cannot be assumed. Node Ready and service-active checks (`design.md:136,141`) are independent of these application paths.

### BLOCKER 5 — Apt's actual transaction and first activation need their own fence

Simulation followed by installation does not reserve the package database (`design.md:103–109`). An unattended upgrade can change it between those operations or consume the guard's deadline while the play waits for apt. An interrupted install can leave configuration actions that a subsequent apt invocation completes outside this guard. Pinning three package versions and omitting `upgrade` does not prohibit dependency upgrades, removals, pending package configuration, or restart hooks elsewhere in the transaction.

The risk is present, not hypothetical scheduling machinery: gmktec's `unattended-upgrades`, `apt-daily.timer` and `apt-daily-upgrade.timer` all reported active. Define coordination with package activity, revalidation after contention, refusal of pending/broken dpkg state and prohibited changes, and an installation deadline compatible with the watchdog. Inspect apt/needrestart hooks and restart policy before promising that tailscaled and k3s never restart. Preserve any existing policy-rc.d policy if using that mechanism. Suppressing postinst service starts alone does not block socket activation. Both Docker activation paths must stay inhibited until configuration, guard and resource prerequisites are ready; controlled first start is easier to reason about than a postinst start.

Evidence: allowed hp `cat /var/lib/dpkg/info/docker.io.postinst /var/lib/dpkg/info/containerd.postinst` showed Docker service/socket enablement, a first-install `invoke-rc.d docker start`, conditional upgrade restart, and containerd daemon-reload plus start/restart. Those calls tolerate some failures, so apt success is not Docker readiness. gmktec `apt-cache policy` confirmed all three packages are currently absent and available at the proposed versions; `apt-cache depends docker.io containerd runc` showed conflicts/replacements as well as dependencies. I did not run an apt simulation or establish the complete target transaction/hook set.

### BLOCKER 6 — Pre-seeding the parent does not establish the sandbox envelope

`design.md:81–85` confuses a default container parent with an installed limit and with the daemon's own cgroup. `cgroup-parent` does not place dockerd inside that slice. The existing slice role first requires `docker info` to work (`tasks/main.yml:65–97`), then installs and starts the slice (`108–135`). It therefore cannot simply be moved wholesale before Docker installation. A first start followed by a failed slice role can leave implicitly created, unlimited container cgroups. File equality is also not proof of the running daemon's loaded parent: the existing role infers it from daemon.json (`161–166,198–225`), which is unsound if a daemon started before the file write.

Split slice installation/activation from the daemon-dependent verification, or enforce zero container admission until the latter completes. Verify an actual new container's cgroup membership and effective limits before enabling Fabro/redis workloads; preserve existing restart-pending state. Admission must also wait for gmktec's effective kubelet reservation, not merely agreement to update a profile. The authoritative profile currently has empty `KUBELET_ARGS` and admits 12 churn slots.

Evidence: `ansible/roles/docker_sandbox_slice/tasks/main.yml` at the lines above; its template `templates/fabro-sandbox.slice.j2:23–26`; defaults `defaults/main.yml:19–24,37–44` show shared container limits of 24G/1400%, not host-specific capacity proof. `ci-runner/k3s/phase0-bare-metal/profiles/gmktec-xubuntu.env:296,361–363` declares empty kubelet args, no taint and capacity 12. `ansible/roles/fabro_server/tasks/main.yml:977–998` starts a stopped/new server by default; its unit template `:36–37` Wants Docker and tailscaled. Its restart prohibition does not prohibit that first start. Gate this entire admission sequence explicitly.

### SHOULD-FIX 7 — The no-sysctl-change assertion is broader than the evidence

gmktec's allowed reads returned IPv4 forwarding `1`, IPv6 all/default forwarding `0/0`, and bridge-nf-call-iptables/ip6tables `1/1`. Therefore there should be no IPv4 forwarding write for the stated fresh configuration. That does not prove Docker never changes sysctls: IPv6 network setup can enable global/default forwarding, and bridge filtering/loopback routing depend on network and proxy settings. Preserving arbitrary existing daemon keys or allowing later user-defined IPv6 networks broadens the behavior beyond this first-install example. Global forwarding changes can affect non-Docker interfaces and IPv6 router-advertisement behavior.

Explicitly constrain supported effective configuration, record both families' relevant sysctls and policies, compare before/after, and define ownership-aware recovery for actual changes. Do not indiscriminately restore shared sysctls while k3s/Tailscale are running. Keep the default bridge IPv4-only if that is the intended scope; this does not mean ip6tables is untouched.

Evidence: gmktec `cat /proc/sys/net/ipv4/ip_forward /proc/sys/net/ipv6/conf/all/forwarding /proc/sys/net/ipv6/conf/default/forwarding /proc/sys/net/bridge/bridge-nf-call-iptables /proc/sys/net/bridge/bridge-nf-call-ip6tables`; [29.1.3 bridge setup](https://raw.githubusercontent.com/moby/moby/docker-v29.1.3/daemon/libnetwork/drivers/bridge/bridge_linux.go), lines 770–829, gates forwarding by network family and bridge filtering by ICC/proxy configuration; [forwarding implementation](https://raw.githubusercontent.com/moby/moby/docker-v29.1.3/daemon/libnetwork/drivers/bridge/setup_ip_forwarding.go), lines 73–108, handles both IPv6 forwarding knobs. The design snapshots neither sysctls nor an explicit per-family policy record (`121–124,154`).

### SHOULD-FIX 8 — Non-overlap and additive interfaces require explicit scope

The proposed subnet does not overlap gmktec's observed main-table routes: LAN 192.168.1.0/24 and pod subnets 10.42.0/24, 10.42.1/24 and 10.42.2/24. That is useful evidence, but plain `ip route` does not inventory policy-routing tables or IPv6 routes. `bip` governs the default bridge, not future user-defined Docker networks. The blanket claims about interfaces and routes (`design.md:93–99`) need restrictions on Docker network modes, persisted networks and additional pools. Reject a pre-existing docker0 that this run does not own before proposing to delete it during rollback.

Evidence: allowed gmktec `ip route` and `ip -br addr` confirmed two LAN interfaces/default routes, tailscale0, flannel.1, cni0 and pod veths, with no docker0. `tailscale status --self --json` reported Running and `ExitNodeOption:false`; `PrimaryRoutes` and `ExitNodeStatus` were absent, not an exhaustive routing audit. I did not run disallowed route/rule variants. Treat the bridge/veth exception as an explicit design scope, not proof that arbitrary future Docker operations preserve all existing interfaces.

### SHOULD-FIX 9 — The current play cannot target gmktec as a factory

Adding gmktec to `sandbox_hosts` alone will not run the current factory play: `ansible/fabro-hosts.yml:17–18` targets literal `hp-xubuntu`. Its redis role runs before the slice (`32–44`), which matters if this ordering is copied to a fresh host. Define a separate first-install sequence, host-specific capacity/instance settings, and prerequisites before enabling the factory. Do not broaden the play to accidentally reinstall or roll back hp's active Docker workloads.

Evidence: `ansible/inventory/legacy.yml:49–64` puts gmktec only in ci_pool and hp in both groups. `ansible/inventory/host_vars/hp-xubuntu.yml:1–5` is generated from role HOST_VARS.md; edits belong in the owning source. Its user/home, candidate binary, concurrency and redis settings are hp-specific (`24–27,42,73–123,150–154`). The reviewed Fabro defaults/handlers defer restarts, but do not constitute a Docker install guard.

### SHOULD-FIX 10 — “Isolation” does not keep sandboxes off other host networks

`design.md:66–69` overstates what Docker isolation provides. hp's Docker rules accept traffic arriving from docker0 and masquerade it toward other interfaces. That enables egress; it is not an egress prohibition toward LAN, pod networks or tailnet destinations. Preserving FORWARD ACCEPT is sensible for coexistence, but is not a sandbox security boundary. State the intended reachability policy separately, including access to host services, and do not infer it from Docker bridge isolation.

Evidence: hp `sudo -n nft list ruleset` showed `iifname "docker0" ... accept` in DOCKER-FORWARD and the POSTROUTING masquerade cited in finding 3. gmktec's current kube-router policy chains specifically match pod addresses; those matches are not evidence of coverage for 172.17.0.0/16. This review does not propose changing the firewall to impose a new policy.

### NOTE 11 — Tailscale SSH is not accurately described as ordinary tailscale0 INPUT traffic

The conclusion that host-terminated Tailscale SSH does not require gmktec's FORWARD chain is sound for the observed topology, but `design.md:38–40` gives the wrong precise mechanism. Tailscale SSH uses userspace netstack interception. The underlay transport still depends on host networking, routes, DNS and tailscaled health; a no-FORWARD dependency is not a universal no-lockout proof. The separate LLM HTTP check is valuable because it exercises a different host-service path. Keep both probes independent and bounded.

Evidence: [Tailscale's SSH documentation](https://tailscale.com/kb/1193/tailscale-ssh), “Authentication and authorization,” describes netstack port interception. `/data/projects/gmktec-xubuntu-info/AGENTS.md`, “Access,” records Tailscale-only SSH. `llm-server.md`, “systemd unit” and “Verification evidence,” records a host-bound service on 100.79.195.82:8080 and authenticated `/v1/models`. That document does not establish `/health` behavior; baseline the chosen health endpoint before installing anything rather than assuming it requires or does not require authentication. A single healthy response also does not establish uninterrupted service throughout the change.

### NOTE 12 — Host records are stale in a way that affects risk assessment

The host AGENTS.md still describes a NoSchedule taint and the old 0-versus-32 capacity discrepancy. The authoritative profile now declares no taint and 12 slots, and the live firewall contains ARC listener and runner/workflow pod rules. The design is right to assume active CI work, not an empty standby node. hp, meanwhile, is documented as factory-only with no CI churn; its coexistence demonstrates compatible daemons, not equivalent workload acceptance.

Evidence: `/data/projects/gmktec-xubuntu-info/AGENTS.md`, “CI cluster role,” explicitly defers to the profile; profile lines cited in finding 6; gmktec `sudo -n iptables -S` included listener and workflow pod chains. `ansible/inventory/legacy.yml:52–56` and `roles/docker_sandbox_slice/HOST_VARS.md:95–117` describe hp's distinct posture. No host documentation was edited during this review.

## Answers to the five open questions

**1. Does tailnet access traverse FORWARD?** Not on gmktec for a tailnet connection terminating in its own Tailscale SSH server: userspace interception handles SSH, and the encrypted transport is host traffic. The LLM connection also terminates on this host. FORWARD remains relevant to pod/container traffic and any actual transit function; being “not an exit node” alone is not a complete topology audit. The live route/status reads and host record support the design's narrow conclusion, but do not justify “cannot cut off.” See finding 11 and [Tailscale SSH internals](https://tailscale.com/kb/1193/tailscale-ssh).

**2. Does ip-forward-no-drop apply to restarts?** Yes, provided the effective configuration still contains it. In upstream Docker 29.1.3, bridge initialization passes the negation of DisableFilterForwardDrop to forwarding setup on initialization, not only first installation; the policy-changing call and its reload callback are skipped when that argument is false. It preserves the current policy rather than repairing a previously installed DROP, and cannot prevent another owner from changing policy. Evidence: [bridge_linux.go](https://raw.githubusercontent.com/moby/moby/docker-v29.1.3/daemon/libnetwork/drivers/bridge/bridge_linux.go), lines 790–816; [setup_ip_forwarding.go](https://raw.githubusercontent.com/moby/moby/docker-v29.1.3/daemon/libnetwork/drivers/bridge/setup_ip_forwarding.go), lines 35–55 and 104–108; [iptabler.go](https://raw.githubusercontent.com/moby/moby/docker-v29.1.3/daemon/libnetwork/drivers/bridge/internal/iptabler/iptabler.go), lines 85–109. This is source-backed, not a restart test of Ubuntu's patched binary; no restart was performed.

**3. Are counter deltas sound, or should the role exec into a pod?** Counter deltas are diagnostic only. Use successful, controlled request/reply probes from a pod on gmktec, with a baseline and explicit DNS, cross-node/ClusterIP and permitted internet destinations. Exec is one way to originate them, but an exec success alone proves only the exec path. Include reconcilers' settling behavior and fresh connections, and do not demand activity in a chain bypassed by earlier ACCEPT rules. The actual gmktec chain ordering is direct evidence against the proposed conjunction; see finding 4.

**4. Is targeted removal sufficient, or is whole-table restore necessary?** Targeted recovery is the right strategy for these independently reconciled tables, but the stated implementation is incomplete. Cover direct raw/NAT rules, both families, policies, owned interfaces, activation state and any actual sysctl changes; preserve unrelated and pre-existing rules, and verify the result. Do not automatically escalate to whole-table restore when cleanup fails: that would replace live Kubernetes/Tailscale state with stale state and can worsen the failure. Keep snapshots diagnostic and any full restore a separately reasoned, attended recovery operation. The live hp rules in finding 3 falsify the current cleanup algorithm; they do not justify replacing it with a full snapshot restore.

**5. Do Ubuntu 26.04 postinst scripts touch networking beyond the listed bridge/rules?** In the installed hp scripts for exactly the proposed package versions, I found no direct tailscale, interface, route or iptables commands. Docker's script manages its group, optional ZFS migration, AppArmor profile, unit enablement and daemon start/restart; containerd's manages unit enablement, daemon-reload and start/restart. Their started services are the indirect networking mutation path, and the Docker socket enables another activation path. Containerd's unit also loads overlay. These observations do not audit every dependency's maintainer script or target apt hook, especially needrestart/unattended-upgrades, and do not prove the entire installation cannot restart tailscaled or change networking indirectly. gmktec has no installed copies of these packages yet; evidence is hp's matching-version `/var/lib/dpkg/info/{docker.io,containerd}.postinst`, service units and both hosts' `apt-cache policy` output. Resolve finding 5 before making the stronger guarantee.
