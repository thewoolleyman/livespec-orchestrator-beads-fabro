Written by `claude:fabro-currency` on 2026-10-20 at about 22:15Z, under the
coordinator's R342 stop-the-line. The record of the stop itself is the plan epic

## What happened

- v0.229.2 (tag commit `775c581e`) shipped the proof-record recapture route of
  pull request #3413 (`bd-ib-j56cur`). That route made every Codex-mode dispatch
  exit 3 at the credential freshness gate, because the dispatch then required more
  credential lifetime than a fresh Codex credential carries.
- Pull request #3416 reverted #3413 server-side. It merged at 2026-10-20T22:06:33Z
  as master commit `bed7a87d`.
- The revert did NOT start a release. Release Please 17.3.0 logged, for that
  commit: `commit could not be parsed: bed7a87d… Revert "fix(review): …"` with
  `unexpected token ' ' at 1:7, valid tokens [(, !, :]`. GitHub's revert button
  writes the git-style subject `Revert "<original subject>"`, which is not a
  Conventional Commit, so Release Please never counts it as a releasable change.
  The `revert` changelog section in `release-please-config.json` matches only a
  `revert:` type prefix, not that subject.

## The remedy

The repository already has a precedent for a merged change that Release Please
cannot release: a `fix:` commit carrying a `Release-As:` footer (0.163.1 and
0.187.1). This note is that commit's content. Its `Release-As: 0.229.3` footer
makes Release Please open the v0.229.3 release pull request, so the revert reaches
the released plugin build that every dispatch runs through.

## For the next revert

A server-side revert of a released `fix:` or `feat:` change does not release by
itself. Plan for a follow-up `Release-As:` commit in the same stop, or edit the
revert commit's subject to `revert: <original subject>` before merging it.
