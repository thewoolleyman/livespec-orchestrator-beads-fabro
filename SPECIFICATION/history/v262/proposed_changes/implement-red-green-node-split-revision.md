## Decision and Rationale

Modified, then ratified under the repository's delegated decision mode (`spec_governance.revise_decision_mode: delegated`; maintainer ruling 2026-11-01 that plan implement-test-performance, epic livespec-dev-tooling-sv6m5p, runs autonomously). The proposal's direction is sound and is the one its design record (livespec-dev-tooling plan/implement-test-performance/research/004-red-green-node-split-design.md) argues from measurement: 78-92% of every implement turn is the agent polling a commit hook or suite run, and since f8340c7ae the engine's hook-skipping checkpoint commit after every node splits a Red test from its implementation and hides a refused commit from the re-entry route. The run dumps of 01M69Z9YFYV9 confirm a distinct checkpoint commit after every node, script nodes included, on the working branch, which is why `commit_green` must fold commits above the Red commit before it amends. Moving both commits into model-free command nodes removes the in-turn commit that the commit-runner, settle and re-entry clauses patch, so narrowing those clauses to `fix` and `review_fix` follows. The resolution departs from no design record: it implements note 004's target graph, its handoff file and its test-wrong edge, and leaves `fix` and `review_fix` on their in-turn commit path exactly as note 004 defers them.

It is a modify rather than an accept because applying items 1-5 literally would leave the specification internally inconsistent in seven places, each repaired here without changing the proposal's intent: (a) the refused-attempt definition the proposal deletes is the one "The recorded hook verdict outranks the agent's account of it" still cites for `fix` and `review_fix`, so it is kept and re-scoped to those stages; (b) clauses across the file address the `implement` node by name (variant node set, adapter configuration and defaults, `dispatcher.node_timeouts.implement`, `loads`, success-critical set, prompt rules, resume never-visited set, riders), so one sentence makes that name address `red` and `green` alike and changes no repository configuration key, and the two command nodes get their own timeout keys; (c) a Definition of Done already satisfied on the dispatch base would make `commit_red` refuse forever (a passing test is refused at Red), so `red` may declare already-satisfied and the already-satisfied paragraph accepts that declaration; (d) an exhausted test-wrong route ends failed carrying both sides' handoff sections, per note 004 risk 1, and — because the engine checkpoints after every node and a test-wrong lap would otherwise stack a second Red commit — `commit_red` folds every engine commit above the dispatch base before it commits, and a test-wrong route returns branch and tree to the dispatch base before `red` re-enters, so the branch carries at most one Red commit and `commit_green` amends the latest one; (e) `commit_red` stages exactly the one Red test file, keeping the existing one-test-file Red rule; (f) the affected-tests-gate paragraph is re-scoped from commits inside an implement turn to commits made by `commit_red` and `commit_green` — the hook's scoped-versus-full selection is unchanged, because the proposal does not ask to change it and note 004's whole-suite-once preference would need its own proposal; (g) Scenarios 179 and 255 named implement turns making commits, which the new paragraph makes impossible, so those steps are re-pointed to `review_fix`/`fix` turns and to `commit_red`/`commit_green`. Scenario 204 keeps its heading and is rewritten for the `green` node; the new scenario takes number 285, the next number neither ratified (scenarios end at 281) nor claimed by a pending proposal (282, 283, 284, 286 and 287 are). ## Modifications

Applied proposal items 1-5 as filed (the two new contracts.md paragraphs, the three narrowed commit-leg paragraphs plus the implement-stage needs-human cause sentence, the rewritten Scenario 204 and the new scenario, numbered 285), with these changes:

1. "An implement turn that ends incomplete does not succeed": rewritten for the `green` node as item 2 asks, but the refused-attempt definition (non-runner and runner) and the commit-run wait are KEPT, re-scoped to `fix` and `review_fix` turns, because "The recorded hook verdict outranks the agent's account of it" defines a refused attempt by reference to this paragraph. The implement-only failing-gate brief order and no-verdict brief sentence are dropped. A complete `green` turn routes to `commit_green`.
2. "The implement stage runs Red and Green as separate nodes" gains: `commit_red` stages exactly the one Red test file the `red` handoff section names and no product file; exhausted re-entry or test-wrong bounds end the stage failed on the implement failure edge, an exhausted test-wrong route carrying the latest `red` and `green` handoff sections; a `red` already-satisfied declaration; a sentence making the stage name `implement` address `red` and `green` alike wherever the specification addresses it by name (no configuration key changes), stating that the commit rules of "An agent stage's instructions and its publication boundary" govern no `red`/`green` turn; and `commit_red`/`commit_green` as command nodes resolving no adapter, with their own timeout keys. It names Scenario 285.
3. The handoff paragraph names the path as the one `git rev-parse --git-path livespec-implement-handoff.md` returns.
4. "An implement turn that reports completion with no diff ends as already satisfied" now applies to the `red` already-satisfied declaration only (after a Red commit the tree can never be unchanged); a `red` turn that leaves the tree unchanged without the declaration reaches `dead_implementer` once `red`'s `max_visits` is exhausted. Scenario 266's two cases are rewritten accordingly, keeping its heading.
4a. `commit_red` folds every engine commit above the dispatch base into the index before committing, so the Red commit sits directly on the dispatch base; a test-wrong route returns the branch and tree to the dispatch base before `red` re-enters; a `red` turn ending with neither a test nor the declaration is a `commit_red` refusal. Scenario 285 adds the refused-Red, exhausted-commit-re-entry and exhausted-test-wrong cases and the one-Red-commit check on the test-wrong lap.
4b. The fifth rule of "An agent stage's instructions and its publication boundary" gains a sentence pointing the implement stage's commit rules at `commit_red` and `commit_green`.
5. "An implement or review_fix turn's commits run the affected-tests gate": re-scoped from commits inside an implement turn to commits made by `commit_red` and `commit_green`; the hook's selection rule is unchanged.
6. §"ACP node timeouts" keys gain `commit_red` and `commit_green`.
7. Scenario 179: the Green-amend runner case names a `review_fix`-stage agent and the needs-human case a `fix` turn. Scenario 255: the first case names a `review_fix` turn, and the janitor and Red/Green cases name `commit_green` and `commit_red`. Scenario 204 keeps its heading (its tests/heading-coverage.json binding is kept, with a reason noting the green-node rebinding owed under livespec-dev-tooling-sv6m5p).
