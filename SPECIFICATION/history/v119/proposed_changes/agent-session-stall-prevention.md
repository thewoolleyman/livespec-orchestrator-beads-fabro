## Proposal: bounded-session-waits-with-honeycomb-observability

### Target specification files

- SPECIFICATION/spec.md
- SPECIFICATION/contracts.md
- SPECIFICATION/constraints.md
- SPECIFICATION/scenarios.md

### Summary

Give host sessions a bounded first-event wait and acknowledged inventory, publish its observations and numeric measurements through livespec OpenTelemetry to Honeycomb, and expose local mismatches independently of telemetry availability.

### Motivation

The approved plan bd-ib-jnpvh4 measured multi-hour silent stalls from serial gate waiters and an idle-only pane loop. The maintainer approved all five outcomes and added inventory and metrics publication to Honeycomb via ecosystem OpenTelemetry.

### Proposed Changes

Add a host-session support contract under the new contracts.md H2 "Bounded session waits and observable inventory", extend spec.md Scope boundary to include this host tooling, and state in constraints.md Process boundaries that these blocking waits are host-session operations and MUST NOT be prescribed inside factory agent turns. This adds a public session-wait CLI with wait, inventory, ack and check subcommands, not an extra named planning skill or daemon.

The wait subcommand MUST require a positive finite explicit deadline budget, bind immutable repository/session/target identities at arm time, and return on the first observed target outside its still-running predicate or on deadline expiry. Detached gate RUNNING and herdr working are the only still-running states. Other states MUST end the wait with the actual verdict or a distinct gone/unavailable/unknown outcome; diagnostic uncertainty MUST NOT become success. Gate identity includes the primary gate-store root and run id; pane identity includes backend, server/socket instance and process generation, and pane id. Retargeting via a rewritten pointer or reused identity MUST be refused. Cancelling a waiter MUST leave the target untouched.

All observations, subprocesses, transport operations and final return MUST share one monotonic deadline, including cancellation of a hung probe at expiry. Observation cadence MUST be no slower than one second while budget remains, and a slow target MUST NOT serialize observation of other targets. The result MUST identify the triggering target, each target's last observed state and freshness, and unfinished targets at expiry. Command outcome and a target's exit code MUST remain separate, both visible. A stale running observation MUST be labeled with its timestamp rather than asserted current.

Arming MUST atomically register a schema-versioned wait beneath the primary repository's ignored tmp/session-waits store before blocking. Records MUST hold session/wait identities, frozen targets, audit/deadline times, waiter process generation, observation sequence, return-ready state and acknowledgement. Concurrent writers MUST preserve each other's records. Inventory MUST re-observe targets and waiter generations, report ended-but-unacknowledged, running-without-waiter and overdue records, and expose corrupt, unsupported or unreadable records as unavailable. Unacknowledged records MUST survive session and waiter exit until explicit disposition; acknowledged retention and export queues MUST be bounded. The waiter's return-ready record proves only result production. An explicit ack by the receiving session MUST mark receipt acknowledgement only; execution consumption and target-result fulfillment MUST remain distinct under the shared obligation contract below. An exporter success or process exit MUST NOT establish any of those later states.

The check subcommand MUST expose those same mismatches before turn end. Existing host planning/drive guidance MUST use the shipped command rather than hand-written serial or single-status wait loops and MUST derive monitoring claims from inventory. Automatic stop integration MUST be claimed only for a runtime whose installed hook surface is exercised; where unavailable, guidance MUST explicitly invoke check and disclose that limit. Factory execution guidance MUST preserve the no-blocking-wait constraint.

When the existing telemetry route is configured, arming, observation changes, return, acknowledgement and inventory snapshots MUST publish curated OTLP/HTTP-JSON trace events through the existing host-local enrichment/scrub and Honeycomb path. Resource service.name MUST be livespec-dispatcher and service.namespace MUST be livespec-family; scope MUST be livespec.orchestrator.session_wait with a version. The closed catalog is session.wait.armed, session.wait.observed, session.wait.returned, session.wait.acknowledged and session.wait.inventory. Arming MUST emit before termination. Events MUST preserve allowlisted repository/session/wait identity, opaque target identity and kind, snapshot/observation identity and sequence, observed state, return reason, acknowledgement and waiter liveness. Existing work.item.id, dispatch.id and fabro.run_id MUST be populated only when known. Context MUST use an existing trace parent when present and otherwise a stable new wait trace.

Elapsed seconds, remaining budget, observation age, overdue seconds, target count, active/unacknowledged counts and export drop/rejection counts MUST be exported as typed numeric fields. An inventory invocation MUST publish its summary plus per-wait observations, including an explicit zero-count summary. Unchanged observation export MUST be rate-limited to at most once per minute; lifecycle changes MUST remain distinguishable immediately. Snapshot time and identity MUST keep repeated observations distinguishable from new waits. These trace measurements satisfy the initial metrics publication contract; a native OTLP metrics signal MAY be added only through a demonstrated ecosystem metrics route with bounded aggregate dimensions. Any unsupported publication MUST have a documented reason and equivalent trace representation where possible.

Only curated allowlisted fields MUST leave the host; raw commands, prompts, transcripts, environment values, secrets and credential-bearing paths/URLs MUST NOT be emitted. Producer, receiver allowlist and consumer MUST agree on the field vocabulary. Telemetry MUST use bounded asynchronous work and MUST NOT extend the wait deadline or suppress local results/alerts. Absent configuration MUST be visible as local-only; configured transport errors, partial rejection and queue overflow MUST be visible locally with bounded, non-recursive reporting. Honeycomb data MUST be labeled as timestamped observations, never as authoritative live control state.

The inventory contract MUST be consumable read-only by the existing overseer. The sibling owns the daemon alert and its own specification; this repository MUST NOT add a second daemon or copy its supervision internals. The plan requires its coordinated alert to surface a completed unacknowledged wait for a monitored parked session within 60 seconds, including a live but ineffective waiter, and to remain locally effective during telemetry outage. Untracked-session coverage MUST be disclosed. This outcome remains a plan-level proof obligation until the sibling implementation is released and observed.

Add scenarios.md headings (assign the next free scenario numbers during revise) with these exact behavioral titles and Given/When/Then examples:

- "The first completed gate wakes a bounded multi-target wait": Given one long-running gate, a later-listed gate that fails first, and a frozen pointer to a third gate, When the pointer is overwritten and the second gate ends, Then the result names that second gate and its exit code before the first ends and retains the third gate's original identity.
- "A pane wait ends on non-working, missing and uncertain states": Given a qualified herdr pane, When it becomes done, blocked, idle or unknown, disappears, becomes unreadable or its server generation changes, Then wait returns a distinct observed/diagnostic result and never continues waiting solely for idle.
- "The shared deadline bounds stalled probes and telemetry": Given a missing/invalid deadline, Then arming is refused; Given a valid deadline, a hung first probe, a finished sibling and a blocked exporter, When observations run, Then the sibling remains observable and the wait returns by its deadline with freshness-aware states while targets stay alive after waiter cancellation.
- "Inventory distinguishes produced and acknowledged wake-ups": Given concurrent armed waits and one killed or reused waiter process, When inventory observes a completed target, Then it reports the completion and missing acknowledgement; When the owner acknowledges it, Then the mismatch clears; corrupt or unsupported records are unavailable, and empty inventory emits an explicit zero summary.
- "The host turn-end check exposes outstanding wait mismatches": Given an ended unacknowledged target, When the installed host check runs before parking, Then the mismatch is surfaced; automatic runtime-hook support is demonstrated only on its real installed surface, and factory agent guidance continues to avoid blocking host waits.
- "Wait inventory and measurements arrive in Honeycomb without controlling liveness": Given configured existing host-local export and a unique proof wait/session, When arming, observing, returning, inventory and acknowledgement occur, Then Honeycomb queries retrieve their identity-linked events and typed numeric fields after scrubbing; Given exporter outage, partial rejection or overflow, Then local results remain deadline-bounded and degradation is visible; unconfigured export is explicitly local-only.

Revise MUST co-edit tests/heading-coverage.json for every new H2 and scenario, linking a real exercising test or an owned non-empty TODO reason until implementation lands. The implementation children must update their generic filing references to the ratified governing scenarios before admission. This proposal defers native metric instruments, additional target adapters, shell-loop refusal hooks and recurring model heartbeats; numeric trace publication, the two initial target kinds and local boundedness remain required.

## Proposal: unfinished-authorized-work-survives-coordinator-turn-end

### Target specification files

- SPECIFICATION/spec.md
- SPECIFICATION/contracts.md
- SPECIFICATION/constraints.md
- SPECIFICATION/scenarios.md

### Summary

Register obligations before waits exist and require an independent consumer to execute safe bounded recovery after coordinator turn end or loss, preserving the relay plan's single authoritative result/deadline model.

### Motivation

Maintainer-authorized stall_plan_review reported gate 20261007T142403Z-3604049 failing after FINAL with no wait or active recovery owner, a prose-only deadline and a stale completed diagnostic pointer. The maintainer requested concrete DoD, carrier and scenario corrections, with HOLD/commit/Red-Green safety and actual command execution rather than report-only attention.

### Proposed Changes

This amendment EXTENDS and, where necessary, supersedes the wait-only scope of the preceding proposal. Add the contract under the same new bounded-session-waits heading, with launch/turn-end integration references from Planning Lane realization and Dispatcher invocation. Keep safety constraints in constraints.md and user purpose in spec.md.

Shared semantics MUST come from the companion relay-delivery-and-progress-deadline contract: stable obligation identity, canonical required_result and reader, original budget/deadline, epoch, target-effect fulfillment and typed causal changed approach. This contract MUST NOT define a second result enum, independently reset an obligation deadline or equate wait completion with result fulfillment. Local runtime inventory is a projection of that authority. Ratification MUST align the two proposals atomically or sequence this consumer contract after the shared semantic contract, and heading-coverage entries MUST be co-edited. Consumer execution adds generation-fenced claim and execution evidence under the canonical recovery attempt identity, not new satisfaction semantics.

Dispatch/delegation MUST persist intent, session/repository/authorization scope, canonical result/epoch/original deadline and independently verifiable wake/consumer coverage BEFORE reporting a protected launch. It MUST attach the actual gate/run/delegation identity and reconcile crashes between intent and attachment by stable operation id without duplicating the external effect. A missing/unsupported independent recovery owner MUST produce an explicit unmonitored refusal/finding, never a claim of protected launch or completion. An actual owning session leaving its turn with unresolved authorized work MUST remain covered even if it never arms a wait. Supported completion gates MUST verify durable launch obligations and independent producer/consumer registration, preserving any existing stricter supervised Stop rules. Unsupported automatic-hook boundaries MUST be disclosed; independent launch-time registration and the consumer, not an invented hook, provide their coverage. Missing/unreadable authority MUST be unobservable, not no obligations. The inventory MUST cross-check unresolved launch obligations and actual gate/run evidence so missing wait records cannot hide outstanding work.

The existing independently supervised consumer MUST read unresolved canonical result/relay obligations on startup and while the coordinator is idle or gone, regardless of waiter existence or pane notification delivery. Terminal target observation or original deadline expiry MUST schedule actual authorized diagnosis/recovery within 60 seconds on the declared supported host configuration while no valid safety barrier applies. Losing the original coordinator or recovery-owner process MUST be handled by the existing service recovery or authorized takeover path within that bound; a stale consumer is fenced by generation. No new daemon or blind killing/restarting of a non-ready coordinator is licensed. A host whose independent coverage cannot be verified MUST explicitly refuse/report unmonitored coverage, and MUST NOT count that result as autonomous prevention. The overseer repository owns and must ratify its consumer/service realization; this repository owns registration, interoperable consumer execution receipts, action reconciliation and released integration proof.

Notification production, receipt acknowledgement, consumer claim, execution start, execution evidence, resulting next-action reconciliation and target-effect fulfillment MUST be separate durable observations. Receipt or claim alone MUST NOT mark recovery consumed. Successful recovery execution MUST NOT discharge the original result unless the relay-owned authoritative reader establishes fulfillment. The consumer MUST re-read current authority, safety state, result epoch, ledger/forge and the recorded remote factory before selecting a typed sanctioned action. A stale pointer to a completed diagnostic MUST be reconciled; a failed local gate MUST NOT be treated as proof that its remote run or merged PR failed. An expired obligation MUST trigger authorized diagnosis rather than fabricate a human block. A genuine decision outside current authority may still route to a person.

Recovery MUST use the canonical stable attempt id with serialized generation-fenced ownership. Duplicate events, concurrent consumers and restart MUST converge on one observed effect for the supported idempotent recovery command. After an ambiguous execution crash the consumer MUST query durable command effects before retrying, retain unobservable state if it cannot decide, and MUST NOT claim exactly-once arbitrary shell execution. An execution receipt carries causal source evidence, command/action identity, build, attempt identity, start/end observation and resulting effect/next action. A self-declared changed-approach record without an executable attempt and execution evidence MUST NOT reset the original deadline.

A legitimate human HOLD MUST name authority, reason, owner and release condition while retaining the original obligation/deadline history. Running commits/hooks and open Red-Green pairs MUST be visible mutation barriers. Observe and queue recovery without interrupting or abandoning protected work. When the actual safety barrier clears, the still-authorized recovery MUST execute within 60 seconds of clearance. Idle state, an ack, prose deadline or stale diagnostic alone MUST NOT count as a HOLD. No boundary may bypass spec/admission valves, interrupt a commit, close another session's pane or break a Red-Green pair to meet a timing bound.

Telemetry MUST include obligation/epoch/original deadline, notification/receipt/claim/execution/next-action identities, coverage and safety state, actual recovery latency, overdue age, duplicate/fencing counts and export degradation as curated typed OTLP events/measurements through the approved existing path. An exporter outage MUST leave local registration, deadline and recovery behavior intact. Honeycomb observation MUST NOT substitute for the authoritative local recovery/result record.

Add the following distinct Given/When/Then scenarios, using next-free scenario numbers and heading-coverage entries during revise:

- "Dispatch obligations survive coordinator FINAL without wait registration": Given an authorized real Codex coordinator in Herdr dispatches a detached operation with a canonical result and independent consumer, When the coordinator ends its actual turn without invoking wait and the gate later fails, Then the unresolved obligation remains discoverable, the consumer refreshes a stale completed diagnostic pointer and one authorized recovery command executes within 60 seconds without human input, with an execution receipt and resulting next action.
- "Independent recovery survives notification and owner loss": Given the same obligation and actual installed recovery service, When the waiter is absent or killed, the pane notification is dropped, the coordinator is gone, or the first recovery owner dies, Then the ordinary recovery/takeover path observes durable state and executes the supported action within 60 seconds with stale owners fenced; missing ALL independently verifiable coverage instead causes an explicit unmonitored refusal and does not pass prevention proof.
- "Receipt is distinct from consumed recovery and fulfilled work": Given a produced notification and receipt acknowledgement with no executed action, When inventory/result readers inspect it, Then recovery remains unconsumed and the original result remains outstanding; Given an execution receipt, Then consumption is observable but only authoritative target evidence can satisfy the result.
- "Duplicate and stale recovery reconcile safely": Given duplicate events, competing consumer generations and a pointer to a completed diagnostic or failed local gate with a merged remote PR, When recovery runs, Then fresh authoritative state selects the sanctioned recovery and one supported command effect is observed; an ambiguous execution receipt requires effect lookup before retry and an unobservable lookup preserves uncertainty.
- "Human HOLD and commit safety barriers retain recovery obligations": Given a valid explicit human HOLD, an actual active commit/hook or an open Red-Green pair, When failure/expiry occurs, Then observation and obligation retention continue while mutation is deferred without interruption; when legitimate clearance occurs, the authorized recovery executes within 60 seconds; idle state and acknowledgement alone never grant that deferral.

A runnable normally installed released-host scenario MUST exercise real Codex/Herdr turn completion (including FINAL), detached failure and independently executed recovery command, including coordinator idle/gone, absent/dead waiter, dropped notification, owner loss, duplicate events, valid HOLD, active commit/open Red pair and unmonitored refusal controls. Capture MUST measure actual command effect and next action, not just an alert, submitted prompt, ack, claimed lease, changed-approach declaration or a replacement process being alive. Independent replay and Honeycomb identity/latency retrieval with local outage controls are required for plan closure. A filed sibling referral, a merged test alone or report-only attention MUST NOT be presented as autonomous stall prevention.

A Claude Stop hook or a simulated session MUST NOT satisfy the Codex/Herdr incident proof. Other supported runtime results MUST be independently labeled. Missing Codex automatic hooks MUST NOT waive launch-time registration and independent consumption on the Codex no-wait path; if that path is unsupported, the actual incident MUST be disclosed as uncovered and its proof assertion MUST remain unmet.
