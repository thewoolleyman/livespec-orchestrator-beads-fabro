## Proposal: fleet-launch-launcher-parity-gates

### Target specification files

- SPECIFICATION/contracts.md

### Summary

State, as MUST rules for the committed `fleet-launch/` launchers, the six caller-side gates the interim launcher tmp/petri-canary/dispatch-dual-r681b.sh enforces today: the per-repository red-master hold, the repository WIP gate before the launch-time preflight, the committed breakage-exception list at wip_cap+1, the early-exit re-ticket, the gmktec factory hold file checked by the launcher itself, and the gmktec target setting with its candidate-instance cap; and require the `check-fleet-launch` harness to cover each.

### Motivation

Work item bd-ib-3ufx6l (ruled by legacy-coordinator-agent under R301, 2026-11-04 ~13:10Z, adopted by plan gmktec-factory-placement) is the parity gate of the bd-ib-x7bwug cutover: gmktec launches cannot move from tmp/petri-canary/dispatch-dual-r681b.sh onto the committed fleet-launch/dispatch-dual.sh and resume-capped.sh until the committed launchers enforce the rules r681b enforces. Measured 2026-11-04 ~13:05Z, marker counts r681b vs committed dispatch-dual.sh: hold-repo 2/0, R77 WIP gate and wip-wait 14/0, r77-breakage-exception 2/0, gmk-target candidate flip 19/0, oj2voj re-ticket 1/0; hold-gmktec only in config.sh. Its spec-change-tier classification (spec v294) found that §"Provisional fleet launch scripts" states a hold-file hold only in general terms and does not state the per-repository hold and ticket-yielding semantics, the per-repository WIP gate before preflight, the breakage exception, the early-exit re-ticket, the gmktec factory hold file, or the candidate-instance target and cap. r681b's whole-host idle floor (gmk-idle-floor) is deliberately NOT ported: the section already requires any CPU gate to measure factory-class pressure, never whole-host idle. This proposal only adds text; it rewrites no existing sentence. It is compatible with (aligns with) the pending proposal a-fleet-launcher-honours-a, which adds per-item exemptions to a repository hold file: nothing here forbids an exemption line, and that proposal's exemption semantics layer on top of the hold stated here.

### Proposed Changes

In SPECIFICATION/contracts.md §"Provisional fleet launch scripts", insert the following paragraphs immediately after the paragraph that begins "A resume launcher MUST NOT run the launch-time Definition-of-Done preflight" and before the paragraph that begins "`just check` MUST run a `check-fleet-launch` target". No existing sentence is changed or removed.

> The committed `fleet-launch/` launchers MUST also enforce the following caller-side gates. Each is a gate on WHEN a launcher invokes `drive --action impl:<item>` or `resume --item <item>`; none of them is an admission decision, and none of them changes any admission condition the Dispatcher owns.
>
> - **Red-master repository hold.** A *repository hold file* is a file named `hold-repo-<repository>`, where `<repository>` is the basename of the target repository's checkout directory, in the directory a host value in `fleet-launch/config.sh` names. While the repository hold file of its target repository exists, an impl launcher or a resume launcher MUST keep its FIFO ticket, MUST yield the FIFO head to the next live ticket, so that launchers for other repositories bind as if its ticket were not there, and MUST launch nothing into that repository. When the file is removed, the launcher MUST take its FIFO place back, in the order of the ticket it kept.
> - **Repository WIP gate.** Before an impl launcher runs its launch-time Definition-of-Done preflight, it MUST read its target repository's active work-item count and that repository's configured `wip_cap`. While the count is at or above the cap, the launcher MUST keep its FIFO ticket, MUST yield the FIFO head as a held launcher does, and MUST NOT run its launch-time preflight; the obligation above to run the preflight while queued applies only while the count is below the cap. Once the count drops below the cap, the launcher MUST take its FIFO place back, in the order of the ticket it kept. This gate is an early yield, not an admission decision: the Dispatcher still applies its own WIP cap to every `drive --action impl:<item>` the launcher starts, and a launcher whose count cannot be read MUST NOT hold on that unreadable count, because the Dispatcher's own cap still applies.
> - **Breakage exception.** The repository includes a committed breakage-exception list under `fleet-launch/`, holding one work-item id per line. For a work item that list names, the repository WIP gate MUST treat the cap as one above that repository's `wip_cap`, so the launcher admits that item while the count is below `wip_cap` + 1. The gate MUST NOT admit, above `wip_cap`, any work item the list does not name, and the exception MUST NOT raise the shared fleet cap or any per-factory cap.
> - **Early-exit re-ticket.** A launcher whose `drive --action impl:<item>` or `resume --item <item>` exits non-zero before the launched run lists on its factory board MUST re-take a FIFO ticket for the same work item, in the order of the ticket it held, and pass every gate again, rather than dropping the item from the queue. A launcher MAY bound how many times it re-takes a ticket for one work item; when it stops, it MUST log the work-item id and the drive's exit code.
> - **gmktec factory hold.** While the gmktec factory hold file exists, a launcher MUST hold every launch onto a gmktec factory instance. The launcher MUST itself assign that hold file's path, taken from the host value in `fleet-launch/config.sh` and overridable like any other, and MUST check it before every gmktec launch; a path assigned only in `fleet-launch/config.sh` that no launcher reads does not satisfy this rule.
> - **gmktec target and candidate cap.** The *gmktec target setting* selects which gmktec factory instance a gmktec launch goes to: the default instance, or the candidate instance. The launcher MUST read the setting on every gate pass from the location a host value in `fleet-launch/config.sh` names, and MUST select the default instance when the setting is absent or names anything other than the candidate. A launcher whose setting selects the candidate instance MUST launch onto it only while that instance's live run count, read from its factory board, is below the configured candidate cap, a host value read the same way; an absent candidate cap MUST be read as 0, and a live run count that cannot be read MUST hold the launch.

In the same section, insert the following paragraph immediately after the paragraph that begins "The `check-fleet-launch` harness cases MUST also cover a resume launcher that waits while the fleet count is at the cap":

> The `check-fleet-launch` harness cases MUST also cover each of the gates above: an impl launcher and a resume launcher that hold their tickets, yield the FIFO head and launch nothing while their repository's hold file exists, and take their place back once it is removed; an impl launcher that yields the FIFO head without running its preflight while its repository is at its `wip_cap`, and takes its place back once the count drops below the cap; an item on the breakage-exception list admitted at one above `wip_cap`, and an unlisted item at the same count held; a launcher whose drive exits before its run lists re-taking a FIFO ticket for the same item; a gmktec launch held while the gmktec factory hold file exists, with the hold file path the launcher assigns; and a gmktec launch sent to the instance the gmktec target setting names, launching onto the candidate only while its live run count is below the candidate cap.
