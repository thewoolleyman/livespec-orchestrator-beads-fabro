## Proposal: The committed fleet launcher honours a canary repository hold with its exemption list, and every queue reader skips a yielding ticket whichever launcher marked it

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Two caller-side rules join contracts.md §"Provisional fleet launch scripts". First, a canary repository hold: while a target repository's canary hold file exists, every launch into that repository yields and keeps its FIFO place, except a launch of an item the canary exemption list names, which launches normally. The hold is re-read at the launch point like the other holds. Second, one yielding-ticket marker: a launcher that yields the FIFO head marks its ticket with a `held=<cause>` line, and every queue reader skips another launcher's live ticket that carries either that line or the transitional `wip-wait=1` line. A ticket that has yielded its place therefore never blocks a launchable ticket behind it, whichever launcher wrote it. Scenario 307 gains two scenarios and the harness paragraph two cases. No `## ` heading is added, changed or removed.

The two behaviours the committed launcher lacks, read from origin/master 7471853a5:
1. It reads no canary-hold-repo-<repository> file and no canary-hold-exempt list. Had csrvhs reached the head, it would have launched an orchestrator item on v0.307.0 outside the two-sample canary. The section has no canary hold at all today: the only repository-wide hold is the red-master repository hold, which has no exemption list.
2. Its yield marker and the seat launcher's do not match. The seat launcher appends `wip-wait=1` and skips only `^wip-wait=1` tickets (dispatch-dual-r681b.sh scan_queue: `[ "$TK_WW" = 1 ] && continue`). Neither launcher skips the other's yielding tickets. The section already requires a held launcher to "yield the FIFO head to the next live ticket, so that launchers for other repositories bind as if its ticket were not there" (the "Red-master repository hold" bullet). It does not say how a queue reader recognises a yielding ticket, so two conforming launchers can each honour that sentence and still serialize the queue. Defining one marker closes that gap.

Why two markers are named rather than one: until the cutover the work item carries ships (bd-ib-pdmadj), the seat's launcher and the committed launcher share one FIFO directory. A rule that only the committed marker counts would leave the committed launcher blocked by every seat-launcher ticket, which is the incident above. The `wip-wait=1` line is accepted on read only. It is never written by a conforming launcher, and it MAY be dropped from the rule when the section's directory is deleted.

The canary hold is deliberately not folded into the red-master repository hold. Its purpose differs: it keeps all but named sample items off a new plugin build. It carries an exemption list that the red-master hold does not, and it is lifted on a canary verdict rather than when master turns green. The pending proposal a-fleet-launcher-honours-a adds per-item exemptions inside a red-master repository hold file. That is a different file and a different hold, and this finding is compatible with it.

### Proposed Changes

All edits are in SPECIFICATION/contracts.md §"Provisional fleet launch scripts" unless stated otherwise. The section's framing is unchanged: each rule below is a caller-side gate on WHEN a launcher invokes `drive --action impl:<item>` or `resume --item <item>`, and neither of them MUST re-implement, pre-empt or stand in for any admission condition the Dispatcher owns. Every host value named below MUST be assigned in `fleet-launch/config.sh` and MUST be overridable from an environment variable whose name begins with `FLEET_LAUNCH_`, per the section's existing rule.

1. Immediately after the "Hold scope by launch kind" bullet, add this bullet:

"- **Canary repository hold.** A *canary repository hold file* is a file named `canary-hold-repo-<repository>`, where `<repository>` is the basename of the target repository's checkout directory, in the directory a host value in `fleet-launch/config.sh` names. The *canary exemption list* is a file whose path is a host value in `fleet-launch/config.sh`, holding one work-item id per line. While the canary repository hold file of its target repository exists, an impl launcher or a resume launcher whose work item the canary exemption list does not name MUST keep its FIFO ticket, MUST yield the FIFO head exactly as the \"Red-master repository hold\" bullet requires, and MUST launch nothing into that repository. When the file is removed, the launcher MUST take its FIFO place back, in the order of the ticket it kept. A launcher whose work item the canary exemption list names MUST NOT be held by the canary repository hold. The launcher MUST read the canary exemption list at every check of the canary repository hold, so that removing a line holds that item again, and an exemption list that is absent or cannot be read MUST exempt no item. The canary repository hold applies to every launch kind; a `kinds:` line has no effect on it. Every log line in which a launcher yields to it MUST name the canary repository hold file and the first line of its contents. The exemption releases a launch only from the canary repository hold. It MUST NOT release a launch from a red-master repository hold, the repository WIP gate, the shared fleet cap, a per-factory cap, the gmktec factory hold or any other gate."

2. In the "Holds re-read at the launch point" bullet, replace the parenthetical "(its repository hold file, with that file's `kinds:` scope, and the gmktec factory hold for a gmktec launch)" with "(its repository hold file, with that file's `kinds:` scope; its target repository's canary repository hold file, with the canary exemption list; and the gmktec factory hold for a gmktec launch)". The "Holds re-read until admission" bullet re-reads holds "by the same rules as the launch-point re-read", so it MUST then apply to the canary repository hold as well; that bullet's text is not otherwise changed.

3. Immediately after the "Repository WIP gate" bullet, add this bullet:

"- **Yielding ticket marked and skipped.** A *yielding ticket* is a live FIFO ticket whose launcher yields the FIFO head under any rule of this section. A launcher that yields the FIFO head MUST mark its own ticket file as yielding by appending one line of the form `held=<cause>`, where `<cause>` names the rule it yields under, while it yields, and MUST remove that line when it takes its FIFO place back. A launcher MUST NOT write a second `held=` line into a ticket that already carries one. A queue reader computing any launcher's place in a FIFO MUST skip over another launcher's live ticket whose file carries a line beginning `held=`, and MUST equally skip one whose file carries a line reading exactly `wip-wait=1`, the marker the dispatcher seat's transitional launcher writes, so that a yielding ticket never blocks a launchable ticket behind it, whichever launcher marked it. A conforming launcher MUST NOT write the `wip-wait=1` form. A skipped ticket MUST keep its ticket number. A launcher MUST NOT skip its own ticket. The marker governs only FIFO order: it MUST NOT change a ticket's number, a dead-pid stall report, or any gate that decides whether the marked launcher itself may launch."

4. In the paragraph that begins "The `check-fleet-launch` harness cases MUST also cover each of the gates above", before its final item ("and a gmktec launch sent to the instance the gmktec target setting names ..."), add these items: "an impl launcher and a resume launcher that hold their tickets, yield the FIFO head and launch nothing into their repository while its canary repository hold file exists, while a launcher for an item the canary exemption list names launches into that repository, and an unlisted launcher takes its place back once the canary repository hold file is removed; a canary repository hold file created while a launcher holds the factory launch mutex, under which it releases the mutex and launches nothing; a launcher that yields under a repository hold appending exactly one `held=` line to its ticket and removing it when it takes its place back; and a waiting launcher behind another launcher's live ticket marked `held=` and behind one marked `wip-wait=1`, which skips both, binds and launches, while the two marked tickets keep their ticket numbers;".

5. In SPECIFICATION/scenarios.md, amend Scenario 307 without changing its heading. After its Scenario "A red-master repository hold yields the FIFO head and keeps the ticket", add these two Scenarios to its gherkin block:

- "A canary repository hold yields every launch except an exempt item": Given impl launchers for work items bd-s and bd-u of repository A holding the two oldest gmktec FIFO tickets, and an impl launcher for repository B behind them; And the canary repository hold file for repository A exists; And the canary exemption list names bd-s and not bd-u; When the launchers run; Then the bd-s launcher binds and launches into repository A; And the bd-u launcher keeps its ticket and launches nothing into repository A; And the repository B launcher binds and launches; When the canary repository hold file for repository A is removed; Then the bd-u launcher takes its FIFO place back in the order of the ticket it kept.
- "A yielding ticket does not block a launchable ticket behind it": Given the oldest gmktec FIFO ticket belongs to a live launcher and its file carries a line beginning held=; And the next ticket belongs to a live launcher and its file carries the line wip-wait=1; And the third ticket belongs to a launcher whose repository no hold or gate holds; When the third launcher computes its FIFO place; Then it skips both marked tickets, binds and launches; And both marked tickets keep their ticket numbers.
