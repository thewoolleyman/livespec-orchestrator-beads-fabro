## Proposal: The committed fleet launcher carries the dispatcher seat launcher's credential, checkout, re-ticket and routing gates, and is the launcher the seat runs

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

The committed fleet-launch/dispatch-dual.sh gains the gates the dispatcher seat's uncommitted launcher copy runs on every launch and the section does not yet state: every launch-time command runs under the target repository's own committed credential_wrapper; a launch is refused unless the target checkout is at the fetched origin default-branch tip; an early-exit re-ticket waits 0 s, 300 s and then 600 s, and stops without re-taking when the dispatch's goal-minijinja-preflight stage failed; every drive receives the configured ACP node overrides and judge-model environment; and the dispatcher seat launches every item through the committed launcher, so no uncommitted copy runs on the dispatching host. Every new host value is assigned in fleet-launch/config.sh and overridable by a FLEET_LAUNCH_ variable, and every new rule is a caller-side gate that MUST NOT stand in for any Dispatcher-owned admission condition.

### Motivation

Linked work item: bd-ib-4xqmqh, "The committed fleet launcher lacks the gates the dispatcher seat's launcher runs on every launch" (Definition-of-Done assertions #1 to #9; spec-change-tier comment: generalization target ## Provisional fleet launch scripts, spec version 321). Measured 2026-11-08 by legacy-dispatcher-agent against origin/master ac3158e1c: the de facto production launcher is the seat's uncommitted copy tmp/petri-canary/dispatch-dual-r681b.sh, which carries about ten gates the committed fleet-launch/dispatch-dual.sh lacks. Every fleet member's launches go through this launcher, so the drift between the two copies is a fleet-wide risk; the item converges them on the committed file. The fleet coordinator (legacy-coordinator-agent) approved this clause map for the legacy-dispatcher-agent seat.

This finding covers assertions #1 (tenant credential wrapper), #6 (origin-tip checkout preflight), the new part of #7 (the 0 s, 300 s, 600 s re-ticket schedule and the goal-minijinja-preflight stop), #8 (ACP overrides and judge-model environment) and #9 (the seat runs the committed launcher). The companion finding in this file covers #2 and #3.

Already stated, and therefore conformance that this proposal does NOT re-propose: #4, the repository WIP gate (the "Repository WIP gate" bullet); #5, the launch-time Definition-of-Done preflight before the mutex, with a failed preflight ending the launch (the preflight paragraph); and the same-ticket-number part of #7 (the "Early-exit re-ticket" bullet).

Measured details the clauses rest on. The uncommitted copy's tenant_wrap reads the target repository's committed credential_wrapper argv from its .livespec.jsonc and falls back to the family wrapper when the key is absent; the committed launcher instead runs one WRAPPER for every target, defaulting to FLEET_LAUNCH_DEFAULT_WRAPPER, so a non-family tenant launch receives the family password. The uncommitted R-ffpreflight step fetches the clone and fast-forwards it to origin's default branch (origin/HEAD, not a literal master) before the preflight and again at launch, and refuses the launch when it cannot; an earlier launch-only step named origin/master literally and silently launched stale clones of main-default repositories, and li-z3ynyp was preflighted on a clone 23 commits behind. Its reticket-decision.sh retries the first early exit at once, the second consecutive one after 300 s and each later one after 600 s (coordinator R301), and stops on a failed goal-minijinja-preflight stage, which fails identically on every retry (legacy-coordinator-agent 2026-11-08 ~03:4xZ, after bd-ib-ev3pbz and bd-ib-s754le each spent about 5.5 minutes of drive per retry). Its R153 step passes one --acp-node argument per line of an operator overrides file, and it exports LIVESPEC_DRIFT_JUDGE_MODEL, LIVESPEC_DOD_JUDGEMENT_MODEL and LIVESPEC_REFLECTOR_MODEL (rulings R47 and R55, 2026-10-26).

Reconciliation with §"Host judgements take the resolved dod_gate chain" (contracts.md): that paragraph says no variable of the host's environment selects a host judgement's model, and a search of .claude-plugin/, dev-tooling/ and fleet-launch/ at origin/master 886ebe8c7 found no code that reads any of the three judge-model variables. The judge-model clause below is therefore written as a pass-through that carries no model-selection authority, so it cannot contradict that paragraph; that paragraph keeps governing every host judgement's model.

Revise ordering: the revise that processes this proposal SHOULD run after the pending proposal a-goal-template-opening-delimiter (PR #4660, filed by another seat for bd-ib-cfgtlo), which moves an item-field goal-minijinja-preflight refusal onto Dispatcher exit code 5. The goal-minijinja-preflight stop below is written to compose with that change: an exit 5 keeps the existing `refused` rule, and this rule covers a failed goal-minijinja-preflight stage reported with any other exit code.

In-flight survey (2026-11-08): 12 remote spec/* branches and two open spec-touching pull requests, #4660 (a-goal-template-opening-delimiter) and #4656 (a-dispatched-pull-request-whose); neither changes §"Provisional fleet launch scripts". The pending proposals a-fleet-launcher-honours-a (per-item exemptions in a repository hold file) and a-launcher-stops-a-drive-a-hold-precedes-admission (holds re-read until admission) edit the same section and are compatible: aligned, under this repository's default-align setting.

### Proposed Changes

All edits are in SPECIFICATION/contracts.md §"Provisional fleet launch scripts" unless stated otherwise. The section's framing is unchanged: `fleet-launch/` stays a PROVISIONAL and EXPERIMENTAL caller-side launch loop, each rule below is a gate on WHEN a launcher invokes `drive --action impl:<item>` or `resume --item <item>`, and none of them MUST re-implement, pre-empt or stand in for any admission condition the Dispatcher owns. Every host value named below MUST be assigned in `fleet-launch/config.sh` and MUST be overridable from an environment variable whose name begins with `FLEET_LAUNCH_`, per the section's existing rule.

1. In the list that begins "The committed `fleet-launch/` launchers MUST also enforce the following caller-side gates", add this bullet as the FIRST bullet of the list:

"- **Tenant credential wrapper.** A launcher MUST run every launch-time command it runs against its target repository's ledger or Dispatcher under that repository's committed `credential_wrapper`, the argv the `credential_wrapper` key of the target repository's own `.livespec.jsonc` declares. Launch-time commands include the ready-set check, the host-only screen, the capacity projection read, the launch-time Definition-of-Done preflight, any read of the work item's record, every ledger comment the launcher appends, `drive --action impl:<item>` and `resume --item <item>`. A launch into a repository whose `credential_wrapper` names a tenant wrapper MUST therefore receive that tenant's password as its bare `BEADS_DOLT_PASSWORD`, and MUST NOT receive the family password in its place. When the target repository's `.livespec.jsonc` declares no `credential_wrapper`, the launcher MUST use the default wrapper its host value in `fleet-launch/config.sh` names. When the key is present but cannot be read as a non-empty argv array, the launcher MUST NOT fall back to the default wrapper: it MUST make a non-run exit whose terminal line names the work item, its ticket number and the cause `credential-wrapper-unreadable`, and the non-run exit rules below apply. An explicit wrapper override the caller passes MUST still take precedence over both, as it does today."

2. In the same list, add this bullet immediately after the "Host-only screen" bullet:

"- **Checkout at the origin tip.** Before an impl launcher runs its launch-time Definition-of-Done preflight, and again immediately before any launcher invokes `drive --action impl:<item>` or `resume --item <item>`, the launcher MUST fetch `origin` in its target repository's checkout and bring that checkout to the fetched tip of origin's default branch, the branch the remote's `HEAD` names, which MUST NOT be assumed to be `master`. It MAY do so by a fast-forward merge. The refresh MUST be serialized per checkout, so that two launchers for one repository never fetch or merge in that checkout at once. A launcher MUST NOT run its preflight and MUST NOT launch when the fetch fails, when the checkout cannot be fast-forwarded because it is dirty or has diverged, or when its `HEAD` is not then the fetched tip; in each of those cases it MUST make a non-run exit whose terminal line names the work item, its ticket number and the cause `checkout-not-at-origin-tip` with the failing step, and the non-run exit rules below apply. This is a caller-side freshness gate on the checkout the launcher reads; it is not an admission decision."

3. In the "Early-exit re-ticket" bullet, after the sentence "A launcher MAY bound how many times it re-takes a ticket for one work item.", insert:

"Before it re-takes the ticket, a launcher MUST wait a delay set by how many consecutive early exits that work item has had with no run listing between them: 0 seconds after the first, 300 seconds after the second, and 600 seconds after the third and each later one. Each of the three delays is a host value assigned in `fleet-launch/config.sh` with those defaults. While it waits, the launcher MUST NOT hold the factory mutex or a fleet in-flight marker, and it MUST yield the FIFO head as a held launcher does. A launcher whose drive reports, in its JSON output, the dispatch stage `goal-minijinja-preflight` with status `failed` MUST NOT re-take its ticket for that exit, because that stage fails identically on every retry until the work item's record is repaired. Unless the drive exited with code `5`, in which case the `refused` rule below applies, the launcher MUST make a non-run exit whose terminal line names the work item, its ticket number and the cause `goal-minijinja-preflight`, and MUST append the one ledger comment that "Ready item never silently dropped" prescribes, naming the dropped ticket number and that cause. Neither that terminal line nor that comment MUST carry a goal-template opening delimiter (a left brace followed by a second left brace, a percent sign or a hash sign), so that the launcher's own record of the refusal does not re-poison the work item."

In the same bullet, replace its last sentence, "Every other non-zero exit before listing remains an early exit and MUST still re-take the ticket at the same ticket number.", with: "Every other non-zero exit before listing, other than one whose drive reports a failed `goal-minijinja-preflight` stage, remains an early exit and MUST still re-take the ticket at the same ticket number, after the delay above."

4. In the same list, add this bullet immediately after the "Early-exit re-ticket" bullet:

"- **Configured ACP overrides and judge-model environment.** The ACP overrides file is a file whose path is a host value in `fleet-launch/config.sh`. A launcher MUST read it before every `drive --action impl:<item>` it starts and MUST pass each of its lines that is neither empty nor begins with `#` to that drive as one `--acp-node` argument, unchanged and in file order. An absent or empty overrides file MUST add no `--acp-node` argument, so the repository's committed routing governs that dispatch, and the launcher MUST log how many override arguments it passed. The launcher MUST NOT write or edit any repository's committed routing configuration to apply an override. The judge-model environment is three host values in `fleet-launch/config.sh`, one each for `LIVESPEC_DOD_JUDGEMENT_MODEL`, `LIVESPEC_DRIFT_JUDGE_MODEL` and `LIVESPEC_REFLECTOR_MODEL`. A launcher MUST export each of those variables whose host value is non-empty into the environment of every drive it starts, and MUST NOT export one whose host value is empty or unset. That export is a pass-through and carries no model-selection authority: §"Host judgements take the resolved `dod_gate` chain" continues to govern the model of every host judgement, and no consumer that paragraph forbids to take a model from the host's environment MAY read these variables."

5. Immediately before the final paragraph of the section ("The directory MUST be deleted once ..."), add this paragraph:

"Until that deletion, every seat that launches factory work through a `fleet-launch/` launcher, the dispatcher seat included, MUST launch every work item by running the committed `fleet-launch/dispatch-dual.sh` from a checkout of this repository in which that file is tracked and carries no uncommitted modification. A seat MUST NOT run, on the dispatching host, a copy of the launcher kept outside `fleet-launch/`, or a locally modified copy, for any launch. A gate the seat needs that the committed launcher lacks MUST land in the committed launcher through this repository's change path before the seat relies on it."

6. In the same section, after the paragraph that begins "The `check-fleet-launch` harness cases MUST also cover hold scope by launch kind", add this paragraph:

"The `check-fleet-launch` harness cases MUST also cover the tenant credential wrapper, the origin-tip checkout gate, re-ticket pacing and the configured routing: a stub target repository whose `.livespec.jsonc` names a stub tenant wrapper, under which every launch-time command, `drive` included, runs under that wrapper and not under the default wrapper; a stub target declaring no `credential_wrapper`, which runs under the default wrapper; a stub target whose `credential_wrapper` is unreadable, which launches nothing and leaves a `credential-wrapper-unreadable` terminal line; a checkout behind a stub origin's default branch, which is fast-forwarded and then launches; a dirty or diverged checkout, and a failing fetch, each of which launches nothing and leaves a `checkout-not-at-origin-tip` terminal line; consecutive early exits of one item that re-take the ticket after the first, second and third configured delays, read through `FLEET_LAUNCH_` overrides; a stub drive whose JSON output reports `goal-minijinja-preflight` failed with exit code `1`, which re-takes no ticket and leaves a `goal-minijinja-preflight` terminal line and one ledger comment that carries no goal-template opening delimiter; an overrides file whose lines each reach the stub drive as one `--acp-node` argument, and an absent overrides file under which the stub drive receives none; and non-empty judge-model host values that reach the stub drive's environment while an empty one is not exported. Scenario 329 in `scenarios.md` exercises these cases."

7. In SPECIFICATION/scenarios.md, add after the last scenario a scenario headed `## Scenario 329 — The committed fleet launcher runs under the tenant wrapper, from the origin tip, with paced re-tickets and the configured routing`, whose governing clause is `contracts.md` §"Provisional fleet launch scripts", with a gherkin block that MUST carry these Scenarios over a Background of fleet-launch/config.sh values overridden to stub factory boards, a stub origin, stub wrappers and throwaway queue, lock, in-flight and state directories:

- "A non-family target runs under its own credential wrapper": Given a target repository whose .livespec.jsonc declares a stub tenant credential_wrapper; When an impl launcher for one of its items runs to launch; Then the ready-set check, the preflight, every ledger read and the drive each run under that tenant wrapper; And none of them runs under the default wrapper.
- "A launch is refused off the origin tip": Given a target checkout that has diverged from the stub origin's default branch; When an impl launcher for one of its items runs; Then it runs no preflight and launches nothing; And its terminal line names the item, its ticket number and the cause checkout-not-at-origin-tip.
- "A behind checkout is brought to the origin tip and launches": Given a target checkout one commit behind the stub origin's default branch, which is named main; When an impl launcher for one of its items runs; Then the checkout's HEAD is the fetched tip of origin's main before the preflight runs; And the launcher launches.
- "Early-exit re-tickets are paced": Given a stub drive that exits 1 before its run lists on every attempt; When the launcher handles three consecutive early exits; Then it re-takes the same ticket number after the first, second and third configured delays in that order; And it holds no mutex and no in-flight marker while it waits.
- "A failed goal-minijinja-preflight stage is not retried": Given a stub drive that exits 1 and reports the stage goal-minijinja-preflight with status failed; When the launcher handles the exit; Then it re-takes no ticket; And it leaves a goal-minijinja-preflight terminal line and one ledger comment that carries no goal-template opening delimiter.
- "Configured routing reaches every drive": Given an overrides file with two override lines and one comment line, and a non-empty DoD-judgement model host value; When the launcher starts a drive; Then the stub drive receives exactly two --acp-node arguments in file order; And LIVESPEC_DOD_JUDGEMENT_MODEL is set in its environment; When the overrides file is removed; Then the next drive receives no --acp-node argument.

## Proposal: The gmktec factory hold releases a freeze-allowlisted item once and a priority-1 item, and a held ticket does not block a releasable one behind it

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

The existing "gmktec factory hold" bullet says a launcher MUST hold every launch onto a gmktec instance while the hold file exists. This amendment narrows that rule to the dispatch freeze the maintainer ruled: an item listed in a freeze allowlist launches exactly once while the hold exists, its allowlist line consumed at LAUNCH; a priority-1 item launches without an allowlist line; and a waiting launcher skips another launcher's queue ticket whose item the hold holds, so a held queue head does not block a releasable item behind it. Scenario 307 is amended to match. No new heading is added.

### Motivation

Linked work item: bd-ib-4xqmqh, Definition-of-Done assertions #2 and #3. These are an AMENDMENT of the existing gmktec-hold bullet and of Scenario 307, not new standalone rules, per the fleet coordinator's (legacy-coordinator-agent) approved clause map.

Provenance: STANDING RULING 11, maintainer direction relayed by legacy-coordinator-agent, recorded on livespec-dev-tooling-6tgd2z at 2026-11-05T20:42:09Z (priorities record 20:42:12Z) and as a scope event on plan epic bd-ib-ynnykl at 2026-11-05T20:45:02Z. Maintainer verbatim: "Make it the top priority to get the expedited plan done. Stop all other work that is not serving it (don't can cel in progress work, just don't dispatch anything else until it's plan is completely done and proven)". The mechanism adopted was the hold-gmktec file plus a freeze allowlist of exempt items. Two later coordinator R301 rulings shaped it: the HELD-HEAD skip (2026-11-06 ~17:3xZ, stop-the-line), and the one-shot grant with the priority-1 pass (2026-11-07 ~23:2xZ, after bd-ib-ltlg4i launched through the freeze on a stale allowlist line).

Measured in the dispatcher seat's uncommitted launcher tmp/petri-canary/dispatch-dual-r681b.sh: the allowlist is read at every check, so removing a line re-holds the item; a launcher consumes its item's line at LAUNCH under a lock shared with every launcher and the seat, and logs the grant; a pre-listing retry then waits behind the hold like any other ticket; the priority is read once per launcher and fails closed to "not priority 1"; and a queue reader skips another launcher's gmktec ticket whose item is not allowlisted, while never skipping its own. The committed fleet-launch/dispatch-dual.sh has none of this, so the section's current wording (hold EVERY gmktec launch) is what it implements.

The repository hold's per-item exemption (pending proposal a-fleet-launcher-honours-a) is a different file and a different hold; this amendment does not change it. The "Holds re-read at the launch point" bullet already re-reads the gmktec hold under the mutex; the amendment makes that re-read honour the same releases.

### Proposed Changes

In SPECIFICATION/contracts.md §"Provisional fleet launch scripts", replace the "gmktec factory hold" bullet with:

"- **gmktec factory hold.** While the gmktec factory hold file exists, a launcher MUST hold every launch onto a gmktec factory instance, except a launch this bullet releases. The launcher MUST itself read that hold file's path from its host value in `fleet-launch/config.sh`, overridable like any other, into a variable of its own, and MUST check that path before every gmktec launch; a path assigned only in `fleet-launch/config.sh` that no launcher reads does not satisfy this rule. The *freeze allowlist* is a file whose path is a host value in `fleet-launch/config.sh`, holding one work-item id per line. While the hold file exists:
  - **One-shot allowlist release.** A launcher whose work item the freeze allowlist names MUST NOT be held by the gmktec hold. The launcher MUST read the allowlist at every hold check, so that removing a line holds that item again. When it invokes `drive --action impl:<item>` or `resume --item <item>` for an allowlisted item while the hold file exists, the launcher MUST remove that item's line from the allowlist at that LAUNCH, under a lock every launcher and the seat that edits the allowlist share, and MUST log the grant with the work item and the time. One allowlist line therefore releases its item exactly once: a later launch of the same item, a re-take after an early exit included, MUST be held as any unlisted item is, unless the allowlist names it again.
  - **Priority-1 release.** A launcher whose work item has priority 1 in the ledger MUST NOT be held by the gmktec hold, and consumes no allowlist line. The launcher MAY read the priority once per launcher. A priority that cannot be read MUST be treated as not priority 1, so the hold applies.
  - **Held queue head skipped.** A launcher computing its place in a gmktec FIFO MUST skip over another launcher's live ticket whose work item the hold holds, exactly as it skips a yielding ticket, so that a held ticket at the head does not block a released ticket behind it. A skipped ticket MUST keep its ticket number and MUST take its FIFO place back when the hold file is removed. A launcher MUST NOT skip its own ticket, and MUST NOT skip a ticket whose work item the freeze allowlist names. A queue reader MAY treat another launcher's ticket whose item the allowlist does not name as held without reading that item's priority; a priority-1 ticket so skipped still binds, because its own launcher never skips its own ticket and the factory mutex still serializes every bind.
  The releases above MUST also apply where the "Holds re-read at the launch point" bullet re-reads the gmktec hold under the mutex. They release a launch only from the gmktec factory hold. They MUST NOT release it from a repository hold, the shared fleet cap, a per-factory cap or any other gate, and they change no admission condition the Dispatcher owns."

In the `check-fleet-launch` harness paragraph that lists "a gmktec launch held while the gmktec factory hold file exists, with the hold file path the launcher assigns", extend that case to read: "a gmktec launch of an item that is neither allowlisted nor priority 1 held while the gmktec factory hold file exists, with the hold file path the launcher assigns; an allowlisted item that launches once while the hold file exists, its allowlist line removed at that launch, and a second launch of the same item then held; a priority-1 item that launches while the hold file exists without an allowlist line, and an item whose priority cannot be read held; and a held ticket at the head of a gmktec FIFO skipped so that an allowlisted ticket behind it launches, the held ticket keeping its ticket number and taking its place back once the hold file is removed".

In SPECIFICATION/scenarios.md, amend Scenario 307 without changing its heading:

- In the Scenario "The gmktec factory hold file holds every gmktec launch", add the step "And the launcher's work item is neither listed in the freeze allowlist nor priority 1" after its Given step.
- After that Scenario, add a Scenario "An allowlisted item launches once through the gmktec hold": Given the gmktec factory hold file exists; And the freeze allowlist names work item bd-x; When a gmktec launcher for bd-x reaches the launch; Then it launches bd-x; And the freeze allowlist no longer names bd-x; When a second gmktec launcher for bd-x reaches the head of the FIFO; Then it launches nothing until the hold file is removed.
- Then add a Scenario "A priority-1 item launches through the gmktec hold": Given the gmktec factory hold file exists; And work item bd-p has priority 1 and is not in the freeze allowlist; When a gmktec launcher for bd-p reaches the launch; Then it launches bd-p; And the freeze allowlist is unchanged.
- Then add a Scenario "A held head does not block a released ticket behind it": Given the gmktec factory hold file exists; And the oldest gmktec FIFO ticket is for work item bd-h, which is neither allowlisted nor priority 1; And the next ticket is for work item bd-x, which the freeze allowlist names; When the launchers run; Then the bd-x launcher binds and launches; And the bd-h launcher keeps its ticket number and launches nothing; When the hold file is removed; Then the bd-h launcher takes its FIFO place back in the order of the ticket it kept.

The amendment adds, changes and removes no `## ` heading, so it needs no tests/heading-coverage.json co-edit.
