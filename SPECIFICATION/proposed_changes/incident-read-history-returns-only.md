## Proposal: The incident authority's read-history action returns every recorded generation of every attempt by work-item id alone, and a closed incident's history ends with its closed generation beside an empty outstanding list

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Orchestrator spec v360 §"Expedited incident lifecycle" requires inspection to report an incident's attempts and requires a failed attempt to remain in the authority history exactly as recorded, but it never names the action an operator runs to read that history, never says what that action returns or how it is selected, never requires a closed incident to expose its closed generation, and never requires an outstanding list at closure. The implementation shows the gap: the incident authority writer's `read-history` action is bound to the exact-identity historical read, so it demands an attempt id, phase, generation, operation and owner and returns the ONE snapshot that matches them; the library's whole-chain history read (`read_incident_history`, every committed attempt oldest first) has no action that exposes it; and a `closed` generation is committed as a plain attempt record, so nothing a later reader can fetch carries the empty outstanding list that `complete-incident` reported once, in its own reply, and never persisted or recomputed. This proposal adds one normative paragraph to §"Expedited incident lifecycle" that names `read-history`, fixes its selector (repository and canonical work-item id alone), its return (every committed generation of every attempt, oldest first, genesis root to current head, each exactly as recorded, with the token that committed it and whether it is the head), its `outstanding` list (judged from the retained history at the time of the read: empty for a `closed` head, no repayment outstanding for a `drill-closed` head, non-empty for every other head), and its bounds (it authorizes nothing, is not normal factory proof, reads only through the authenticated canonical reader, and refuses by name rather than returning an empty or partial history), and adds one named `## Scenario` to `scenarios.md` that exercises the several-attempts case, the closed case and the two refusal cases.

### Motivation

Filed for work item bd-ib-92x3o (orchestrator tenant; spec-change tier, verdict partial, generalization target `## Expedited incident lifecycle`, spec version 360), under livespec-dev-tooling's plan expedited-incident-response-flag (epic livespec-dev-tooling-bqnzcm), which carries plan assertion 14: "Operators can inspect each incident's skipped work, verification evidence, attempts, merge and revert SHAs, CI runs, deferred spec work and final factory proof using the incident work item as the durable identity." Measured evidence, from the A14 READS comment on livespec-dev-tooling-t26bbr (2026-11-11T21:29:21Z, livespec-dev-tooling tenant): that incident was recorded `closed` at generation 19 after four attempts (the original repair, a corrected attempt, a reverting recovery and a normal repayment; PRs livespec-dev-tooling#4161, #4172 and #4204; merges d8d23cae, dfef5765, 02adb9db and the revert cf4d1715). `incident-authority read-history` run with the closed identity returned ONLY that one attempt record (1681 bytes), not the chain, so on its own it could not show every attempt; the four attempts were reachable only by reading the item's whole comment stream through `context --json` (435 KB) and attributing them by hand; and no canonical record of the closed generation together with `outstanding []` was exposed anywhere a reader could fetch; only the plan owner's prose receipt carried it. The verified plan record of 2026-11-11T23:56:53Z states the same limit, and completeness review bqnzcm-completeness-review-20261112T100929Z recorded it as gap G3. The ratified text covers the all-attempts half only by implication (`Inspection MUST report the item's attempts ...`; `The failed attempt and its pr-bound carrier MUST remain in the authority history exactly as recorded`), so an implementation whose only history action returns one snapshot is not in conflict with the spec as written. The spec has to name the action and its return before bd-ib-92x3o can be implemented against it and before livespec-dev-tooling-bqnzcm.2, the integration host proof that waits on this item's release, can judge the reader. The proposal places the behaviour in `contracts.md` because the incident authority writer's actions and their replies are the plugin's wire contract, and realization belongs in this repository, not in livespec core, per the cross-repo placement split. It changes no phase, transition, fence or closure rule: the paragraph adds a reader and bounds it, and the existing exact-identity historical snapshot read stays available under a different action name.

### Proposed Changes

In `SPECIFICATION/contracts.md`, section `## Expedited incident lifecycle`, insert the following paragraph immediately AFTER the paragraph that begins "Inspection MUST report the item's attempts, owner/generation, current carrier, merge/revert SHAs, CI run identities, skipped work, focused evidence, retained failures, deferred debt, recovery receipts and final normal proof." and BEFORE the paragraph that begins "These incident-specific first-authority and pre-PR carrier requirements do not replace the ordinary claim-token protocol":

> The incident authority writer MUST expose a `read-history` action selected by repository and canonical work-item id alone; it MUST NOT require an attempt id, phase, generation, operation id or owner to select, and it MUST NOT accept any of them as a filter. `read-history` MUST return every committed generation of every attempt in the item's retained authority history, oldest first, from the item's first incident authority root to the current head, walking the whole retained chain from that root: it MUST NOT start from any later pointer to the head, MUST NOT return only the current attempt, and MUST NOT omit a generation because a later generation, a corrected attempt, a revert or a reopen superseded it, so a failed attempt and its `pr-bound` carrier, a corrected successor, a reverting recovery attempt, a reopened generation and every normal repayment generation each appear exactly as recorded. For each generation the reply MUST carry the attempt record byte-identical to the committed snapshot, the identity of the closed token that committed it, and whether it is the current head. The reply MUST carry one `outstanding` list, judged from the retained history alone at the time of the read with every unobserved fact treated as unobserved: for a head at incident phase `closed` the list MUST be empty and the history MUST end with that `closed` generation, so an operator can read the closure and its generation from the item id alone, without the reply of the write that recorded it; for a head at incident phase `drill-closed` the list MUST report no repayment outstanding, as this section already requires of readers; for any other head the list MUST be non-empty and MUST name each obligation the retained history leaves owed, so no reply for an unclosed incident can be read as a closure. `read-history` MUST read only through the authenticated canonical reader; a label, comment, metadata key, flag or caller assertion MUST NOT add, remove or reorder a generation. The reply MUST state that it authorizes no current effect and is not normal factory proof. For an item with no incident genesis it MUST refuse with the named reason `incident-authority-missing`, and when the chain cannot be walked or the tenant cannot be read it MUST refuse by name; it MUST NOT return an empty history, a partial history, or the generations it could read before the failure. A historical read of one exact attempt snapshot, where the writer offers one, MUST be a differently named action, MUST keep requiring the full fenced identity, and MUST NOT be presented as the item's history.

In `SPECIFICATION/scenarios.md`, insert the following named scenario immediately AFTER `## Scenario: incident completion requires final normal proof rather than an old repair merge` and BEFORE `## Scenario: a recorded scratch-branch drill closes through the drill-close action and a master incident is refused`, matching the named `## Scenario:` form every incident scenario in this file uses. The first line below is the new `## ` heading and lands outside the fence; the `Feature:` block that follows it lands inside a ```gherkin fence, as every neighbouring incident scenario does:

```gherkin
## Scenario: incident read-history returns every recorded generation by work-item id and a closed incident's history ends with its closed generation beside an empty outstanding list

Feature: incident read-history returns every recorded generation by work-item id and a closed incident's history ends with its closed generation beside an empty outstanding list

  Scenario: an incident with several attempts is inspected by its work-item id alone
    Given an incident whose retained authority history holds a failed expedited repair attempt with its pr-bound carrier, a corrected repair attempt, a reverting recovery attempt and a normal repayment attempt, each with several committed generations
    When the incident authority's read-history action is run with the repository and the canonical work-item id and no attempt identity
    Then it returns every committed generation of every attempt, oldest first, from the genesis root to the current head
    And each generation carries its attempt record exactly as recorded, the token that committed it and whether it is the current head
    And the failed attempt, the corrected attempt and the recovery attempt are each present as recorded, not only the current attempt
    And the reply states that it authorizes no current effect and is not normal factory proof

  Scenario: a closed incident exposes its closed generation and an empty outstanding list
    Given an incident whose closure write recorded incident phase closed as generation N
    When read-history is run for it by work-item id
    Then the returned history ends with the closed generation N
    And the reply carries outstanding as an empty list beside it
    And a read-history of an incident whose head is neither closed nor drill-closed carries a non-empty outstanding list naming each obligation the retained history leaves owed

  Scenario: read-history is never an empty or partial history
    Given an item with no incident genesis
    When read-history is run for it
    Then it refuses with incident-authority-missing rather than returning an empty history
    And when the chain of a recorded incident cannot be walked or its tenant cannot be read, read-history refuses by name rather than returning the generations it could read
```

The `## Scenario:` heading above is a new `## ` heading in `scenarios.md`, so the revise pass that accepts this proposal MUST add its row to `tests/heading-coverage.json` in the same change, per this repository's revise co-edit discipline: `spec_root` `SPECIFICATION`, `spec_file` `scenarios.md`, `test` `TODO`, a `reason` naming the owed tier ("A real test at the integration tier or above is owed for this incident read-history behaviour; bd-ib-92x3o owns implementation and proof.") and `work_item` `bd-ib-92x3o`, and regenerate `tests/heading-coverage-debt.json`. The row for `## Expedited incident lifecycle` itself already exists and is unchanged by this proposal.

No other section changes. The phase table, every transition and fence, `drill-close`, the closure requirements, the paragraph `Inspection MUST report ...` and the exact-identity historical snapshot read all keep their ratified text; this paragraph adds the reader those requirements assumed and bounds it.
